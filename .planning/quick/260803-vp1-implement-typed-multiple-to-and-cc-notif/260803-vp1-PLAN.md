<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CDT/SQMS caller to Workflow API | Caller-controlled recipient strings enter the engine; caller owns selection and validation by approved design. |
| Workflow API/application to SQL Server | Exact recipient arrays become durable task and outbox snapshots. |
| Outbox processor to SMTP relay | Persisted recipient values are parsed by MailKit and sent as one message. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-VP1-01 | Tampering | CanonicalRequestHasher | mitigate | Include ordered To/Cc arrays in the effective request hash so the same idempotency key plus changed recipients returns IdempotencyConflict. |
| T-VP1-02 | Information disclosure | RecipientOverride diagnostics | mitigate | Suppress all original To/Cc envelope recipients while override is active; expose intended lists only in the controlled message body for the override mailbox. |
| T-VP1-03 | Denial of service | Invalid recipient during MailKit construction/send | mitigate | Fail the single message, release the outbox claim, increment row RetryCount, store LastError, and leave the row Pending; no partial recipient tracking. |
| T-VP1-04 | Spoofing | Recipient selection | accept | The engine intentionally trusts authenticated/integrated callers to select and validate addresses; adding lookup or validation contradicts the approved generic boundary. |
| T-VP1-05 | Elevation of privilege | Workflow role vs email recipient | mitigate | Keep AssignedRoleKey authorization/task ownership unchanged and separate from NotificationRecipients; recipient arrays never authorize workflow actions. |
</threat_model>
