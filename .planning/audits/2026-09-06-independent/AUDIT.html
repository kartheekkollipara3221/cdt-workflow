Counterevidence and open questions
  • Caller-owned transactions: Execution deliberately avoids owning a transaction when CurrentTransaction exists. At WorkflowExecutionService:738–742, a late template failure returns ValidationFailed after earlier writes; transaction?.Rollback() then does nothing. Start and SQMS roll back failures when they own the outer transaction. A target caller that commits after failure can persist partial work. The live SQL probe demonstrated partial persistence when its deliberately misbehaving caller committed after failure; outer rollback preserved Draft. This remains an integration contract question, not proof that either real target caller commits failures. Establish rollback responsibility or add an operation savepoint with tracker recovery. EF's automatic SaveChanges savepoint covers that individual save, not all prior updates in the service. Official transaction guidance.
  • SLA synchronization concurrency: The completion/edit race is now demonstrated as F09. Other concurrent edit/monitor interleavings remain unexercised; existing rowversion and uniqueness protections should not be dismissed.
  • Resource ownership: Context has no per-business-object read authorization; transitions check roles rather than target-record membership. Whether additional ownership restrictions apply is external information, not a fabricated requirement. Header trust alone does not answer it.
  • Delivery semantics/configuration: Checked-in API settings select NoOp; console selects Console; SQMS is disabled by default. Successful processing marks messages Sent even for these senders. These may be intentional environment defaults. Actual production sender, SMTP TLS enforcement, credentials/network trust, schedule cadence and crash recovery operation were not verified. MailKit uses SecureSocketOptions.Auto; transport guarantees need the actual relay configuration.
  • Metadata integrity/versioning: Some definition references are scalar IDs/keys without EF relationships. Runtime checks cover many lookups, but not all inconsistent metadata combinations. Version-1 seed upserts modify/reactivate metadata in place. Full SQL DML/seed/upgrade reconciliation remains a coverage gap. No claim is made that deployed metadata is inconsistent.
  • Observability/status: Production exceptions get sanitized ProblemDetails and structured exception logs. Development does not install this custom handler, so mapped application exceptions can behave differently. Domain failures returned as results all map to HTTP 500, and CLI execute-json uses exit 0 for business failure. Preserve backward compatibility when making operational status clearer. Raw SMTP exception text reaches action-result messages; actual sensitive content depends on relay errors.
  • Exactly-once delivery: Token claims reduce duplicate workers, but SMTP acceptance followed by a crash/database failure can lead to redelivery. This cannot be resolved merely by a SQL transaction around sending. No exactly-once guarantee is established.
