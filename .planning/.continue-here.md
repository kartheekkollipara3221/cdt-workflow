<decisions_made>

- SQMS remains an in-process adapter. Do not create or imply a second standalone generic Workflow API.
- Target API owns Opportunity/Bid business persistence, HTTP contracts, trusted actor resolution, authorization, recipient lookup, and the outer transaction.
- Thin layer owns deterministic workflow identity, generic-engine calls, authoritative state projection, and refreshed workflow context.
- UI sends only target-owned form data plus selected `actionKey` and expected workflow version when applicable.
- UI must not send `toState`, `Status`, `WorkflowState` as authority, actor/roles, final recipients, template/link values, workflow instance IDs, or idempotency keys.
- Target API should return workflow state, version, and `availableActions`; UI refreshes from the response and does not hardcode state transition rules.
- `WorkflowState` already exists in both supplied target tables. The UI may display it, but it is a read-only integration value, not a user-editable database change.
</decisions_made>

## Critical Anti-Patterns (do NOT repeat these)

| Pattern | Description | Severity | Prevention Mechanism |
|---|---|---|---|
| Treat SQMS as standalone Workflow API | CDT public endpoints are not the SQMS integration surface. | advisory | Start the document with the in-process ownership diagram and exact `ISqmsWorkflowService` operations. |
| Say thin layer saves target business data | It only projects four workflow/audit columns. | advisory | Quote the exact `UPDATE` and list target-API-owned business columns separately. |
| Let UI control workflow authority | UI must not send next state, identity, recipients, templates, or links. | advisory | Include explicit UI sends/UI never sends tables. |
| Assume two EF contexts share a transaction automatically | A target-context transaction is not automatically visible to `WorkflowDbContext`. | advisory | Require the same open connection and explicit transaction enlistment; prove rollback with an integration test. |
