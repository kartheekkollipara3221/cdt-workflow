1. About this guide

1.1 Purpose and reader

This is the final hand-over document for the workflow engine component of CP Atlas. The reader is a .NET and SQL Server developer of the target team. The reader did not write this code.

After you read this guide, you can:

  • find the file and the member for a workflow behaviour;
  • follow one action from the request to the database and to the e-mail;
  • add or change workflow metadata with SQL scripts;

  • see which items are open and which decisions are not made.

The target API (the CP Atlas back end of the target team) calls the engine in-process. It does not call the engine over HTTP. The CDT, SQMSO and SQMSB apps use the engine. TTD and AIN do not use it.

2.1 What the engine does

  • It loads workflow definitions (metadata) from SQL Server. A workflow is rows, not code.
  • It starts one workflow instance for each business object. The instance ID is WF- + the business object ID (StartWorkflowService.Start).
  • It finds the next state from a transition row: definition version + current state + action key + role.
  • It closes and creates tasks, calculates SLA schedules, queues e-mail in the outbox and writes an audit row. All of this happens in one SQL transaction.
  • It returns the workflow context (current state, task, SLA, available actions) for a form.
  • It sends queued e-mail through an INotificationSender (Console, NoOp or SMTP with MailKit).

2.2 What the engine does not do

  • It has no timer and no hosted background service. A scheduled job must run the console commands. Timers never move a workflow state (owner decision O5).
  • It has no condition expressions. The caller selects the action key from the business decision. Each conditional path is its own action and transition (owner decision O6).
  • The request cannot set the next state. No request field names a toState.
  • workflow.options in the console envelope cannot override metadata. A conflict gives only a warning (WorkflowExecutionService.BuildOptionWarnings).
  • It does not authenticate users. The caller gives the user ID and roles. Authentication belongs to the target (decision D01).
  • It has no user-to-role table. The caller sends the roles of the actor.
  • It has no parallel branches. One instance has one current state and at most one Pending task (filtered unique index on WorkflowTask).
Portfolio Trade is sample metadata. Its keys are in seed classes and SQL scripts, not in the engine logic. Some literals are known exceptions: the first state Draft, the action key SaveDraft, and the console-only MakerPrimary check (decision D08, settled). See section 15.

5. Metadata and seed

5.1 How a workflow is described

A workflow is a set of rows for one definition version. To describe a workflow, write rows for these items:

  1. The definition (workflow key, business object type) and a version.
  2. The states. Mark the end states with IsTerminal. The first state must have the key Draft, because Start sets CurrentStateKey = "Draft" (StartWorkflowService.InsertFreshInstance).
  3. The roles and the actions.
  4. The tasks (owner role, optional SLA policy key) and, if necessary, the dynamic assignment roles.
  5. The participants that Start captures (for example originalMaker).
  6. The transitions: from state + action + allowed role gives to state, task to close, task to create, route.
  7. The SLA policies, the notification routes and the recipient rules.

A workflow with no tasks is valid. The SQMS workflows have no tasks and no SLA policies.

5.2 Portfolio Trade seed (C#)

The Portfolio Trade metadata is in C# seed classes. They are seed data, not engine logic.

  • PortfolioTradeSeedData: version 1 (states, roles, actions, SLA policies, tasks, routes, templates, recipient rules, assignment roles, transitions).
  • PortfolioTradeSeedDataV2: version 2 for CDT. Same keys, states, actions and transitions. New SLA timing, three new routes and new recipient groups.
  • WorkflowSeedService: SeedPortfolioTrade, SeedPortfolioTradeVersion2(activate), ActivatePortfolioTradeVersion(versionNumber). It inserts or updates rows, and sets old recipient rules inactive.

The console command init-db applies migrations and seeds version 1. The option --portfolio-trade-version 2 also seeds version 2 and makes it the only active version (WorkflowDatabaseInitializer.Initialize(int)).

5.3 Seed verification

The command verify-seed runs SeedVerificationService.Verify. It compares the database rows of PortfolioTrade version 1 (and version 2 if it exists) with the seed classes: key sets for states, roles, actions, tasks, routes, rules and transitions. It also checks that exactly one version is active. It checks only PortfolioTrade. SQMS has its own SQL verification script: 003_verify_sqms_deployment.sql.

5.5 Keys are stable identifiers

Workflow, state, action, task, role, SLA policy, notification route and template keys are integration identifiers. Callers, SQL scripts, stored instances, audit rows and outbox rows use them. Do not rename them, remove them or change their meaning in place. To change behaviour, add a new definition version (as CDT v2 does) and activate it with a script.

6.2 The steps in WorkflowExecutionService.Execute

File: WorkflowExecutionService.cs. Each check returns a result with a result code. Until step 5, nothing is written.

  1. Replay. TryBuildIdempotencyReplay: if a record has the same key and the same request hash, return the stored result (Replay = true). A different hash gives IdempotencyConflict.
  2. Instance. Read the instance. Missing gives WorkflowInstanceNotFound. If DeriveIdentityFromPersistence is true, copy the workflow key and the business object from the instance (ApplyPersistedIdentity). Then ValidateEnvelopeIdentity.
  3. Version and status. A different workflowDefinitionVersion in the request gives WorkflowDefinitionVersionMismatch. A Completed instance gives InvalidTransition.
  4. Action and transition. The action must be active in the version. The console also checks the section and button echo (ValidateActionEcho). Transitions are read for (version, current state, action). None gives InvalidTransition.
  5. Concurrency, first check. CheckConcurrency compares the optional expectedCurrentState, expectedCurrentTaskId, expectedCurrentTaskKey and expectedInstanceVersion. A difference gives ConcurrencyConflict with the current context.
  6. Role. The transitions whose AllowedRoleKey is in the actor roles match. No match gives Forbidden. Two matching roles give AmbiguousRoleMatch. The console flag --admin-override skips this check and audits the role AdminDemoOverride.
  7. Destination and inputs. The destination state must be active. ValidateAssignedRoleKey checks dynamic assignment. ValidateSlaInput requires slaInput.targetDate for an ApplicationTargetDate task. ValidateSlaReminderAudience resolves the reminder recipients. The recipient rules of the route are resolved (NotificationRecipientResolver.Resolve). Each failure gives ValidationFailed.
  8. Side effects (ExecuteSideEffects, one transaction):
    1. Read the instance and the pending task again. Run CheckConcurrency and CheckTransitionStillCurrent again.
    2. Console only: insert MockSectionData.
    3. If the action is not SaveDraft: UPDATE WorkflowInstance ... WHERE Id = @id AND Version = @v sets the new state, Version + 1, and Completed for a terminal state. Zero rows gives ConcurrencyConflict and a rollback.
    4. Close the task in TaskToCloseKey and call IWorkflowSlaSynchronizationService.Complete.
    5. Create the task in TaskToCreateKey with the recipient snapshot. If the task has an SLA policy, call Synchronize.
    6. If the transition has no task change and a task is pending, call Synchronize (a new target date can supersede the schedule).
    7. If the transition has a route: render the subject, the body and the HTML body. A missing template value gives ValidationFailed and a rollback. Insert one outbox row with status Pending.
    8. If the action is SaveDraft: no state change and no version change. If a task is pending, call Synchronize.
    9. Insert the audit row. Build the success result and the new context. Insert the idempotency record. Commit.

The transaction uses the default isolation level (READ COMMITTED). PROJECT.md section 15 does not permit SERIALIZABLE or SNAPSHOT in v1. If a caller already has a transaction on the same WorkflowDbContext, the service uses that transaction and does not commit it.

6.4 SaveDraft behaviour

SaveDraft is a transition row from a state to the same state (for example Draft to Draft). The engine compares the action key with the literal "SaveDraft". For SaveDraft, the engine does not run the version-guarded UPDATE. The instance Version does not change. The audit row has the same from and to state. This is the cause of the SaveDraft race in section 15.

6.5 SLA-only request

The API accepts a request with no actionKey and a slaTargetDate. WorkflowActionService then calls only IWorkflowSlaSynchronizationService.Synchronize for the pending task. It writes no audit row and does not change the version. It maps WorkflowSlaValidationException to HTTP 400. The result code is SlaSynchronized.

6.6 Start

StartWorkflowService.Start reads the one active version for the workflow key. It inserts the instance with state Draft, Status = Active and Version = 1. It captures the participants (WorkflowParticipantCaptureService). With InitialActionKey, it runs the first action in the same transaction. A second Start for the same business object gives AlreadyExists. Reset deletes all runtime rows of the instance; only the console uses it.

7. SLA

An SLA policy belongs to a task definition. When the engine creates the task, it makes an SLA schedule. A scheduled job runs the SLA monitor. The monitor queues reminder e-mail in the outbox. The SLA never moves a workflow state.

7.1 Policy modes

ModeDeadline (OverdueAtUtc)Recurrence
DurationFromTaskCreationTask creation + DurationMinutes. With OverdueStartsNextLocalDay: the next local day at ReminderLocalTime in TimeZoneId.RecurrenceIntervalMinutes (minute recurrence), or RecurrenceIntervalDays with a local reminder time, or none (one reminder).

The calculation is in SlaScheduleCalculator (CalculateDuration, CalculateApplicationDate, CalculateNextLocalDay, CalculateNextRecurringOccurrence, CalculateCalendarOccurrence). 7.3 The SLA monitor

File: RunSlaService.RunAsync(RunSlaRequest(Now)). The console command run-sla [--now <iso8601-utc>] calls it. Nothing in the engine calls it on a timer.

  1. Select candidates: schedule Active, NextReminderAtUtc <= now, task Pending, instance Active. The first page also counts all candidates and fixes an upper schedule ID. Schedules made during the run wait for the next run.
  2. Read pages of Sla:BatchSize rows (default 100) with a cursor on (NextReminderAtUtc, Id). Each page uses a new WorkflowDbContext.
  3. For each schedule, open a transaction and check the candidate again.
  4. Find the occurrence and its kind. Duration mode is always Overdue. Application-date mode is Overdue on or after target date + offset, else DueToday. Missed slots are not filled in (no backfill).
  5. If an outbox row for (schedule, occurrence time, kind) exists, move the cursor only.
  6. Else insert an outbox row. The subject is OverdueSubjectPrefix of the reminder route + the subject of the primary e-mail of the task. The body comes from the primary e-mail. The correlation ID is sla-{scheduleId}-{ticks}-{kind}. Move the cursor to the next occurrence. Commit.
  7. A data problem (missing route, missing primary e-mail, recipient snapshot not valid, subject longer than 300 characters) rolls back that schedule and adds a warning. The cursor does not move. The next run tries again.

Batching and context lifetimes: SLA_BATCH_PROCESSING.md. The primary e-mail is the outbox row with WorkflowTaskId = the task and no SlaReminderKind. So a transition that creates a task with an SLA policy must have a notification route.

8. Notifications and the outbox

8.1 Routes, rules and recipient snapshots

A transition names a route (NotificationRouteKey). The route has the templates and the recipient rules. NotificationRecipientResolver.Resolve makes the final To and Cc lists:

  • It reads the active rules of the route in SortOrder. A rule with an AssignedRoleKey applies only when the action assigns that role. A null AssignedRoleKey applies to all assignments.
  • Source types: StaticAddress (address in the row), WorkflowParticipant (captured at Start, for example originalMaker), RequestInput (from notification.recipientInputs, for example selectedCcUsers).
  • A required rule with no value is an error. The result must have at least one To address.
  • It removes duplicates without case. It keeps the first value as it was sent. To wins over Cc.
  • It does not check address syntax, the directory or the mailbox. Addresses are opaque strings.

The engine stores the result as JSON (the recipient snapshot) on the task and on the outbox row. A later change of a rule does not change a pending task or a queued row. The design is in multiple-notification-recipients-design.md.

8.2 Templates

NotificationTemplateRenderer replaces tokens {{key}} (letters, digits, underscore). Values come from notification.templateData plus the engine values workflowInstanceId, actionKey, oldState, newState, taskKey (WorkflowExecutionService.BuildNotificationContext). RenderHtml encodes each value for HTML. A missing or empty value is a validation error, and the action does not commit.

8.3 Outbox life cycle

Three places insert rows: WorkflowExecutionService (task and state e-mail), RunSlaService (SLA reminders) and QueueWorkflowNotificationService.QueueAsync (e-mail with no instance, keyed by NotificationOccurrenceKey; SQMS uses it). A second queue call with the same occurrence key returns the first row (Replay = true).

8.5 Retry

OutboxProcessingOptions.GetNextAttemptAtUtc calculates the next attempt: min(RetryMaxDelaySeconds, RetryInitialDelaySeconds × 2^RetryCount). With RetryInitialDelaySeconds = 0 (default), a failed row is eligible again at once. With a batch size, the worker writes the failure time so that a failed row goes behind mail that already waits (fix H01). Rollout notes: OUTBOX_RETRY_ROLLOUT.md and H01_OUTBOX_BATCH_BLOCKING_EXPLAINED.html.

8.6 Senders and SMTP

Notifications:Sender selects the INotificationSender in AddWorkflowInfrastructure: Console (default, ConsoleNotificationSender), NoOp (NoOpNotificationSender) or Smtp (SmtpNotificationSender). An unknown value stops the start-up.

SmtpNotificationSender uses MailKit. It connects with SecureSocketOptions.Auto. It does not authenticate (IP-restricted relay; credentials are stop-and-ask). It sends a plain text part and, if the HTML body is not empty, an HTML part. With Smtp:RecipientOverride, all mail goes to that one address, and the plain and HTML bodies start with a header that shows the original To and Cc.

14. How to change the engine safely

14.1 Backward compatibility (AGENTS.md)

  • Existing endpoints, actor headers, request and response JSON, status codes and field meanings must continue to work. New request fields must be optional.
  • Console commands, arguments, envelope fixtures and samples must stay executable.
  • Database changes must upgrade an existing database in place and keep its data. Add nullable columns and new tables. Do not rename, drop or change the meaning of a persisted column without an approved migration plan.
  • Keys (workflow, state, action, task, role, SLA policy, route, template) are stable identifiers.
  • Recipient snapshots, SLA behaviour and e-mail subject and body meanings must stay valid.
  • Keep the DI registration methods and the public .NET surfaces. Add overloads or optional parameters. Example: WorkflowExecutionService keeps an older constructor next to the new one, and ProcessNotificationOutboxService has a constructor with and without OutboxProcessingOptions.
  • Before you finish, run the regression gates of section 13 and the tests for the new behaviour.

14.2 Stop and ask first (PROJECT.md section 22)

Get approval from the owner before you do one of these:

  • change the shape of WorkflowActionEnvelope, WorkflowContextResponse or WorkflowActionResult;
  • change the Portfolio Trade transition matrix, or remove a Return to Maker path;
  • add an external package (only MailKit is pre-approved);
  • change the SQL schema in a non-trivial way;
  • add CQRS, MediatR, event sourcing, BPMN, sagas or message brokers;
  • remove seed verification, sample files, console commands or show-context;
  • change to parallel workflow, or make the engine depend on Portfolio Trade fields;
  • let the request set the next state, or let workflow.options override metadata;
  • add AdminDemoOverride as an allowed role in a transition row;
  • add conditional action fields without a conditional metadata model;
  • add a user table, a user-to-role table or a name lookup;
  • audit failed actions in v1;
  • call DateTime.UtcNow outside the composition root;
  • use SERIALIZABLE or SNAPSHOT isolation;
  • use PT-DEMO outside the demo command;
  • add a synthetic WorkflowStarted audit row or a nullable FromStateKey;
  • allow more than one instance for the same business object;
  • add SMTP credentials;
  • add recipient validation or rewriting, or change the recipient resolution rules.

14.3 Rules of the code

  • Use TimeProvider for the clock. The only TimeProvider.System registrations are in the composition roots (console and API Program.cs). A search finds no DateTime.UtcNow in src/ or workflow-api/src/.
  • Warnings are errors (Directory.Build.props).
  • Keep the engine generic. Put workflow behaviour in metadata rows.
  • Deliver a database change for the target as an idempotent SQL script in sql/upgrades/. If you also add an EF migration, say in the script that a database uses one or the other.
  • To change workflow behaviour, add a new definition version. Running instances stay on their version. Do not install an engine build that is older than the build that a running version needs.
  • A change in a runtime file that the target merged (for example the dispatcher or InfrastructureServiceCollectionExtensions.cs) needs a manual merge at the target. List these files in the release notes.

16. Glossary

TermMeaning in this guide
ActionA named step that a user or a system does, for example SubmitForChecker. Its key is the action key.
ActorThe user that sends the request: user ID, display name and roles. The caller gives these values.
Admin overrideConsole flag --admin-override. It skips the role check and audits the role AdminDemoOverride.
Assignment roleThe role of a created task when the task has dynamic assignment (assignedRoleKey).
Audit rowOne WorkflowAudit row for each successful action.
Business objectThe record of the app that the workflow is for, for example a trade. Type + ID.
CallerCode that calls the engine: the target API, the reference host, the console or the SQMS layer.
Definition versionOne WorkflowDefinitionVersion and all its metadata rows.
DeployedInstalled and running at the target.
DispatcherWorkflowActionNotificationDispatcher: it sends the e-mail of one action during the request.
EnvelopeWorkflowActionEnvelope: the internal object that describes one action request.
Idempotency keyA key that identifies one action request. The same key and the same request hash replay the stored result.
InstanceOne WorkflowInstance: the workflow of one business object. ID = WF- + business object ID.
LeaseThe 15 minutes for which a Processing outbox row belongs to one run.
MetadataThe definition rows (states, actions, transitions, tasks, policies, routes, rules).
OccurrenceOne reminder time of an SLA schedule, or one SQMS e-mail with an occurrence key.
Outbox rowOne NotificationOutbox row: one complete e-mail with its recipient snapshot and retry state.
ParticipantA person that Start captures for the instance, for example originalMaker.
Primary e-mailThe outbox row of the action that created a task. SLA reminders copy its subject and body.
PublishedCommitted and pushed to origin/console-code-first-0518.
Recipient ruleOne NotificationRecipientRule row: a To or Cc source for a route.
Recipient snapshotThe resolved To and Cc lists, stored as JSON on the task, the schedule or the outbox row.
Reference hostThe workflow-api project. It shows a correct use of the engine over HTTP.
Request hashA hash of the normalized request (CanonicalRequestHasher).
Result codeThe string in WorkflowActionResult.ResultCode, for example ConcurrencyConflict.
RouteOne NotificationRoute: templates and recipient rules for one kind of e-mail.
ScheduleOne WorkflowTaskSlaSchedule row for a task: deadline, next reminder and status.
SeedThe C# code that writes the Portfolio Trade metadata (init-db).
SLA policyOne SlaPolicy row: how to calculate the deadline and the reminders of a task.
SLA-only requestAn API request with no action key and a target date. It changes only the SLA schedule.
Stable identifierA key or a name that callers or stored data use. It must not change.
StateThe current position of an instance in its workflow (CurrentStateKey).
TargetThe CP Atlas system and code of the target team.
TaskOne WorkflowTask: the open work of a role. At most one task is Pending for each instance.
Terminal stateA state with IsTerminal = 1. A move to it completes the instance.
TransitionOne WorkflowTransitionDefinition row: from state + action + role gives the next state and the side effects.
WorkerA scheduled run of the console (run-sla, process-notification-outbox, run-sqms-scheduled).
