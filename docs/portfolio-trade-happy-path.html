Portfolio Trade · One happy path

How the engine moves one trade through the workflow

Maker submits a trade request. Checker approves it. Trading Desk executes the trade. Client Service confirms fulfillment. The engine controls each handoff.

A happy path is a successful sequence without a return for correction.

One trade request

ABC Capital requests a USD 1,000,000 purchase of a security. This business example explains the process. The engine does not calculate the trade amount.

The application identifies the trade as PT-HAPPY-1001. The engine identifies its workflow as WF-PT-HAPPY-1001.

A workflow instance is the engine record for this one trade request.

People in this example
PersonRoleWork
maker1MakerPrepare and submit the request.
checker1CheckerReview the request and select the desk.
trader1Trading DeskExecute the trade and record its execution.
bdrm1BDRM Client ServiceConfirm correct trade fulfillment.

A role is a named permission group. BDRM Client Service is the sample role for final confirmation. This page calls it Client Service.

The people perform the business work. The engine does not buy securities or settle trades. It controls state, tasks, deadlines, notifications, and history.

Four engine terms

  • A state is the current workflow stage.
  • An action key is the stable code for a user decision. For example, SubmitForChecker means “submit for review.”
  • A task is a record of work for a role. A pending task still needs completion.
  • Metadata is configuration in SQL Server. It defines states, actions, roles, tasks, deadlines, and notification rules.

SQL Server is the database system that stores these rules and workflow records. Seed data is the sample configuration that the repository supplies.

The instance has one current state. It can have at most one pending task.

The complete path

The instance version is a change counter. The engine increases it once for each state-changing action.

The definition version identifies the metadata set. It remains 1 throughout this example.

Stage 1 · Draft · Instance version 1

Maker prepares the request

The application starts the PortfolioTrade workflow for PT-HAPPY-1001. The engine selects the active definition version.

The engine creates the instance in Draft. It sets status to Active. It records the starting user and time.

The public Start request supplies the Maker address under notification.recipientInputs.originalMaker. The engine stores this address for later notifications.

A participant is a recipient that the engine stores for the workflow lifetime. The seeded originalMaker participant is required and immutable. Immutable means later actions cannot replace it.

The instance has no pending task in Draft. Starting the instance does not create an action history row.

Maker selects Submit

The application sends actionKey = SubmitForChecker. The engine finds the matching transition in SQL Server.

A transition is a metadata rule for movement between states. This rule maps Draft + SubmitForChecker + Maker to CheckerReview.

  • The engine moves the instance to CheckerReview.
  • It increases the instance version to 2.
  • It creates CheckerReviewTask for role Checker.
  • It starts the task deadline schedule.
  • It queues WorkflowTaskAssigned through RouteCheckerAssignedOnSubmit.
  • It records the action in history.

Maker can also select SaveDraft before submission. That action saves console section data and records history. It keeps state and instance version unchanged.

Stage 2 · CheckerReview · Instance version 2

Checker approves the request

Checker opens the request. The application gets workflow context: the current state, task, deadline status, and available actions.

Checker selects “Send to Trading Desk.” The application sends CheckerSendToTradingDesk.

Checker selects the Taxable desk. The application sends assignedRoleKey = TradingDeskTaxable. This value selects the role for the new task.

The application also sends slaTargetDate = 2030-01-20. The current Trading Desk policy requires this date.

  • The engine completes CheckerReviewTask and its deadline schedule.
  • It moves the instance to TradingDeskReview.
  • It increases the instance version to 3.
  • It creates TradingDeskReviewTask for TradingDeskTaxable.
  • It calculates the new deadline from the target date and policy.
  • It queues WorkflowTaskAssigned through RouteTradingDeskAssigned.
  • It records the Checker action in history.

The task belongs to the selected role. The engine leaves AssignedUserId null. Checker does not become the task assignee.

The selected desk controls task assignment and applicable recipient rules. The display value deskName controls email text only.

Stage 3 · TradingDeskReview · Instance version 3

Trading Desk records execution

Trading Desk executes the trade through its business process. Then trader1 selects “Trade Executed.”

The application sends TradingTradeExecuted. The seeded transition requires actor role TradingDesk.

The selected task role is TradingDeskTaxable. The actor role for this action remains TradingDesk. The upstream application supplies that trusted actor role.

  • The engine completes TradingDeskReviewTask and its deadline schedule.
  • It moves the instance to BdrmClientServiceReview.
  • It increases the instance version to 4.
  • It creates BdrmClientServiceReviewTask for BDRMClientService.
  • It starts the new task deadline schedule.
  • It queues WorkflowTaskAssigned through RouteBdrmAssigned.
  • It records the execution action in history.

The trade has an execution record. The workflow still needs Client Service confirmation.

Stage 4 · BdrmClientServiceReview · Instance version 4

Client Service confirms fulfillment

Client Service checks the trade result. Trading Desk executed the trade correctly. Settlement also completed correctly.

bdrm1 selects “Trade Fulfilled.” The application sends BdrmTradeFulfilled.

  • The engine completes BdrmClientServiceReviewTask and its deadline schedule.
  • It moves the instance to Completed.
  • It increases the instance version to 5.
  • It sets instance status to Completed and records the completion time.
  • It queues WorkflowCompleted through RouteWorkflowCompleted.
  • It records the fulfillment action in history.
Stage 5 · Completed · Instance version 5

The workflow has no remaining task

The engine creates no new task or deadline schedule. Workflow context returns no available actions.

The engine keeps the instance, completed tasks, and history in SQL Server. The completion route sends the final confirmation to the stored Maker address.

This business object has one workflow lifetime. Another Start request for the same object returns AlreadyExists.

How the engine processes one Checker action

Orchestration means that the engine coordinates several changes for one action. The Checker handoff shows this work.

Application request→Metadata checks→SQL transaction→Result and context→Email delivery

1. The application sends a decision

An API is a callable software interface. The public API receives this body at POST /v1/WorkflowAction.

JSON is a text format for structured data. This JSON shows the complete Checker body for the example.

{
  "workflowInstanceId": "WF-PT-HAPPY-1001",
  "actionKey": "CheckerSendToTradingDesk",
  "assignedRoleKey": "TradingDeskTaxable",
  "slaTargetDate": "2030-01-20",
  "notification": {
    "recipientInputs": {
      "selectedCcUsers": [
        {
          "userId": "checker1",
          "emailAddress": "checker.person@example.test",
          "displayName": "Checker One"
        }
      ]
    },
    "templateData": {
      "submitterDisplayName": "Maker One",
      "deskName": "Taxable",
      "securityType": "Bond",
      "accountShortName": "ABC",
      "accountDisplayName": "ABC Capital",
      "tradeLink": "https://application.example.test/trades/PT-HAPPY-1001"
    }
  }
}

This body assumes the instance already exists in CheckerReview. It also assumes Start captured maker.person@example.test as originalMaker.

The upstream application supplies X-Workflow-UserId: checker1 and X-Workflow-Roles: Checker. The API reads actor identity from these trusted headers.

The request sends the chosen action. SQL metadata supplies the destination state.

2. The engine checks persisted state and metadata

The API loads business identity through the engine. It generates internal request identifiers. The engine reads the instance and its pending task.

It matches this transition in the instance definition version:

FromStateKey         = CheckerReview
ActionKey            = CheckerSendToTradingDesk
AllowedRoleKey       = Checker
ToStateKey           = TradingDeskReview
TaskToCloseKey       = CheckerReviewTask
TaskToCreateKey      = TradingDeskReviewTask
NotificationRouteKey = RouteTradingDeskAssigned

It checks the selected assignment role against allowed task roles. It requires the target date for the new task policy.

It resolves recipients from the notification route. A notification route selects message templates and recipient rules.

The engine uses the same generic procedure for the other three actions. Their transition rows supply different states, tasks, and routes.

3. The engine commits the handoff

A transaction groups database changes. The database commits the group together or rolls it back.

  1. Recheck the current state, pending task, and instance version inside the transaction.
  2. Update the state to TradingDeskReview. Increase the version from 2 to 3.
  3. Complete the Checker task. Record the actor, completion time, and closing action.
  4. Complete its deadline schedule. Create the Trading Desk task and new schedule.
  5. Store the message and recipient snapshot in NotificationOutbox.
  6. Write the action history in WorkflowAudit.
  7. Store the successful result in IdempotencyRecord. Commit the transaction.

The outbox is a database queue of messages for delivery. An audit row records who performed an action and how the state changed.

Idempotency prevents duplicate execution for the same internal request key and content. The engine can return the stored result for that key.

The public API generates a new internal key for each HTTP request. It does not expose the console replay key to callers.

Optimistic concurrency checks that another action did not change the instance. A conflicting update cannot commit this handoff.

4. The API returns the result and context

The result reports the old state, new state, closed task, and created task. It also includes refreshed workflow context.

The context uses the submitting actor. Checker now sees TradingDeskReview and no available actions.

Trading Desk gets its own available actions when it opens the request.

Form data has a separate owner. The public workflow API does not accept or save trade form fields. The calling application owns that data and its transaction design.

The console uses an internal WorkflowActionEnvelope fixture. That fixture includes dataSave and simulated actor roles.

On the console path, the engine saves an append-only MockSectionData row in the workflow transaction. Append-only means each save adds a row. The public API disables that mock save.

How email and deadlines support the path

Email recipients

The public path uses the current route rules. For the Checker example, the checked-in seed selects these recipients:

  • To: taxable-trading-desk@example.test and taxable-trading-operations@example.test.
  • Cc: the stored Maker address and checker.person@example.test.

To identifies primary email recipients. Cc identifies copied recipients.

A snapshot is the exact recipient list stored for this action. The engine stores it on the task and outbox message.

The engine removes duplicate addresses without regard to letter case. To takes precedence over Cc.

The caller supplies the complete copied audience in selectedCcUsers for each action. The engine does not accumulate previous lists.

Later rule changes do not change existing snapshots. Deployed route rules can differ from the checked-in seed.

Task deadlines

SLA means service-level agreement. Here, an SLA policy defines a task deadline and reminder schedule.

The checked-in demo seed gives Checker and Client Service two-minute deadlines. Production policies can use different durations.

The Trading Desk policy uses the supplied target date. It sets a due-today reminder at 09:00 in America/New_York.

For target date 2030-01-20, the task becomes overdue at 09:00 on 2030-01-21 in that timezone.

The engine stores the overdue threshold in DueAtUtc. UTC is Coordinated Universal Time.

The run-sla processor checks active schedules on pending tasks. It queues due reminders from policy metadata.

SLA reminders reuse the task recipient snapshot. A reminder does not move the workflow state.

Delivery follows the database commit

The public API attempts delivery of the new action messages after engine execution. The console uses process-notification-outbox.

The configured sender handles delivery. The default console sender prints the message. The SMTP sender sends email through a mail server.

SMTP means Simple Mail Transfer Protocol. It is the protocol for sending email.

An email failure does not undo the committed workflow transition. The API can return NotificationDeliveryFailed after the state has changed.

The outbox retains failed messages for another delivery attempt. Workflow completion does not prove that every email reached a mailbox.

In this happy path, every person finishes before the task deadline. No overdue reminder is necessary.

What SQL Server holds at the end

For this path, assume one Start and four successful actions. Exclude the optional SaveDraft action and duplicate requests.
