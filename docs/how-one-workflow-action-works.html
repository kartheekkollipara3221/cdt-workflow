How one workflow action works

Read this guide to explain, debug, and maintain an action from request to stored result. Allow about 20 minutes for reading. Allow more time for the exercise.

This guide describes branch console-code-first-0518, inspected at commit 417f31ca878a2d12950f1fc59b93b8fd22e82d92. It uses the existing submit-for-checker sample. The evidence and SQL reference records verification results and limits.

1. What the engine owns

The engine selects a transition from SQL metadata. It changes workflow state, manages tasks and deadlines, queues notifications, and records successful actions. It uses .NET 10, EF Core, and SQL Server. A workflow instance has one current state and at most one pending task.

The calling application owns form data, field validation, authentication, and role resolution. Portfolio Trade supplies sample metadata. Its field values must not select transitions in the reusable engine. These are the intended boundaries in PROJECT.md, sections 5, 6, and 18.

There are two entry paths. Do not mix their request contracts.

Entry pathCaller suppliesAdapter behavior
Console execute-jsonWorkflowActionEnvelope, including actor, section payload, guards, and request identityValidates the envelope. Saves opaque section JSON to MockSectionData.
HTTP POST /v1/WorkflowActionWorkflowActionRequest, containing workflow-only fieldsResolves the trusted actor. Generates request identity. Loads business identity from persistence. Disables section saving.

Both paths call IWorkflowExecutionService.Execute. See the API boundaries for the full public contract. For integration inside a target API, use the existing target API integration reference.

2. Essential terms

TermMeaning in this engine
Workflow definitionThe named process, such as PortfolioTrade.
Definition versionA set of state, action, transition, task, SLA, and notification metadata. An instance refers to one version.
Workflow instanceThe stored execution for one business object. It has its own identity, current state, and status.
Instance versionAn integer used to detect a competing update. It is different from the definition version.
StateThe current workflow position, such as Draft.
ActionA requested operation, such as SubmitForChecker. It does not specify the destination state.
TransitionA metadata row selected by definition version, current state, action, and allowed role. It defines the destination and side effects.
Actor / roleThe user performing the action and the supplied roles used for transition authorization. A role is not an email address.
TaskWork assigned to a role. A task is Pending or Completed. The submitting actor is not automatically its assignee.
SLA policy / scheduleA service-level timing rule and its stored application to a task. The schedule tracks deadline and reminder timing.
Recipient snapshotThe final To/Cc arrays stored for a task or message. Later SLA messages reuse the task snapshot.
OutboxStored messages waiting for a sender. Queueing a message and delivering it are separate operations.
AuditA record of a successful action. Rejected attempts do not create audit rows.
Idempotency key / request hashA lookup key for an action attempt and a fingerprint of selected request content. Together they distinguish replay from conflicting reuse.
Correlation IDA value that connects an action with its audit and notification records. It is not the idempotency key.

4. Follow the request through the code

Step 1: Adapt and validate the request

Program.cs builds the services and calls CommandRegistry.Dispatch. ExecuteJsonCommandHandler.Execute reads and deserializes the file.

It calls WorkflowActionEnvelopeNormalizer.Normalize before validation and hashing. Console identity overrides therefore affect the request hash. Overrides also add a deterministic suffix to effective request IDs. This lets the sample run for separate demo objects without reusing one global idempotency key.

WorkflowActionEnvelopeValidator.Validate checks required blocks and the Maker button/action combination. It requires saveAsDraft=false for this submit action. It does not validate the business meaning of comment.

CanonicalRequestHasher.ComputeHash hashes selected content with stable object-property ordering. It preserves array order. It excludes transport identity fields such as correlation ID and requested time. Consult that method before changing replay behavior; the hash is not a hash of every envelope property.

Step 2: Resolve replay before current state

WorkflowExecutionService.Execute first calls TryBuildIdempotencyReplay.

  • No record: continue.
  • Same key and hash: return stored ResultJson, with replay diagnostics.
  • Same key and different hash: return IdempotencyConflict.

The replay must precede current-state checks. A successful submit has already left Draft. Checking its old guards first would reject a valid replay. PROJECT.md, section 9 states this reason explicitly.

Replay returns the stored context too. It does not refresh that context to the latest state.

Step 3: Find and authorize the transition

Execute loads the instance and validates identity. It then checks the definition version, completed status, action metadata, and console action echo. It loads active transitions for the instance's definition version, state, and action.

The service calls CheckConcurrency before role selection. It then selects a transition whose AllowedRoleKey matches an actor role. No matching role returns Forbidden. Multiple matching roles return AmbiguousRoleMatch.

For this request, metadata selects Draft -> CheckerReview. The engine does not calculate the next state from a stage number. The request does not select toState. This implements PROJECT.md, section 6.

ValidateAssignedRoleKey and ValidateSlaInput check the task requirements. Checker assignment is static, so this sample needs no desk selection or target date. BuildOptionWarnings reports conflicts with optional request hints; metadata still controls side effects.

For the API path, NotificationInput is present. The service calls NotificationRecipientResolver.Resolve before side effects. The seeded submit route selects static Checker To addresses, the captured originalMaker participant for Cc, and optional selectedCcUsers. Unknown inputs or missing required sources fail validation. The console sample supplies its final arrays directly. In both paths, storing a snapshot lets later SLA messages reuse the task's audience.

Step 4: Open the transaction and recheck

ExecuteSideEffects opens a transaction unless the caller already owns one on the same context. It reloads the instance and pending task. It runs CheckConcurrency and CheckTransitionStillCurrent again.

This recheck detects changes made after the first read. The state update also uses WHERE Id = ... AND Version = .... It increments Version. Zero updated rows produce ConcurrencyConflict.

The default transaction uses SQL Server READ COMMITTED. The conditional update and the unique pending-task index support concurrency control. PROJECT.md, section 15 states why the engine uses these mechanisms instead of SERIALIZABLE.

Step 5: Store the action effects

For this submit, ExecuteSideEffects performs these operations in the transaction:

  1. Adds the mock section save.
  2. Changes the state to CheckerReview and version to 2.
  3. Creates CheckerReviewTask with role Checker and AssignedUserId=null.
  4. Calls WorkflowSlaSynchronizationService.Synchronize. It creates schedule version 1 and projects its deadline onto WorkflowTask.DueAtUtc.
  5. Renders the route templates and queues one WorkflowTaskAssigned message.
  6. Writes the audit and builds the success result.
  7. Reads context for the submitting actor. Stores the canonical result in IdempotencyRecord. Commits.

Several SaveChanges calls occur before commit. They do not commit the outer transaction. The early task save obtains its SQL identity for the schedule and outbox references.

Template rendering can fail after writes have begun. The service rolls back its transaction in that case. It does not leave the workflow partly moved. If a caller supplies the transaction, that caller owns commit and rollback. Do not interpret a returned result as an independent commit in that case.

Step 6: Interpret the result

Expect Success, old state Draft, new state CheckerReview, one created task, a queued notification, and an audit summary. The result's context is for maker1. It does not imply that Maker can perform Checker actions.

WorkflowContextReader.Read and BuildAvailableActions use current state and actor roles. A separate context read as checker1 with role Checker exposes CheckerReturnToMaker and CheckerSendToTradingDesk.

The console handler wraps a structured workflow rejection in a successful command result. Inspect JSON result.success and result.resultCode; process exit code alone does not prove that the action succeeded.

6. What happens after commit

Console execution queues the assignment message. ProcessNotificationOutboxService.ProcessAsync delivers it when invoked. It claims a row as Processing, calls INotificationSender, then marks it Sent. A send exception returns the row to Pending, increments RetryCount, and records LastError. The processor continues with later rows unless cancellation stops it.

RunSlaService.RunAsync scans active schedules for pending tasks. Each candidate has a separate transaction. It queues eligible reminder occurrences and advances the schedule. It copies the task's recipient snapshot. It does not send email. An external scheduler must invoke the commands; storing a deadline does not start a timer.

Delivery is outside the workflow transaction. Do not claim exactly-once email delivery. A process can send a message and stop before it records Sent. The outbox processor can reclaim an expired processing lease after 15 minutes.

The HTTP path differs here

WorkflowActionService.ExecuteWorkflowAction generates a new GUID identity per call. It sets PersistSectionData=false, ValidateActionEcho=false, and DeriveIdentityFromPersistence=true.

After execution, it calls WorkflowActionNotificationDispatcher.DispatchCreatedNotifications. That dispatcher selects pending messages by workflow instance and action correlation ID. It attempts delivery before the HTTP response.

If delivery fails, the API changes the returned result to NotificationDeliveryFailed. WorkflowActionController.ExecuteWorkflowAction returns HTTP 500 for a failed workflow result. The workflow can already be committed. Inspect state and outbox before retrying. The stored engine result is the pre-dispatch success result.

Public WorkflowActionRequest accepts neither client idempotency keys nor expected-version guards. Repeating an HTTP body is a new attempt, not the console replay described below. After a successful submit, another submit has no transition from CheckerReview and returns InvalidTransition if the state remains there.

Order matters. These cases assume valid shape and identity unless stated otherwise.

A fresh key does not guarantee a concurrency error for an old submit. Transition lookup occurs before guard checks. If no transition exists from the current state, the result is InvalidTransition. Likewise, an unchanged successful request replays before its old version guard is checked.

No rejected attempt writes a failure audit. This is an explicit limitation in PROJECT.md, section 16.1. Capture the result code, failed guard, expected/actual values, correlation ID, and workflow instance ID for diagnosis.

9. Debugging exercise

Use .NET 10 and a disposable local SQL database. From the repo root, run the following PowerShell commands. init-db migrates and seeds the selected database. Choose a new database name if this one already contains useful data.

git branch --show-current
$env:ConnectionStrings__DefaultConnection = 'Server=DOLLY;Database=workflowengine_onboarding_local;Integrated Security=true;TrustServerCertificate=True;Encrypt=False'
$env:Notifications__Sender = 'Console'
dotnet build src/WorkflowEngine.sln -warnaserror
dotnet run --project src/WorkflowEngine.Console -- init-db
dotnet run --project src/WorkflowEngine.Console -- verify-seed
$onboardingId = 'PT-ONBOARD-' + [Guid]::NewGuid().ToString('N').Substring(0, 8)
$onboardingWorkflowId = 'WF-' + $onboardingId
dotnet run --project src/WorkflowEngine.Console -- start-workflow PortfolioTrade $onboardingId --user maker1

Confirm the requested branch before continuing. The new instance must be Draft/version 1, with no task. Keep the two generated IDs for inspection. No reset is needed.

Configure your debugger to launch WorkflowEngine.Console from the repo root. Give it the same environment variables. Use these arguments, replacing the two PowerShell variables with their generated values:

execute-json ./samples/workflow-actions/02-submit-for-checker.json --business-object <generated-object-id> --workflow-instance <generated-workflow-id> --format json

Set these breakpoints in the linked files from section 4:

BreakpointExpected observation

Run the action once in the debugger. Then inspect it:

dotnet run --project src/WorkflowEngine.Console -- show $onboardingWorkflowId
dotnet run --project src/WorkflowEngine.Console -- show-tasks $onboardingWorkflowId
dotnet run --project src/WorkflowEngine.Console -- show-history $onboardingWorkflowId
dotnet run --project src/WorkflowEngine.Console -- show-notifications $onboardingWorkflowId
dotnet run --project src/WorkflowEngine.Console -- show-context $onboardingWorkflowId --user checker1 --roles Checker --format json
dotnet run --project src/WorkflowEngine.Console -- execute-json ./samples/workflow-actions/02-submit-for-checker.json --business-object $onboardingId --workflow-instance $onboardingWorkflowId --format json

Compare the rows with section 5. The last command must replay. It must not create a second task or message. Run process-notification-outbox in this disposable database to observe Pending -> Processing -> Sent. With sender Console, Sent means that the console sender completed; it does not prove email delivery.

For deterministic failure debugging, run the focused test commands. Debug the missing-token rollback test and the stale-version test. These tests set up their own SQL state. Watch the result and query the tables after execution. Do not edit the tracked sample to simulate those failures.

10. Known discrepancies and verification limits

Source statementCurrent evidence and consequence
PROJECT.md section 15 puts validation, hashing, initial lookup, and authorization inside the transaction.The handler validates and hashes first. Execute performs initial checks before ExecuteSideEffects opens the transaction. The service rechecks state/task before writing. Do not describe all reads as one transactional snapshot.
The root README's form-open example shows CheckerReviewTask with ApplicationTargetDate.Checked-in PortfolioTradeSeedData.SlaPolicies assigns Checker a duration policy. This guide uses that seed and the tested submit path.

These discrepancies are reported, not resolved by this documentation task. Implementation and tests establish the described behavior. PROJECT.md remains the source of intended requirements.

Three questions you must be able to answer

  1. Which metadata row permits this actor's action, and which records must change together before it commits?
  2. Why does a repeated request replay, conflict, or fail a state/version check, and where can you prove the decision?
  3. If the API reports notification failure, how do you determine whether the workflow committed and which message needs recovery?
