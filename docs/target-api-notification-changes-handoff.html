Target API Notification Change Handoff

Use this checklist to apply the last two workflow notification changes to your target API: caller-supplied typed multiple To/Cc recipient snapshots, and persisted HTML email bodies.

Summary

Change 1: typed recipient snapshots

The target API selects and validates ordered To/Cc addresses from the business data it owns, then sends them in a dedicated notificationRecipients object. The reusable engine preserves the exact values, order, whitespace, and duplicates without lookup or normalization.

The created task and initial outbox row store the same recipient snapshot. SLA reminders copy the task snapshot unchanged.

Change 2: HTML notification bodies

Notification routes now store both a plain-text template and an HTML template. Queued outbox rows store both rendered bodies. SMTP sends multipart email when HTML is available.

The API must send plain values in notificationContext. The engine handles HTML escaping.

Keep this boundary: do not add recipient validation, trimming, deduplication, role/directory resolution, SQL/config address maps, singular fields, or delimited parsing to the engine. Do not let the UI send HTML. The business/API layer supplies validated recipient arrays and plain template values.

Database Updates

Historical HTML-body migration

Apply the older 20260620130000_AddHtmlNotificationBodies migration before deploying code that reads or writes HTML email bodies. Its equivalent SQL is: 

IF COL_LENGTH('dbo.NotificationRoute', 'HtmlBodyTemplate') IS NULL
BEGIN
    ALTER TABLE dbo.NotificationRoute
    ADD HtmlBodyTemplate nvarchar(max) NOT NULL
        CONSTRAINT DF_NotificationRoute_HtmlBodyTemplate DEFAULT ('');
END;

IF COL_LENGTH('dbo.NotificationOutbox', 'HtmlBody') IS NULL
BEGIN
    ALTER TABLE dbo.NotificationOutbox
    ADD HtmlBody nvarchar(max) NOT NULL
        CONSTRAINT DF_NotificationOutbox_HtmlBody DEFAULT ('');
END;
If your target API uses EF migrations, prefer an EF migration equivalent to 20260620130000_AddHtmlNotificationBodies. If deployment is DBA-controlled, use the SQL above as the implementation shape.

Recipient-snapshot migration

Next apply 20260803120000_AddNotificationRecipientSnapshots. It adds required nvarchar(max) recipient snapshots to both runtime tables and removes the obsolete recipient role and user columns from NotificationOutbox. For a DBA-controlled deployment, use this one-time SQL in the same order as the EF migration: 

BEGIN TRANSACTION;

DELETE FROM [dbo].[NotificationOutbox];
DELETE FROM [dbo].[WorkflowTask];

ALTER TABLE [dbo].[WorkflowTask]
    ADD [NotificationRecipientsJson] nvarchar(max) NOT NULL;

ALTER TABLE [dbo].[NotificationOutbox]
    ADD [NotificationRecipientsJson] nvarchar(max) NOT NULL;

ALTER TABLE [dbo].[NotificationOutbox]
    DROP COLUMN [RecipientRoleKey];

ALTER TABLE [dbo].[NotificationOutbox]
    DROP COLUMN [RecipientUserId];

COMMIT TRANSACTION;
Approved disposal boundary: delete NotificationOutbox rows first and WorkflowTask rows second. Do not delete workflow instances, workflow audit, mock section data, workflow definitions, transitions, routes, or other metadata. Do not invent a legacy backfill: old runtime rows do not contain an authoritative ordered typed To/Cc snapshot. Back up and obtain the target-system data owner's approval before applying this destructive migration outside a disposable environment.

Target API Changes

Request DTO shape

Reuse the shared application recipient contract; keep addresses outside notificationContext.

public sealed class WorkflowActionRequest
{
    public string? WorkflowInstanceId { get; set; }
    public string? ActionKey { get; set; }
    public string? AssignedRoleKey { get; set; }
    public Dictionary<string, string?>? NotificationContext { get; set; }
    public NotificationRecipients? NotificationRecipients { get; set; }
}

public sealed class NotificationRecipients
{
    public List<string> ToEmailAddresses { get; set; } = [];
    public List<string> CcEmailAddresses { get; set; } = [];
}

Immediate action notification dispatch

After workflow execution succeeds, deliver only rows created by that action. Select by WorkflowInstanceId plus CorrelationId. 

var resultEnvelope = workflowExecutionService.Execute(request);

if (resultEnvelope.Result.Success
    && resultEnvelope.Result.Notification?.Queued == true)
{
    var dispatch = notificationDispatcher.DispatchCreatedNotifications(
        resultEnvelope.Result.WorkflowInstanceId,
        resultEnvelope.Result.CorrelationId);

    if (!dispatch.Success)
    {
        resultEnvelope.Result.Success = false;
        resultEnvelope.Result.ResultCode = "NotificationDeliveryFailed";
        resultEnvelope.Result.Message = dispatch.FailureMessage;
    }
}
Do not dispatch all pending notifications from the API request. Dispatch only rows created by the current workflow action. The scheduled outbox processor handles old pending rows and retry backlog.

Reusable Engine Changes

Render plain and HTML templates

var renderedSubject = templateRenderer.Render(route.SubjectTemplate, notificationContext, "workflow.notificationContext");
var renderedBody = templateRenderer.Render(route.BodyTemplate, notificationContext, "workflow.notificationContext");
var renderedHtmlBody = templateRenderer.RenderHtml(route.HtmlBodyTemplate, notificationContext, "workflow.notificationContext");

var templateErrors = renderedSubject.Errors
    .Concat(renderedBody.Errors)
    .Concat(renderedHtmlBody.Errors)
    .ToArray();

Persist outbox row

dbContext.NotificationOutbox.Add(new NotificationOutbox
{
    WorkflowInstanceId = instance.WorkflowInstanceId,
    WorkflowTaskId = createdTask?.Id,
    BusinessObjectType = instance.BusinessObjectType,
    BusinessObjectId = instance.BusinessObjectId,
    NotificationType = route.NotificationType,
    NotificationRecipientsJson = notificationRecipientsJson,
    Subject = renderedSubject.Rendered,
    Body = renderedBody.Rendered,
    HtmlBody = renderedHtmlBody.Rendered,
    PayloadJson = JsonSerializer.Serialize(notificationContext),
    Status = "Pending",
    CorrelationId = normalized.EffectiveCorrelationId,
    CreatedAtUtc = timeProvider.GetUtcNow()
});

SMTP sender behavior

The sender should:

  • Without an override, add every persisted To and Cc item to one message in caller order.
  • Never resolve addresses from payload/template context, route roles, SQL, directories, or configuration maps.
  • Treat any MailKit parse/send failure as failure of the complete outbox row; retry is message-level.
  • With Smtp:RecipientOverride, send only to the override mailbox, suppress intended envelope recipients, and include both ordered intended lists in controlled diagnostics.
  • Send multipart email when HtmlBody is not blank.

Persist the exact same notificationRecipientsJson on the created task and initial outbox row. PayloadJson remains template context only. SLA reads and copies the task snapshot unchanged; missing or malformed task snapshots are warned and skipped rather than reconstructed.

Configuration

Use this shape while smoke testing. Keep RecipientOverride on until you are ready to send real mail.

{
  "Notifications": {
    "Sender": "Smtp"
  },
  "Smtp": {
    "Host": "smtp-relay.yourfirm.local",
    "Port": "25",
    "From": "workflow@yourfirm.com",
    "RecipientOverride": "operator-smoke-test@yourfirm.com"
  }
}
Smtp:RecipientOverride is the only delivery-address override. Remove it only when every notification-producing caller supplies validated To/Cc arrays.

Verification Checklist

  1. Apply the database migration.
  2. Run seed or metadata update so every notification route has HtmlBodyTemplate.
  3. Build the target API with warnings as errors.
  4. Start a workflow and execute an action that queues a notification.
  5. Confirm the created task and initial outbox row contain identical ordered NotificationRecipientsJson while PayloadJson contains template values only.
  6. Confirm NotificationOutbox.HtmlBody is not blank.
  7. With Smtp:RecipientOverride enabled, confirm the smoke mailbox is the only envelope recipient and sees both original ordered To/Cc lists in the body.
  8. Remove RecipientOverride only when ready to send real mail.
  9. Run the scheduled processor path for overdue and retry processing.
