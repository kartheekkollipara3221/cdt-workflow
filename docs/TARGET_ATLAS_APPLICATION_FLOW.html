CP Atlas application flow

This document shows how the CP Atlas application operates from end to end. It covers the framework, the security model, the business applications, the data stores and the workflow engine integration.

1. What CP Atlas is

CP Atlas is an internal web portal with many business modules. The database name (cp_sharepoint) and the old column names show that the modules replace earlier SharePoint lists. All modules use one framework. A JSON file for each module gives the screen layout, the rules and the workflow settings.

3. Metadata-driven framework

The framework has three parts: module JSON, the rules engine and reflection-based data mapping. A new module needs a JSON file, a service class, EF models, stored procedures and some UI routing code.

Validators: Required, Email, MinLength, MaxLength, Pattern. The UI applies the validators. The server does not validate again.

3.2 Rules engine (CPRule)

A rule has match criteria and effects.

  • Criteria: Roles, States, IsOwner. An empty criterion always agrees. Roles and states agree when one value is the same (case is ignored).
  • Effects: Visible, Disabled, EnableControls, DisableControls, ShowControls, HideControls.
  • The first rule that agrees is used.
  • ApplyRules sets controls. ApplyButtonRules sets buttons. ApplyTabRules and ApplyMenuRules set dashboard tabs and row menus.
  • The server applies the rules when it builds the response. The rules change only the Visible and Disabled flags in the response.

CDT also uses step States and step Roles. If the record state is not in the step States, or the user does not have a step role, the server disables all controls on that step.

3.3 Data mapping

  1. The UI sends Outputs as a list of {Name, Value}.
  2. MapData finds the entity property with the same name (case is ignored). It converts the value to the property type and sets it.
  3. MapData also returns the list of changed values. The service puts this list in the response.
  4. On load, BindData copies each entity property to the controls with the same Field.

3.4 Dashboard JSON (CPAtlasDashboardConfig.json)

Each module has a dashboard with Tabs and Buttons. A tab has a stored procedure, parameters (the value LANID becomes the user LAN ID), Menus (Edit, Delete, History), Rules and grid settings (Groups, Sums, ColumnTypes). The server returns the rows as KeyValues and the column widths as KeyLength.

4. Security model

  1. Authentication. IIS uses Windows authentication. The UI sends credentials with each call. The host also registers JWT bearer as the default scheme, but the UI does not send a token.
  2. Portal access. GET v1/authorize finds the user in Active Directory. It checks that the user is in a group from AppSettings:ADGroup. If not, it returns no user, and the UI shows /unauthorized-access.
  3. Module access. dbo.Get_Application returns the modules for the LAN ID. The UI shows these modules in the side menu.
  4. Module roles. The tables CP_Atlas_User, CP_Atlas_UserEntitlement and CP_Atlas_Entitlement give roles for each module. Examples: CDT "Directed Trades Checker", SQMS "MFO" and "IPG", AIN "Admin", "Write" and "Read".
  5. Enforcement. The server uses the roles to set visible and disabled flags on tabs, menus, buttons and controls. The save, delete and download endpoints do not check roles again.
  6. Workflow roles. The engine checks the actor roles for each action. CDT sends the roles from the step config. SQMS sends the user roles from the entitlement tables.

5. Request flows

5.1 Start-up (program.cs)

  1. The host reads appsettings.json from the application folder into a separate configuration object.
  2. The host registers CPSharepointContext and CPPBContext. TPAMAPIAccess adds the password to each connection string.
  3. The host registers TimeProvider.System and the engine helpers (normalizer, hasher, result builder, serializer).
  4. The host calls AddWorkflowInfrastructure and AddSqmsWorkflowIntegration.
  5. The host adds log4net, Swagger (development only), JWT bearer, CORS, controllers, static files and the index.html fallback.

5.2 Sign-in and menu

  1. The UI calls GET v1/authorize and keeps the user (profile, groups, roles).
  2. The UI calls GET v1/Application and builds the side menu with links to dashboard/<Code>.

5.3 Dashboard

  1. The UI calls GET v1/Dashboard?code=<Code>.
  2. The module service reads the user roles for the module.
  3. For each tab, the service runs the stored procedure and gets the rows.
  4. The service applies the menu, button and tab rules.
  5. The UI shows each visible tab as an ag-grid with a quick search, groups and totals.
  6. The row menu gives Edit, Delete and History. The header buttons open a new record.

5.4 Open a record

StepStepper module (CDT)Section modules (SQMSO, SQMSB, TTD, AIN)
1GET v1/Step gives the step list and the header (request type, account, state).—
2GET v1/StepPage gives one step.GET v1/SectionPage gives the full form.
3The service loads the entity and child rows. It fills look-up lists (users, accounts, opportunities, dates). It binds the values to the controls.
4The service compares the state with the step States and checks the step Roles.The service applies ApplyRules with roles, status and owner. SQMS also reads the engine context and adds the available-action buttons.
5The UI makes one form control for each config control, applies the validators and shows the page. Field-change code fills related fields (for example Account → Account Information).

5.5 Save a record

  1. The user clicks Save (or a workflow button on a section page). The UI validates the form.
  2. The UI sends POST v1/ManagePage as multipart data: input = {Code, Step, ID, Outputs}, and the files.
  3. The module service starts a transaction on CPSharepointContext.
  4. The service maps Outputs to the entity and adds the audit stamps.
  5. For a workflow module, the service calls the engine (section 6).
  6. The service saves child rows and attachments, then commits.
  7. The UI shows "Record saved successfully" and goes back to the dashboard.
  8. The UI interceptor sends the response (the changed values) to POST v1/AuditLog.

5.6 Other functions

  • Delete: POST v1/RemovePage sets IsDeleted = true.
  • Attachments: the service keeps file bytes as GZip in CDT_Attachment. On load, it writes the file to a folder and gives a v1/Download link. POST v1/RemoveAttachment sets IsDeleted.
  • History: GET v1/GetAuditLog reads <Code>AuditLog. The modal shows the date, the user and the changed values.
  • Account look-up: GET v1/Account?rmcode= gets an IMDS token and calls AccountInfo.
  • PB accounts: GET v1/PBAccounts and the SQMS and TTD pages read the Oracle views. A static cache keeps the list for 24 hours.
  • Make a Bid: GET v1/Execute?action=MakeBid makes a new bid page with opportunity values.

6. Workflow engine integration

The workflow engine is a separate, reusable code base. It knows only generic concepts: definition, version, instance, state, action, transition, role, task, SLA policy, notification outbox and audit. It does not know CP Atlas form fields. CP Atlas adds workflow functions to its modules through the engine.

6.1 Division of responsibility

CP Atlas does thisThe engine does this
Show the form and keep the business data (CDT_General, SQMS.*).Keep the workflow definition and version (states, actions, transitions, roles).
Select the action key from the form values (config Actions).Check that the action is valid for the current state and the actor roles.
Select the assigned role (config AssignRoles).Move the state. Close and open tasks. Record participants.
Collect recipients and template values.Make the recipient snapshot, render the template and queue the email in NotificationOutbox.
Send the target date (SlaInput).Make the SLA schedule and the reminders.
Copy the new state to its own WorkflowState column.Keep the audit history (WorkflowAudit) and idempotency records.
Show buttons from the available actions (SQMS).Return the workflow context (state, tasks, available actions).

6.2 Registration

  • AddWorkflowInfrastructure(configuration) registers WorkflowDbContext with the connection string DefaultConnection, the engine services and the email sender (Notifications:Sender = Smtp).
  • AddSqmsWorkflowIntegration(configuration) adds the SQMS workflow parts.
  • The engine tables are in cp_sharepoint, schema dbo. The engine uses its own DbContext and its own transactions.

6.3 The Workflow block in module JSON

"Workflow": {
  "Key": "PortfolioTrade",                 // engine workflow key
  "Roles": ["Checker"],                    // actor roles (CDT)
  "Actions": {                             // action key → conditions on entity fields
    "CheckerSendToTradingDesk": [{ "Name": "CheckerStatus", "Value": "Approve" }]
  },
  "AssignRoles": {                         // assigned role key → conditions
    "TradingDeskTaxable": [{ "Name": "CheckerStatus", "Value": "Approve" },
                           { "Name": "TradingDesk",   "Value": "Taxable" }]
  },
  "Notifications": {                       // config action key → engine call settings
    "CheckerSendToTradingDesk": {
      "ActionKey": "CheckerSendToTradingDesk",   // key sent to the engine
      "IsSLA": true,                             // send TargetCompletionDate as SlaInput
      "IsExecuteInvoke": true,                   // false = do not call the engine
      "Request": {
        "recipientInputs": { "selectedCcUsers": [] },
        "templateData": { "deskName": "TradingDesk", "tradeLink": "URL/stepmaster/CDT/ID" }
      }
    }
  },
  "AdditionalInfo": { "CheckerReturnToMaker": ["CHECKERREMARKHISTORY"] }
}

The service examines each Actions entry. All conditions in an entry must agree. If two or more entries agree, the last entry is used.

6.5 Background processing

CP Atlas sends action emails in the request. SLA reminders and outbox retries need the engine console commands run-sla and process-notification-outbox. CP Atlas does not register a background worker. A scheduled job must start these commands.

7.2 Recipients and status

  • originalMaker: the user whose display name is in CreatedBy.
  • selectedCcUsers: the emails in InitiatorNotificationGroup and the users in InitialAdditionalWatcher. The default group holds users with the roles IM Risk, Client Service and BDRM Support, plus the Relationship Manager.
  • Template values: referenceNumber (CDT-{id}), tradeLink, desk, security type, account, submitter, and the user who returned the trade.
  • The local column Status is "Trade Request" until the state is Completed. Then it is "Trade Settled". The dashboard tabs "Pending Trades" and "Completed Trades" use this column.

8. SQMS: Opportunity and Bid

SQMS is a secondary market for client holdings in private funds. Roles: MFO (relationship managers), IPG (investment team), ADMIN, and "Seller" (given at run time).

8.1 Opportunity (SQMSO, workflow SqmsOpportunity)

  1. An MFO RM (the seller) makes an opportunity: account (PB accounts), fund, vehicle, full or partial commitment, sale amount, rationale. The effective date is the start of the next quarter.
  2. The service starts the workflow with SubmitOpportunity.
  3. IPG adds valuation data: management fee, minimum bid, latest valuation, contributions, distributions, estimated fair value, remaining commitment.
  4. The page shows one button for each engine available action. The button sets Status, and the save runs the action.
  5. Statuses: DRAFT, SUBMITTED, PENDING, OPEN TO BIDDING, PENDING SELLER APPROVAL, AWAITING ALLOCATION, PARTIALLY ALLOCATED, NOT FULFILLED, COMPLETED.

8.2 Bid (SQMSB, workflow SqmsBid)

  1. An MFO user who does not own the opportunity clicks "Make a Bid" on an opportunity that is OPEN TO BIDDING.
  2. The bid page gets the fund, vehicle, amounts and fair value from the opportunity.
  3. The buyer enters the buyer RM team, the buyer account (PB accounts for the user branch), full commitment Yes or No, the amount and the percent of fair value.
  4. The service starts the workflow with SubmitBid.
  5. The rule CHECKSELLER gives the role "Seller" to the opportunity owner or a member of its seller RM team. The seller accepts, partially accepts or rejects the bid.
  6. After each bid save, the service writes the total, largest and lowest bid to the opportunity.
  7. Statuses: SUBMITTED, UNDER REVIEW BY SELLER, ACCEPTED, PARTIALLY ACCEPTED, NOT ACCEPTED.

8.3 Dashboard tabs

My Opportunities, My Bids, IPG Opportunities, IPG Bids, Open To Bidding, Pending Seller Approval (MFO). "My" means rows that the user made or rows where the user name is in the RM team.

Recipients: sellerRmTeam or buyerRmTeam, and relationshipManager. SQMS does not send SLA input or an assigned role.

9. TTD: Tax Time Database

TTD does not use the workflow engine.

  • A tax preparer records one week of time: account (PB accounts), tax year, category (OTHER, STMT_N, TAX_N), description, preparer and week-ending Sunday.
  • A grid has minutes for each day (Monday to Sunday) and a weekly total. The UI calculates the total.
  • Dashboard tabs: Current Tax Timesheet (my rows), Tax Time All Report, Tax Time Report (rows where I am the preparer).

10. AIN: Account Inventory

AIN does not use the workflow engine.

  • One master record for each investment-management account: client family, custodian, reporting lead, KYC, close date, mailing status, portfolio managers, strategy, security identifiers, market-data licence and AUM.
  • Roles: Admin can edit all fields. Write can edit 12 fields. Read can only view.
  • The dashboard runs AIN.Get_AccountInventory.
