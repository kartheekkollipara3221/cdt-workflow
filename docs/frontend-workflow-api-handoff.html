Frontend Workflow API Handoff

This guide reflects the optimized public DTOs in the live reference API.

TypeScript request types

type WorkflowRecipientInput = {
  userId?: string | null;
  emailAddress?: string | null;
  displayName?: string | null;
};

type WorkflowNotificationInput = {
  recipientInputs?: Record<string, WorkflowRecipientInput[] | null>;
  templateData?: Record<string, string | null>;
};

type WorkflowStartRequest = {
  workflowKey: string;
  businessObjectId: string;
  actionKey?: string | null;
  slaTargetDate?: string | null; // yyyy-MM-dd
  notification?: WorkflowNotificationInput | null;
};

type WorkflowActionRequest = {
  workflowInstanceId: string;
  actionKey?: string | null;
  assignedRoleKey?: string | null;
  slaTargetDate?: string | null; // yyyy-MM-dd
  notification?: WorkflowNotificationInput | null;
};

Actor transport

X-Workflow-UserId: maker1
X-Workflow-Roles: Maker
X-Workflow-DisplayName: Maker One

These headers model a trusted upstream identity adapter. Do not copy user or role values from editable body fields.

Starting the workflow

POST /v1/WorkflowStart
Content-Type: application/json

{
  "workflowKey": "PortfolioTrade",
  "businessObjectId": "PT-FE-1001",
  "actionKey": "SubmitForChecker",
  "notification": {
    "recipientInputs": {
      "originalMaker": [
        {
          "userId": "maker1",
          "emailAddress": "maker@example.test",
          "displayName": "Maker One"
        }
      ],
      "selectedCcUsers": []
    },
    "templateData": {
      "referenceNumber": "1050",
      "submitterDisplayName": "Maker One",
      "tradeLink": "https://example.test/trades/PT-FE-1001"

Persist the returned workflowInstanceId with the business record. Use it for context reads and all later actions.

Opening or refreshing the form

GET /v1/WorkflowContext?workflowInstanceId=WF-PT-FE-1001

Render buttons from result.workflowContext.availableActions. Submit the selected actionKey. Do not infer or submit destination state.

Recipient input rules in seeded metadata

OperationAllowed UI inputFinal placement
Workflow StartoriginalMaker requiredCaptured for later metadata routes.
SubmitForCheckerselectedCcUsers optionalChecker static address is To; selected users are Cc.
CheckerReturnToMakerselectedCcUsers optionalCaptured Maker is To; selected users and operations metadata are Cc.
Other seeded routesNo request recipient input unless metadata declares oneStatic or captured sources determine recipients.
The UI resolves the Maker and any selected users. It does not choose To versus Cc. It may submit opaque address strings, including values that are not syntactically valid email addresses; the workflow API stores them without syntax, directory, mailbox, or SMTP validation. Do not trim or rewrite address strings before calling workflow if exact preservation is required.

Do not send

Do not send toState, form payload, business-object type on Start, workflow/business identity on Action, expected-state/task/version guards, request/correlation/idempotency IDs, final To/Cc arrays, UI button labels, action reason, SLA configuration, route keys, or dueAtUtc. Unknown root or nested fields are rejected.

Error handling

  • HTTP/model-binding failures return ProblemDetails.
  • Workflow failures return the API response wrapper with a failed action result and HTTP 500 under the current boundary.
  • After a successful action, replace local workflow UI state with returned workflowContext.
  • If immediate delivery fails after commit, show failure and allow server-side outbox retry; do not resubmit a guessed transition.
