Frontend Workflow API Handoff

This handoff explains the current reference API in workflow-api/WorkflowEngine.WorkflowApi.slnx. It is for a frontend developer who needs to open a workflow-backed form, render workflow actions, call the workflow endpoints, and run the full Portfolio Trade happy path.

Updated: 2026-06-09 Reference host: workflow-api Base URL: http://localhost:5058 Workflow key: PortfolioTrade JSON model fields: PascalCase
1. Quick Start 2. Required Headers 3. JSON Casing 4. Endpoint Contracts 5. Frontend Rules 6. Full Happy Path Demo 7. Response Fields To Use 8. Errors

1. Quick Start

Run this against the reference ASP.NET Core host under workflow-api/. The current local http launch profile uses http://localhost:5058 and exposes Swagger UI at the root. 

dotnet run --project workflow-api\src\WorkflowEngine.WorkflowApi --launch-profile http
Notification delivery matters for the demo. The http launch profile sets Notifications__Sender=Smtp with Smtp__Host=localhost and Smtp__Port=3025. Start smtp4dev on port 3025 before running action steps that queue email, or override Notifications__Sender=NoOp for a UI-only smoke test.
API owns

Workflow state, tasks, SLA state, notification outbox rows, audit rows, and workflow context.

API does not own

Form field data, form validation, user lookup, business object creation, or UI button rendering.

Frontend reads

result.workflowContext.AvailableActions to decide which workflow buttons to show.

2. Required Headers

The reference API uses trusted actor headers. They are temporary integration headers, not a permanent authentication model.

Header Required Example Meaning
X-Workflow-UserId Yes maker1 User identifier recorded as workflow evidence.
X-Workflow-Roles Yes Maker, Checker, TradingDesk, BDRMClientService Comma- or semicolon-separated workflow roles used for metadata authorization.
X-Workflow-DisplayName No Maker One Friendly actor name. If omitted, the API uses X-Workflow-UserId.
For Trading Desk actions, send X-Workflow-Roles: TradingDesk. The AssignedRoleKey field selects the specific desk task recipient such as TradingDeskTaxable; the actor action itself is still authorized by the broad TradingDesk role.

3. JSON Casing

The current reference API sets JsonSerializerOptions.PropertyNamingPolicy = null. Use PascalCase for model fields. The top-level wrapper names result, actionResult, and workflowContext are explicitly configured as lower-case names. 

{
  "result": {
    "actionResult": {
      "Success": true,
      "ResultCode": "Success",
      "WorkflowInstanceId": "WF-PT-FE-1001"
    },
    "workflowContext": {
      "Workflow": {
        "CurrentState": "CheckerReview"
      }
    }
  }
}

4. Endpoint Contracts

POST /v1/WorkflowStart

Starts one workflow instance for a business object. For the demo path, use InitialActionKey = SubmitForChecker so the first call represents Maker submit.

Body field Required Example Notes
WorkflowKey Yes PortfolioTrade Seeded workflow definition key.
BusinessObjectType Yes PortfolioTrade Business object type supplied by the calling app.
BusinessObjectId Yes PT-FE-1001 Must be unique for each demo run. The generated workflow instance id is WF-{BusinessObjectId}.
InitialActionKey No SubmitForChecker When present, starts the workflow and immediately executes the first metadata-valid action.
NotificationContext Only when the action queues a templated notification Dictionary of string keys and values Blank keys and blank values are ignored. Keys and values are trimmed.

GET /v1/WorkflowContext

Reads the workflow state for form-open or after-action refresh. The frontend should call this with the currently logged-in actor's workflow headers.

Query field Required Example Notes
workflowInstanceId Yes WF-PT-FE-1001 Returned by WorkflowStart and every action response.

POST /v1/WorkflowAction

Executes one workflow action on an existing workflow instance. This endpoint is workflow-only. It does not accept or persist form section payload data.

Body field Required Example Notes
WorkflowInstanceId Yes WF-PT-FE-1001 Workflow instance to move.
ActionKey Yes CheckerReturnToMaker Must be one of the actor's current AvailableActions.
AssignedRoleKey Only for dynamic Trading Desk assignment TradingDeskTaxable Required when CheckerSendToTradingDesk creates TradingDeskReviewTask.
NotificationContext Only when the action queues a templated notification Dictionary of string keys and values Provides template values and, for Return to Maker, recipientEmail.

5. Frontend Rules

Do this. On form open and after each workflow action, read workflowContext. Render workflow buttons from workflowContext.AvailableActions. Send only the selected action key and supported workflow fields.
Do not send these fields to /v1/WorkflowAction: toState, form payload, field values, BusinessObjectId, BusinessObjectType, WorkflowKey, ExpectedCurrentState, ExpectedCurrentTaskId, ExpectedCurrentTaskKey, ExpectedInstanceVersion, sectionKey, buttonKey, buttonLabelShown, or saveAsDraft.

Important SaveDraft boundary

SaveDraft is a workflow action. In the reference API it keeps the workflow in Draft or ReturnedToMaker and does not create tasks or notifications. It does not save form fields because this API intentionally has no form payload. The form/business API must save draft field data separately.

Maker primary button mapping

Current state Save as Draft checked Save as Draft unchecked
Draft SaveDraft SubmitForChecker
ReturnedToMaker SaveDraft ResubmitForChecker

7. Response Fields To Use

Action response shape

{
  "result": {
    "actionResult": {
      "Success": true,
      "ResultCode": "Success",
      "WorkflowInstanceId": "WF-PT-FE-1001",
      "ActionKey": "CheckerSendToTradingDesk",
      "OldState": "CheckerReview",
      "NewState": "TradingDeskReview",
      "ClosedTask": {
        "TaskKey": "CheckerReviewTask",
        "AssignedRole": "Checker"
      },
      "CreatedTask": {
        "TaskKey": "TradingDeskReviewTask",
        "AssignedRole": "TradingDeskTaxable",
        "DueAtUtc": "2026-06-09T16:02:00Z"
      },
      "Notification": {
        "Queued": true,
        "NotificationType": "WorkflowTaskAssigned",
        "RecipientRole": "TradingDeskTaxable"
      }
    },
    "workflowContext": {
      "Workflow": {
        "WorkflowInstanceId": "WF-PT-FE-1001",
        "CurrentState": "TradingDeskReview",
        "Status": "Active"
      }
    }
  }
}

Workflow context fields

Field Frontend use
Workflow.CurrentState Current workflow state, such as CheckerReview or Completed.
Workflow.Status Active or Completed.
CurrentTask Current pending task, or null after completion.
Sla.Status NoSla, OnTrack, or Overdue.
ActorAccess.CanAct Whether the actor has any action in the current state.
ActorAccess.ReadOnlyReason Reason the current actor cannot act, useful for read-only messaging.
AvailableActions Source of truth for workflow buttons.

Available action item shape

{
  "ActionKey": "CheckerSendToTradingDesk",
  "SectionKey": "Checker",
  "ButtonKey": "CheckerPrimary",
  "ButtonLabel": "Send to Trading Desk",
  "Intent": "Approve",
  "RequiresReason": false,
  "RequestDefaults": {
    "WorkflowKey": "PortfolioTrade",
    "WorkflowInstanceId": "WF-PT-FE-1001",
    "WorkflowDefinitionVersion": 1,
    "ExpectedCurrentState": "CheckerReview",
    "ExpectedCurrentTaskId": "42",
    "ExpectedCurrentTaskKey": "CheckerReviewTask",
    "ExpectedInstanceVersion": 3
  }
}
RequestDefaults are useful display/debug context in this reference API, but POST /v1/WorkflowAction does not accept those guard fields. Send only WorkflowInstanceId, ActionKey, optional AssignedRoleKey, and optional NotificationContext.
RequiresReason is returned from workflow metadata for actions such as Return to Maker, but the current reference POST /v1/WorkflowAction body does not accept an action reason field. Do not add ActionReason to the frontend request unless the API contract is explicitly changed later.

8. Errors

Status Body Frontend handling
200 WorkflowStartApiResponse, WorkflowActionApiResponse, or WorkflowContextApiResponse Read result. For action/start, require result.actionResult.Success === true.
400 ProblemDetails Request is malformed or required fields are missing. Show detail.
401 ProblemDetails X-Workflow-UserId is missing.
403 ProblemDetails X-Workflow-Roles is missing or empty.
404 ProblemDetails Workflow instance was not found.
500 Either WorkflowActionApiResponse with Success=false, or ProblemDetails Workflow failed, notification delivery failed, or an unexpected error occurred. Show Message or detail.

Common workflow failure result

{
  "result": {
    "actionResult": {
      "Success": false,
      "ResultCode": "ValidationFailed",
      "Message": "Workflow action request failed validation.",
      "Diagnostics": {
        "ValidationErrors": [
          {
            "Field": "workflow.assignedRoleKey",
            "Message": "workflow.assignedRoleKey is required when creating task 'TradingDeskReviewTask'."
          }
        ]
      }
    },
    "workflowContext": null
  }
}
If SMTP delivery fails after a workflow action commits, the API returns ResultCode = NotificationDeliveryFailed and HTTP 500. The notification row remains pending for retry by the outbox processor.
