1. Scope

Source files checked

This document is based on the current code in workflow-api/src/WorkflowEngine.WorkflowApi, src/WorkflowEngine.Application/Commands, and src/WorkflowEngine.Infrastructure/Persistence/Seed/PortfolioTradeSeedData.cs.

API body models

The API exposes two POST body models: WorkflowStartRequest and WorkflowActionRequest. GET /v1/WorkflowContext has no JSON body.

Workflow-only boundary

The workflow API does not save form fields, validate Portfolio Trade data, create business records, authenticate users, or decide next state from request JSON.

Portfolio Trade

Portfolio Trade is sample seed metadata. It provides the current action list and flow examples, but the reusable engine must stay metadata-driven.

3. Endpoint Inventory

Endpoint Body Use Response wrapper
POST /v1/WorkflowStart WorkflowStartRequest Starts a workflow instance for a business object. Can optionally execute the first metadata-valid action. result.actionResult and result.workflowContext
GET /v1/WorkflowContext?workflowInstanceId=WF-PT-1001 None Reads current state, task, SLA, actor access, and available actions. result.workflowContext
POST /v1/WorkflowAction WorkflowActionRequest Executes one workflow-only action against an existing workflow instance. result.actionResult and result.workflowContext

JSON property names

Examples use lower camel case names such as workflowKey and workflowInstanceId. Keep that shape in target API contracts even though the C# request properties are PascalCase.

4. Workflow Flow

Reference API call flow

Target app saves or loads business data. The workflow API only receives business object identity and workflow action data.
Start the workflow. Call POST /v1/WorkflowStart with workflowKey, businessObjectType, and businessObjectId.
Open the form with workflow context. Call GET /v1/WorkflowContext. Use the returned available actions and current task to decide which form buttons are enabled.
Execute an action. Call POST /v1/WorkflowAction with workflowInstanceId, actionKey, optional assignedRoleKey, and optional notificationContext.
Refresh UI from returned context. Do not guess next state in the client. The API returns the action result and refreshed workflow context.

5. WorkflowStart JSON Bodies

POST /v1/WorkflowStart requires workflowKey, businessObjectType, and businessObjectId. It accepts optional initialActionKey and optional notificationContext.

Start only: create Draft workflow

{
  "workflowKey": "PortfolioTrade",
  "businessObjectType": "PortfolioTrade",
  "businessObjectId": "PT-1001"
}

Start and save first draft

This starts the workflow and immediately executes the metadata action SaveDraft. It stays in Draft and does not queue an email for the current Portfolio Trade seed. 

{
  "workflowKey": "PortfolioTrade",
  "businessObjectType": "PortfolioTrade",
  "businessObjectId": "PT-1001",
  "initialActionKey": "SaveDraft"
}

Start and submit to Checker in one call

This starts the workflow and immediately executes SubmitForChecker. Include notification data because this transition queues a Checker assignment email. 

{
  "workflowKey": "PortfolioTrade",
  "businessObjectType": "PortfolioTrade",
  "businessObjectId": "PT-1001",
  "initialActionKey": "SubmitForChecker",
  "notificationContext": {
    "referenceNumber": "1050",
    "submitterDisplayName": "Maker User One",
    "recipientDisplayName": "Checker Team",
    "deskName": "Taxable",
    "securityType": "Other",
    "accountShortName": "EFG",
    "accountDisplayName": "INSURANCE-5091003029-EFG INSURANCE, LTD./ASI",
    "submittedDate": "4/24/2026",
    "tradeLink": "https://sharepoint.example.test/trades/1050"
  }
}

Start endpoint restrictions

The start body does not accept reset, form payload, task IDs, expected state, expected version, source system, client action ID, correlation ID, or idempotency key.

8. Notification Context

notificationContext is a string key/value dictionary used only for notification rendering. Blank keys and blank values are ignored. It is not form payload and it does not drive workflow transitions.

Scenario Actions Useful keys
Task assigned to Checker SubmitForChecker, ResubmitForChecker referenceNumber, submitterDisplayName, recipientDisplayName, deskName, securityType, accountShortName, accountDisplayName, submittedDate, tradeLink
Return to Maker CheckerReturnToMaker, TradingReturnToMaker referenceNumber, returnedByDisplayName, recipientDisplayName, recipientEmail, ccEmailAddresses, accountShortName, accountDisplayName, submittedDate, tradeLink
Task assigned to Trading Desk CheckerSendToTradingDesk, BdrmTradeNotExecutedProperly referenceNumber, submitterDisplayName, recipientDisplayName, deskName, securityType, accountShortName, accountDisplayName, submittedDate, tradeLink
Task assigned to BDRM TradingTradeExecuted referenceNumber, traderDisplayName, deskName, securityType, accountShortName, accountDisplayName, tradeLink
Workflow completed BdrmTradeFulfilled referenceNumber, confirmerDisplayName, accountShortName, accountDisplayName, tradeLink
SLA overdue Created by run-sla, not by API JSON workflowInstanceId, taskKey, assignedRoleKey, dueAtUtc, overdueAtUtc are added by the SLA service.

Recipient handling

For per-record Maker emails, include recipientEmail. For copied recipients, include ccEmailAddresses as comma- or semicolon-separated addresses. Keep both inside notificationContext; do not add a new public DTO field.

9. Fields Not To Send

The reference API intentionally hides the low-level console envelope. Do not add these fields to target API request bodies unless the project owner explicitly changes the boundary.

Do not send Reason
toState SQL transition metadata decides the next state.
dataSave, payload, form section fields The target business API owns form data persistence.
uiAction, sectionKey, buttonKey, buttonLabelShown, saveAsDraft The API executes workflow action keys only. UI echo fields are console-envelope scope.
workflowKey, businessObjectType, businessObjectId on WorkflowAction The action endpoint derives these from persisted workflow instance data.
expectedCurrentState, expectedCurrentTaskId, expectedCurrentTaskKey, expectedInstanceVersion The API validates current workflow state and task from persisted data and metadata.
clientActionId, correlationId, idempotencyKey, sourceSystem, commandType The API generates these internally.
actionReason Not part of the public workflow-only API body.
reset Console demo setup only. The public start endpoint does not reset workflow data.

10. Console Methods In Real Usage

The console command entry point is src/WorkflowEngine.Console. It is useful for database setup, verification, scheduled processors, support diagnostics, and local demos. It is not a public end-user API.

Real-use command classification

Command Usage Real environment guidance Example
init-db Applies workflow EF Core migrations and seed data. Use for local/dev setup. For production, use an approved migration deployment step. dotnet run --project src\WorkflowEngine.Console -- init-db
verify-seed Checks required metadata such as states, actions, transitions, roles, task routes, and notification routes. Run after migration/seed deployment and before API smoke testing. dotnet run --project src\WorkflowEngine.Console -- verify-seed
run-sla Scans pending tasks with SLA due dates and queues overdue notifications. Real scheduled processor. Run outside IIS through Task Scheduler or a worker process. dotnet run --project src\WorkflowEngine.Console -- run-sla
process-notification-outbox Sends pending notification outbox rows with the configured sender. Real retry/backlog processor. Schedule after run-sla and also use after SMTP outages. dotnet run --project src\WorkflowEngine.Console -- process-notification-outbox
show-context Reads the same workflow context concept that the API returns to the UI. Useful for support diagnostics. The UI should call GET /v1/WorkflowContext instead. dotnet run --project src\WorkflowEngine.Console -- show-context WF-PT-1001 --user checker1 --roles Checker --format json
show Prints workflow summary, current state, current task, and counts. Support/read-only diagnostic. dotnet run --project src\WorkflowEngine.Console -- show WF-PT-1001
show-tasks Prints workflow task rows for one workflow instance. Support/read-only diagnostic for assignment and SLA checks. dotnet run --project src\WorkflowEngine.Console -- show-tasks WF-PT-1001
show-history Prints audit/history entries for one workflow instance. Support/read-only diagnostic for who did what and when. dotnet run --project src\WorkflowEngine.Console -- show-history WF-PT-1001
show-notifications Prints notification outbox rows for one workflow instance. Support/read-only diagnostic for pending, sent, and failed email rows. dotnet run --project src\WorkflowEngine.Console -- show-notifications WF-PT-1001
start-workflow Starts a workflow from console with optional demo reset. Demo and local smoke testing. Target app should use the API or application service instead. dotnet run --project src\WorkflowEngine.Console -- start-workflow PortfolioTrade PT-1001 --user maker1 --reset
execute-json Executes a full console WorkflowActionEnvelope sample file. Demo/test only. This command can include form payload and console-only fields that the API must not accept. dotnet run --project src\WorkflowEngine.Console -- execute-json .\samples\workflow-actions\02-submit-for-checker.json
demo Runs the sample happy path and prints branch guidance. Local demonstration only. dotnet run --project src\WorkflowEngine.Console -- demo

11. Target API Integration Flow

Use this order when integrating the workflow engine into the target API. The target API owns its existing business data and authentication. Workflow owns workflow state, tasks, audit, SLA, notification outbox, and workflow context.

Resolve actor from target auth. Build user ID, display name, and role keys from the target API's trusted identity source.
Save business data in the target API. Do this before calling workflow action execution. Workflow API bodies should not contain form data.
Start or execute workflow. Use the JSON shapes in this file. Let metadata validate the actor role and transition.
Dispatch action-created notifications immediately. The reference API dispatches notification rows created by the current action using workflow instance ID plus correlation ID. If SMTP fails, the action response becomes NotificationDeliveryFailed and the pending row remains available for scheduled retry.
Return refreshed context to the UI. The UI should render state and buttons from workflowContext, not from hardcoded client guesses.
Run scheduled processors separately. Use console run-sla and process-notification-outbox outside IIS.

Integration rule

Do not turn console setup, SLA scanning, outbox processing, or demo reset behavior into public HTTP endpoints. Those are operational methods, not form-user API methods.
