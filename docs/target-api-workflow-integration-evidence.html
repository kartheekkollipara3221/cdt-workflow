1. What the target integration does

Atlas calls the workflow engine inside the API process. The shown form-save path uses .NET service calls. It does not use the standalone workflow-api HTTP contract.

The Atlas API references the engine Application, Domain, Infrastructure, and SQMS projects. Its controller receives engine interfaces. Atlas passes these interfaces to three application services: CDT, SQMS Opportunity, and SQMS Bid. E01 E02 E03 E04

The browser sends an Atlas form request. Atlas saves the business fields and selects an action. The adapter builds the engine request. The engine returns a result. Atlas copies a non-empty NewState to the business row. The browser receives an Atlas page result. E05 E07 E11 E16 E20

The engine still owns workflow transition rules in the local reference implementation. Atlas owns form fields, action selection, caller roles, recipient inputs, and the copy of workflow state on its business row. These are two separate responsibilities. E09 E13 E18 E21 E28

Evidence limit: This report proves the calls in the supplied source snapshot. It does not prove that the deployed application uses these exact files. It does not prove successful execution in production.

5. Save sequence

New record

  1. Atlas opens a business database transaction.
  2. Atlas maps the form outputs to its business entity.
  3. Atlas inserts the row and obtains its ID.
  4. The adapter calls IStartWorkflowService.Start. It sends the workflow key, business ID, actor, roles, and initial action.
  5. The adapter requests notification dispatch when the start result reports a queued notification.
  6. Atlas copies a non-empty returned state to the business row.
  7. Atlas saves the row and commits its transaction.
E11 E12 E16 E20

Existing record

  1. Atlas maps submitted values to the existing row.
  2. The adapter tests its configured action conditions against that row.
  3. The adapter builds and normalizes a WorkflowActionEnvelope.
  4. The adapter computes a request hash and calls the engine.
  5. The adapter requests notification dispatch and returns the result’s NewState.
  6. Atlas preserves the old copied state if NewState is empty. Otherwise, it writes NewState.
  7. Atlas commits its business transaction.

7. Identity, roles, and available actions

The controller requires authorization. UserInfo reads HttpContext.User.Identity.Name, looks up the directory user, and derives the LAN ID from the name. The adapter sends this LAN ID to the engine. E03 E08

The shown host configures JWT bearer authentication. UserInfo also uses Windows directory APIs. This source does not establish the full deployed authentication chain. The exact token claims, proxy behavior, and host settings remain unverified. E02 E08

CDT sends roles from the selected step configuration. Its form-loading code also checks Atlas entitlements. The shown save-to-engine path does not establish a fresh entitlement intersection for the submitted step. Confirm server-side step access before treating the configured engine role as proof of caller membership. E13 E36

SQMS execution queries Atlas entitlement tables by user LAN ID. The queries shown in both execution methods have no application filter. Bid form loading does apply an application filter. The Bid adapter can replace the role list with Seller under the CHECKSELLER rule. This makes role selection different between the form-open and save paths. E18 E19 E21

On SQMS form open, Atlas reads engine context and maps AvailableActions to buttons. This is direct use of the engine’s available-action model. CDT form routing instead uses the copied business WorkflowState and its form configuration in the shown load path. E15 E19 E36

8. Notifications and scheduled work

Atlas builds recipient inputs and template values before the engine call. CDT derives Maker and watcher data from Atlas records. SQMS Opportunity resolves seller-team and relationship-manager recipients from Atlas users. The mapper converts the target request to the input passed to the engine. E09 E12 E13 E17 E18

After Start or Execute, the adapter checks Success and Notification.Queued before it calls DispatchCreatedNotifications. It passes the workflow instance ID and correlation ID. The dispatch call occurs before the outer Atlas business transaction commits. E11 E12 E13 E14

The target dispatcher and mapper implementations are absent. The current local versions are in the standalone workflow-api project. The local mapper is internal to that project. Its dispatcher registration is in that API host. The shown target references a different application namespace and does not reference the workflow-api project. Target helper placement and registration therefore need confirmation. E01 E03 E27 E31 E32 E33

Do not infer SMTP delivery, retries, final recipient addresses, or message content from the caller alone. This review did not send email. It did not inspect production outbox rows.

The adapters contain an SLA synchronization branch. CDT also supplies a target date for configured SLA actions. These calls do not establish a background reminder schedule. No hosted worker, SLA runner call, or outbox retry runner call was found in the supplied Atlas and Service files. A separate production job can exist outside this snapshot. E13 E18 E21 E27 E30

9. Database and deployment boundary

Atlas registers CPSharepointContext with SQL Server through the DBConnection setting and TPAMAPIAccess. The local engine registration creates a separate WorkflowDbContext from ConnectionStrings:DefaultConnection. The contexts can use the same database and still have separate transactions. E02 E27 E35

The supplied settings file has ConnectionStrings keys for DBConnection, AuditDBConnection, and PBDWConnection. No DefaultConnection key was found. Values are omitted from this report. The engine receives a separately built configuration that reads appsettings.json. Confirm how the deployed engine receives its connection. Do not assume environment configuration on builder.Configuration also enters this separate configuration.

E02 E27 E35 S01

The SQL export contains dbo workflow definitions, instances, tasks, schedules, audit, and notification outbox tables. It also contains business tables. This proves that the export includes those DDL definitions. It does not prove the live schema, active definition version, seed rows, or actual connection used by either context. E26

User statement: The production workflow tables and Portfolio Trade seed were already applied with manually generated SQL scripts. Future changes will use reviewed scripts similar to sql/sqms. This review did not run init-db, migrate a database, or change seed data.

Atlas starts its own transaction. The local engine starts a transaction when its own context has none. No UseTransaction, EnlistTransaction, or TransactionScope bridge was found in the supplied Atlas and Service source. If the target follows the local engine implementation, an engine commit can survive a later Atlas rollback. Atomic commit across both contexts is not demonstrated. E11 E16 E20 E28 E29

Bid aggregate updates run after the bid transaction commits. They use another business transaction. A later failure cannot undo the already committed bid by rolling back the earlier transaction. The exact production response to such a failure was not tested. E20
