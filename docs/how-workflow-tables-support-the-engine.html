Workflow engine · Table support

How the tables work together to run a workflow

The engine reads rules from configuration tables. It records progress in runtime tables. Other tables support deadlines, messages, history, and duplicate protection.

The tables store rules and records. Engine code performs the work that connects them.

Start with two types of data

SQL Server is the database system. A table stores records with the same fields. A row is one record.

Configuration data defines what a workflow permits. The engine calls this data metadata.

Runtime data records what happens to a specific item. A workflow instance is the engine record for one item.

A definition version identifies a set of workflow rules. A task records work for a role.

A role is a named permission group. An SLA is a service-level agreement. Here, an SLA policy defines deadlines and reminder timing.

An outbox is a stored queue of complete messages. A database constraint is a rule that stored data must satisfy.

A task definition describes work

WorkflowTaskDefinition can define CheckerReviewTask. It specifies a default owner role and an SLA policy.

A task records actual work

WorkflowTask records one Checker task for one trade. It stores the status, creation time, deadline, and completion evidence.

One definition can support many instances. Each instance has one current state and at most one pending task.

A state is the current workflow stage. A pending task still needs completion.

The tables support each engine operation

The engine does not read every table for every operation. It uses the tables that support the current operation.

A transaction groups database changes. The database commits the group together or rolls it back.

A replay repeats a request with the same internal identity. Later sections explain how the engine prevents duplicate work.

An audit is a history record of a successful action.

Workflow context is a response with the current state, task, SLA status, and available actions.

A Start request can include an initial action. In that case, Start also performs the action work in its transaction.

Watch the tables support one handoff

Use the same trade from the Portfolio Trade explanation. Its instance is WF-PT-HAPPY-1001.

Checker sends the request to the Taxable desk. This action key identifies the decision: CheckerSendToTradingDesk.

1. Runtime rows tell the engine where the item is

WorkflowInstance
  WorkflowInstanceId          = WF-PT-HAPPY-1001
  WorkflowDefinitionVersionId = the internal ID for definition version 1
  CurrentStateKey             = CheckerReview
  Status                      = Active
  Version                     = 2

WorkflowTask
  WorkflowInstanceId = WF-PT-HAPPY-1001
  TaskKey            = CheckerReviewTask
  AssignedRoleKey    = Checker
  Status             = Pending

The engine uses persisted state as authority. The request supplies the action, selected desk role, target date, and notification inputs.

A notification route selects a message type, templates, and recipient rules. A template is message text with named placeholders.

A participant is a recipient that Start stores for the workflow lifetime.

2. Configuration rows tell the engine what to do

A transition is a rule for movement between states. The engine matches the current state, action key, actor role, and definition version.

WorkflowTransitionDefinition
  FromStateKey         = CheckerReview
  ActionKey            = CheckerSendToTradingDesk
  AllowedRoleKey       = Checker
  ToStateKey           = TradingDeskReview
  TaskToCloseKey       = CheckerReviewTask
  TaskToCreateKey      = TradingDeskReviewTask
  NotificationRouteKey = RouteTradingDeskAssigned
  • WorkflowStateDefinition confirms the active destination state.
  • WorkflowTaskDefinition describes the new Trading Desk task.
  • WorkflowTaskAssignmentRoleDefinition permits TradingDeskTaxable as its selected owner role.
  • SlaPolicy defines how the engine uses the target date.
  • NotificationRoute supplies the message type and templates.
  • NotificationRecipientRule selects the recipient sources for the selected desk.
  • WorkflowParticipant supplies the stored original Maker address.

3. The engine commits the runtime changes

A hash is a fingerprint of content. The engine uses a request hash to compare a replay with the original request.

Rows that change for this action
TableEngine change
WorkflowInstanceSet state to TradingDeskReview. Increase Version from 2 to 3.
WorkflowTaskComplete the Checker task. Create a pending Trading Desk task for TradingDeskTaxable.
WorkflowTaskSlaScheduleComplete the Checker schedule. Create the Trading Desk schedule from its policy and target date.

The engine rechecks current work inside the transaction. A conflicting change prevents this handoff from committing.

The engine reads configuration rows during this action. It does not change them as part of the handoff.

The next action uses the same procedure. Different transition rows supply the next state, task, and route.

The 12 configuration tables define the rules

Seed data is the sample configuration that the repository supplies. Portfolio Trade lives in seed data.

The generic engine uses these table structures for other workflows too.

Actor role and task owner have different purposes

AllowedRoleKey controls who can perform the transition. AssignedRoleKey controls the new task owner.

In the example, Checker performs the action. TradingDeskTaxable owns the new task.

WorkflowRoleDefinition does not map users to roles. The upstream application supplies trusted actor roles.

Definition versions keep lookups together

Most configuration rows carry WorkflowDefinitionVersionId. The engine uses that ID with each state, action, task, policy, or route key.

NotificationRecipientRule uses NotificationRouteId. The route supplies the definition version.

An existing instance keeps its selected definition-version ID. A newer definition version does not automatically move that instance to new rules.

A definition version is not an immutable database snapshot. Editing rows within that version can affect later reads.

The eight runtime tables record the work

A snapshot is a stored copy of values at a specific time. Tasks, schedules, and messages preserve selected values this way.

Each runtime table preserves a different fact

An API is a callable software interface. The public workflow API does not save form fields in MockSectionData.

The calling application owns its form data.

NotificationOutbox also supports messages without a workflow instance. Those messages use NotificationOccurrenceKey as their unique event identity.

WorkflowAudit records successful actions. Start stores its actor and time on the instance. Failed actions do not create failure audit rows.

SaveDraft can create an audit row without changing state. Its previous and next states are the same.

How the engine connects the rows

A key identifies a record or a named configuration item. An internal Id and a public workflow key serve different purposes.

A foreign key is a database constraint that requires a referenced row to exist. Some engine relationships use key lookups instead.

These are lookup paths. They do not all have foreign-key constraints. WorkflowDbContext defines the actual constraints.

EF Core is the .NET database library. WorkflowDbContext maps its record classes to tables in schema dbo.

A schema is a namespace for database objects. For example, the full instance table name is dbo.WorkflowInstance.

Three version fields answer three different questions

  • WorkflowDefinitionVersion.VersionNumber: Which numbered rule set applies?
  • WorkflowInstance.Version: How many state changes has this instance committed, after its initial version 1?
  • WorkflowTaskSlaSchedule.ScheduleVersion: Which deadline schedule revision belongs to this task?

The internal definition-version ID identifies a row. It is not the same value as VersionNumber.

Stored schedules and recipients preserve task behavior

Policy becomes a task schedule

SlaPolicy defines timing rules. The engine copies applicable settings into WorkflowTaskSlaSchedule and calculates actual times.

The active schedule drives reminder scans. WorkflowTask.DueAtUtc mirrors its overdue threshold for task display.

UTC means Coordinated Universal Time. Fields ending in Utc store timestamps on that time basis.

A changed application target date can supersede the active schedule. Superseded means a newer schedule replaces it.

The engine creates the next schedule version and cancels undelivered reminders for the old schedule.

Task completion marks its active schedule Completed. The task keeps its historical deadline.

Recipient rules become a message snapshot

NotificationRecipientRule chooses sources. A stored participant or current request input supplies values for dynamic sources.

The engine stores the final ordered list in WorkflowTask.NotificationRecipientsJson and NotificationOutbox.NotificationRecipientsJson.

JSON is a text format for structured data. These fields store primary recipients and copied recipients as arrays.

SLA reminders copy the task recipient list. They do not resolve a new audience from changed recipient rules.

The monitor also copies the original task message body. It adds the configured reminder prefix to the original subject.

Changing route rules does not rewrite existing task or outbox recipient snapshots.

WorkflowParticipant stores workflow-lifetime recipients. A task snapshot stores the final audience for one task. They serve different time spans.

Tables help the engine prevent conflicting work

A unique index prevents duplicate values for a specified set of columns. A filtered unique index applies that rule to selected rows.

Database rules and engine checks work together

Idempotency means that replay of the same identified request does not repeat its effects.

Optimistic concurrency means checking that a row did not change before an update. The engine combines these checks with database rules.

The public API generates a new internal request key per HTTP request. Its public body does not accept the console replay key.

Message delivery has its own lifecycle

NotificationOutbox.Status
  Pending → Processing → Sent
               │
               └─ delivery failure → Pending

  Undelivered SLA message → Cancelled
  when its schedule becomes inactive

The sender records retry count and error details on delivery failure. The workflow transition remains committed.

One outbox row represents one complete message. The engine does not track a separate retry lifecycle for each recipient.

A processing claim prevents ordinary concurrent delivery. It does not guarantee exactly-once delivery across mail-server and database failures.

Use this model when you inspect a workflow

  1. Read WorkflowInstance to find the current state and definition-version ID.
  2. Read its pending WorkflowTask to find the current work.
  3. Read matching definition rows to understand the permitted next actions.
  4. Read the active schedule to understand deadlines and reminders.
  5. Read audit rows to understand successful actions.
  6. Read outbox rows to understand message delivery.
