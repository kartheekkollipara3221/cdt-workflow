2. How I decided

I asked five questions for each finding.

QuestionHow it changes the order
What is the effect?Lost access, wrong data or a false record comes first. A rare effect with no harm comes last.
Who can get it?A hole that each new app or each new workflow can get counts more than a hole that only old data can get.
How large is the fix?Small fixes with a clear effect come first.
Does a caller see a change?A change for callers or for target files needs your approval, and it must be additive.
Is it proved?An item with the label "Inference - verify" gets a failing test first. If the test passes, I drop the item.

These rules stay the same for every item (AGENTS.MD, inventory section 1.4):

  • No state-machine library, no new package, no BPMN, no rule language.
  • Stored status texts, keys, result codes and log names do not change. A constant must have the same text as the SQL CHECK constraint.
  • Database changes only as SQL scripts. Any change to 050 or 090 is stop-and-ask.
  • The settled decisions stay settled: D08, O4, O5, O6, D01, D07.

W13 Cut-over and rollback scripts (P08) Step 2, firstMediumStop-and-ask

Today. On the change-over day, 050 gives the TTDV2 roles, revokes all TTD roles and copies the TTD data. It does not store which roles it revoked. To undo this, 090 finds the roles again with a rule: revoked by the same person, in the hour before the time of the 050 log row (090:31-39). 050 writes its log row one time only (050:207).

Three holes.

  1. R01 Known, High, tested 090 also gives back a role that an admin revoked on purpose in that hour. A removed user gets access again.
  2. R02 Known, High, tested A second cut-over after a rollback copies only the rows whose ID is not in TTDV2 (050:191, 203). TTDV2 shows old data. Then the script revokes the TTD roles again.
  3. Second run Inference - verify After a second cut-over, 090 uses the time of the first run (090:25-26). Its one-hour rule does not find the roles that the second run revoked.
WhenScriptEffect today (example times)
Day 1, 09:00050Revokes the TTD roles. The log row gets the time 09:00.
Day 1, 11:00090Gives back the roles that the same person revoked between 08:00 and 09:00. The users have TTD again.
Day 2, 09:00050, after the app is installed againRevokes the TTD roles again. The log row keeps the time of day 1.
Day 2, 10:00090Looks between 08:00 and 09:00 of day 1, and finds no role of day 2. It removes the TTDV2 roles.
ResultThe users have no TTD role and no TTDV2 role.

Change. The same as the recommended options A of Q07 and Q08 in PENDING_DECISIONS.html:

  • 050 writes the exact IDs of the user entitlements that it revokes to a new log table. This is a new SQL script: additive, idempotent, with a CP_Atlas_ScriptLog row.
  • 090 gives back only those IDs. The one-hour rule goes away. This closes R01 and the second-run hole.
  • 050 stops, with no change and no revoke, when TTDV2 already has copied rows. This closes R02 for now. A second cut-over then needs a reconciliation procedure first.

Users see. A rollback gives back exactly the roles that the cut-over removed. A second cut-over cannot run by mistake.

Proof. The review of 2026-11-01 has tests that show R01 and R02. The platform SQL tests make and drop their own databases. I never run 050 or 090 in the shared development database.

Your decision. Q07, Q08 and Q21.

The inventory and the hand-off write "Q07 to Q10". Only Q07 and Q08 are about 050 and 090. Q09 (R04, the All Report total) and Q10 (R03, the multiple-select delimiter) are other review findings. This plan does not need them.

W4 SaveDraft race (E01) Step 3SmallKnown, High

Today. Each action updates the instance with a version check. If another request moved the instance first, no row changes, the transaction rolls back, and the result is ConcurrencyConflict. SaveDraft skips this update:

// WorkflowExecutionService.cs:675-699 (shortened)
var isSaveDraft = string.Equals(workflow.ActionKey, "SaveDraft", StringComparison.Ordinal);
if (!isSaveDraft)
{
    var updatedRows = dbContext.WorkflowInstances
        .Where(row => row.Id == instance.Id && row.Version == instance.Version)
        .ExecuteUpdate(...);
    if (updatedRows == 0)
    {
        // roll back, return ConcurrencyConflict
    }
}
// A SaveDraft commits with no version check.

Example. Request A (SaveDraft) reads the instance in Draft and passes its last check. Then request B (Submit) moves the instance and commits. Then A commits its audit and its idempotency record, with no final version check, as if the record were still a draft.

Two limits (the independent assessment, section 4.1): a transition that commits before the last check of A is found, so the gap is only after that check. Section data is in the gap only when the caller asks the engine to store it; the workflow API sets PersistSectionData = false (WorkflowActionService.cs:127).

Change. A SaveDraft also checks the version at its write, in its transaction. It keeps the approved rule that a SaveDraft does not change the version. If the instance moved, the result is ConcurrencyConflict and nothing is saved.

Callers see. A SaveDraft that loses the race gets ConcurrencyConflict, the same as other actions. This is rare. Q41 already recommends this item as the first engine fix (CODEX_HANDOFF.md, section B).

Your decision. Q41 and SM2.

W7 Metadata checks for all workflows, and the SQMS version (E01, E02, E04, E08) Step 3Medium

Today. The engine is generic, so the metadata decides the behaviour. Some metadata errors give bad states, and nothing reports them before they occur:

  • A terminal move that does not close the open task. The instance is Completed, but a task stays Pending and its SLA schedule stays Active (E01).
  • A task with an SLA policy whose creating transition has no e-mail route. Each SLA scan finds the reminder Blocked and writes only a warning (E04).
  • Two active versions of one workflow. Start fails (E08).
  • A version with no Draft state. A new instance has no move (E01).
  • A reference to a metadata row that is not active. Example: a new task reads its task definition with no IsActive filter, but the SLA code needs an active task definition (E08).

Only PortfolioTrade has some of these checks today (SeedVerificationService.cs:47).

SQMS version. SqmsScheduledService.cs:246 sends the version number 1 as a literal. If SQMS gets an active version 2, the open and reminder e-mails get NotFound.

Change. A check command for all workflows that lists errors and warnings. You run it before each activation. Nothing changes at run time. The SQMS scheduler uses the active version in place of the literal 1.

Users see. Nothing today, because SQMS has only version 1.

W5 Cancel during send (E05) Step 3SmallInference - verify

Today. Two orders of events give a false record.

Order 1 (the inventory).

  1. The worker claims reminder row 41: Processing, with its token.
  2. The worker checks the SLA schedule (Active) and starts the send.
  3. At the same time, a transition closes the task. The SLA code sets row 41 to Cancelled and clears the token (WorkflowSlaSynchronizationService.cs:219-231).
  4. The send succeeds. "Mark Sent" looks for Processing and the token (ProcessNotificationOutboxService.cs:141-155). It finds no row.
  5. Result: the e-mail went out, but row 41 says Cancelled. The run shows only a warning.

Order 2 (the independent assessment, section 4.3).

  1. The SLA code reads row 41 into EF Core tracking and sets it to Cancelled in memory.
  2. Before the SLA code saves, the worker sends the e-mail and sets row 41 to Sent in the database.
  3. The SLA code saves. The outbox has no concurrency token, so the save writes Cancelled over Sent.

Change (option A). The SLA code cancels with one conditional database update: only rows that are still Pending when the update runs. This closes both orders. A row that a sender claimed is not changed: it says Sent when the send succeeds. When the send fails, the row goes back to Pending. Then the worker cancels it at its next claim, because the worker checks the schedule after each claim (ProcessNotificationOutboxService.cs:104-136).

The rule behind option A. A database update cannot call back an e-mail that the sender already accepted. So when a send has started, the send wins, and the record shows what occurred.

Users see. The same e-mails as today. Only the record changes: it becomes true.

Your decision. SM3.

W6 SLA-only request when no task is open (E03, E09) Step 3SmallInference - verify

Today. A request with an SLA date and no action key changes the SLA of the open task. If the instance has no open task (for example in state Draft, or when it is completed), ResolvePendingTask uses .Single() and throws InvalidOperationException (WorkflowSlaSynchronizationService.cs:171-178). The API catches only WorkflowSlaValidationException (WorkflowActionService.cs:92-98). So the caller gets HTTP 500 "An unexpected error occurred.", and the log records a server error for a mistake of the caller.

Change (option A). When no task is open, the engine throws WorkflowSlaValidationException with a message that names the case: the instance does not exist, or it has no open task. The API already turns this exception into HTTP 400 "Invalid workflow SLA input." with the message.

Callers see. HTTP 400 with a clear message, in place of HTTP 500. Only one engine file changes. At the target, the same exception type is already caught, but the catch is empty (section 6).

Why option A. It uses an answer that the same request already gives for other SLA errors, and an exception type that the target already catches. Option B needs a new result code. Option C hides a mistake of the caller.

Your decision. SM4.

W8 SLA change and task completion at the same time (F09, E03) Step 3MediumKnown, F09

Today. The sequence:

  1. An SLA change reads the open task (WorkflowSlaSynchronizationService.cs:29).
  2. Another request completes that task and its schedule, and commits.
  3. The SLA change finds no active schedule. It adds a new Active schedule for the task that it read before.

Result: a completed task with an Active schedule. The SLA scan selects only schedules of Pending tasks (RunSlaService.cs:49-78), so no scan reads this schedule, and no e-mail goes out. The task row has no row version, and the unique index permits the new schedule, because the old schedule is completed.

Change. The SLA change checks the task again at its write, in its transaction. Example: a conditional update of the task row, "only if it is still Pending". If the task is closed, the SLA change stops with the same "no open task" answer as W6.

Why in step 3. In the chat I put it "later", because no wrong e-mail goes out. I moved it: the fix is in the same file as W5 and W6, so the target merges that file one time. The independent assessment rates it High, because the schedule data must stay correct.

Callers see. In this rare race, the SLA change gets the "no open task" answer of SM4 in place of a success.

Your decision. SM1 (scope) and SM4 (the answer).

What changes

  • Most items are small. Today, open decisions and approvals stop them, not the size of the work: Q40 and Q41 for the engine, Q07 and Q08 for W13, a contract approval for W6.
  • An owner makes these decisions. Then the small fixes cost little.

What stays the same

  • Backward compatibility: current callers, stored values and keys stay valid.
  • The quality gates: PROJECT.md section 21 for the engine and the five platform gates in AGENTS.MD, with the regression tests.
  • Only additive contract changes. Database changes only as SQL scripts.
  • No state-machine library and no new package.
  • The settled decisions: D08 (Draft and SaveDraft), O4 (no parallel approvals), O5 (timers never move state), O6 (no condition expressions), D01 (authentication), D07 (unique business object IDs).
Why now. Nothing is live. The pilot runs in the dev region at the target. A fix to a life cycle costs least before there is production data to migrate.

8. Words used on this page

Additive change
A change that adds and removes nothing. Old callers continue to work.
Cut-over, rollback
The change from TTD to TTDV2 on the change-over day (script 050), and the way back (script 090).
Gate
A check that must pass before a step is done: build, tests, --atlas-check.
Inference - verify
A conclusion from reading the code. A test must prove it before a fix.
Literal
A fixed text in the code, for example "Pending".
Merge at the target
The changed file goes into the target code again.
Package
The set of platform files that you copy to the target.
Row version
A value that SQL Server changes at each write of a row. A save compares it to find a conflict.
Runtime file
An engine file that the target has a copy of. There are 13.
SLA-only request
A request with an SLA date and no action key.
Stop-and-ask
A change that needs your approval before code.
Trigger
The event that makes a later item necessary.
