Identity for the standalone API

Send Content-Type: application/json. The trusted upstream server supplies X-Workflow-UserId and X-Workflow-Roles. X-Workflow-DisplayName is optional. Roles can be comma-separated. Do not let browser-supplied identity become trusted without target authentication. The in-process adapter obtains the actor from its authenticated context.

Use Maker, Checker, TradingDesk, or BDRMClientService for the action shown below. Desk assignment keys are separate from actor roles.

2. Required caller changes for v2

  1. Omit notification.recipientInputs.selectedCcUsers on CheckerReturnToMaker, TradingReturnToMaker, and BdrmTradeFulfilled. Do not send an empty array or null under that key. The v2 route does not declare the key.
  2. Keep selectedCcUsers on submit, resubmit, Checker approval and Trading approval when Cc recipients are needed. Put the RM in that list.
  3. Capture originalMaker once when the workflow starts. Do not send it again on later actions.
  4. Save the Maker's revised desk and target date in the target application. Pass their current values when Checker approves and creates the new desk task.
  5. Do not send ICG RA, Risk Team or desk membership as request recipients. Those To recipients come from versioned metadata.

Omitting the three removed Cc inputs is also accepted by v1 because its rules are optional. However, the omitted users will no longer receive Cc on those actions. This is a recipient-behavior change for those requests, even though the request remains valid.

If the target maps a UI choice to BdrmTradeFulfilled, apply the final-approval rules to that effective action. Do not infer the engine action from the UI label. BdrmTradeNotExecutedProperly remains a separate engine rework action.

6. SLA and reminder contract

TaskTiming in America/New_YorkReminder recipients
CheckerReviewTaskFirst Overdue 60 minutes after creation; repeat every 60 minutes.Saved Checker task To/Cc: ICG RAs, Risk Team, selected Cc.
TradingDeskReviewTaskDue Today at 14:00 on target date. If calculated after 14:00, omit Due Today. Overdue from next date at 08:00, then daily, including weekends.Selected desk only. No Cc. Saved separately when the task schedule starts.
BdrmClientServiceReviewTaskFirst Overdue next local date at 09:00; then daily at 09:00.originalMaker only. No Cc.
Maker reworkNo SLA policy.No SLA reminder.

A scan on a later date follows overdue catch-up. It does not backfill all missed dates or send Overdue before its local time. A late scan on the target date can send Due Today only if the schedule contains that reminder.

The engine snapshots reminder recipients at task creation. Membership changes affect new tasks. Changing a target date supersedes the schedule and keeps its saved reminder audience. Closing a task completes its schedule and cancels undelivered reminder rows. A message already accepted by SMTP cannot be recalled.

The target must run both the SLA scanner and outbox processor. A browser request does not replace those jobs. No caller JSON sets reminder recipients, recurrence, timezone, due time, or overdue time. The new six database columns are internal persistence fields.

7. Responses, failures and retries

Standalone Start and Action responses use the same wrapper. The following is a partial illustration, not a complete response fixture. Additional result and context fields are present. Do not send this object as a request.

{
  "result": {
    "actionResult": {
      "success": true,
      "resultCode": "Success",
      "workflowInstanceId": "WF-CDT-1050",
      "actionKey": "CheckerSendToTradingDesk",
      "oldState": "CheckerReview",
      "newState": "TradingDeskReview"
    },
    "workflowContext": {
      "workflow": {
        "workflowInstanceId": "WF-CDT-1050"
      }
    }
  }
}

Read result.actionResult.success, resultCode, message and diagnostics.validationErrors. Use result.workflowContext to refresh the UI. It contains current workflow/task/SLA state and available actions. GET WorkflowContext returns result.workflowContext without an action result. Treat newly added response fields as additive.

Standalone HTTP resultMeaningCaller action
200The returned action result reports success. Start can also report AlreadyExists.Use the returned instance ID and state. Do not assume AlreadyExists means a fresh instance.
400Malformed/unknown JSON fields, required input errors, or mapped SLA-only validation errors.Correct the input.
401 / 403Missing trusted actor / missing actor roles.Correct authenticated identity propagation.
500 with action resultCurrent controllers return 500 when actionResult.success is false, including engine business failures.Inspect resultCode and diagnostics. Do not assume every 500 is transient.
NotificationDeliveryFailedState can already be committed when synchronous email delivery fails.Read current context before recovery. Avoid blindly repeating the action.
404 on context lookupThe workflow instance does not exist.Check the stored identifier.

The public Action DTO has no caller-supplied idempotency key. Its service generates a new key per call. A repeated HTTP request is not guaranteed to replay the first result. Preserve the target adapter's supported idempotency and transaction strategy; do not add an unsupported JSON field.

An in-process call returns WorkflowActionResultEnvelope, whose top-level properties are Result and WorkflowContext. The target owns its outer HTTP wrapper and status mapping. Do not assume the standalone wrapper is the target form-save wrapper.

9. Release and target acceptance

  1. Deploy the caller omission of selectedCcUsers for the three v2 routes.
  2. Apply the approved six-column schema upgrade and deploy the v2-capable engine to all hosts.
  3. Create v2 inactive. Install approved group addresses. Use target change control for membership and route changes.
  4. Run verification, then activate v2 for new workflows. Never run init-db against the target database.
  5. Keep v2-capable software while v2 instances remain. Reactivating v1 changes new starts only.
  6. Run the complete return-and-resubmit sequence using the target adapter. Verify both the response and persisted state at each step.
  7. Confirm desk-only reminders after the new desk/date selection, one reminder per SLA-enabled task, and no new reminders after completion.

Local evidence: the real in-process engine completed 10 actions, six SLA tasks, and 17 SMTP messages: nine action emails plus eight reminders. Ordered To/Cc and subjects matched the captured messages. The injected test clock advanced through January 2030. This was not a target HTTP or UI acceptance run.

Two reviewed edge cases are owner-accepted under target change controls: temporarily disabling/reactivating an explicit reminder route, and removing all members of a required group. This handoff preserves those decisions; it does not claim those cases were fixed.
