Core workflow engine · Finding H01 · 18 October 2026

Failed emails can block later emails

High — under the conditions below

The email processor can select the same failed messages on every run. These messages can fill the batch. Later messages then get no send attempt.

Evidence status: The source code shows this path. A test model reproduced the selection problem. The audit did not reproduce it through SQL Server or confirm an incident in production.

2. How the failure occurs

Use this example. The batch size is 100. The outbox contains 100 older messages that always fail. One healthy message is newer.

  1. The processor finds the messages that are eligible now.
  2. It puts the oldest messages first. It selects only the first 100.
  3. Each selected message fails. The processor returns that message to Pending.
  4. The creation time of each failed message stays the same. Thus, these messages stay before message 101.
  5. The next poll starts when all 100 failed messages are eligible again.
  6. The processor selects the same 100 messages. Message 101 receives no attempt.
Select the oldest 100 → all fail → wait → select the same 100

This sequence can continue indefinitely while the conditions stay the same.

Conditions required

  • The host has enabled a finite batch size.
  • Enough older messages fail repeatedly to fill the batch.
  • Those messages are eligible at each poll.
  • The healthy message depends on this processor. Another sender does not send it.

A zero retry delay permits immediate selection again. A positive delay also permits this problem if each poll occurs after that delay.

The default setting has no batch limit. This specific problem requires a batch limit.

3. Why the retry delay does not always help

The recommended settings permit 100 messages per batch. The first retry delay is 60 seconds. The maximum delay is 60 minutes.

Time in the exampleWhat happens
09:00The processor selects the 100 older messages. They fail. Each receives a retry time.
By approximately 10:00All 100 messages are eligible again. Their delay cannot exceed 60 minutes.
10:01The next poll starts. The processor selects the same 100 older messages.
Later polls, 61 minutes apartThe sequence repeats. Message 101 still receives no attempt.

This example assumes that the failed attempts finish quickly. The exact condition is that all failed messages are eligible before the next selection.

A poll before the retry times can select the healthy message. The existing fairness test checks that case. It does not check repeated polls after the retry times.

4. Why the finding is High

One failed batch can prevent email delivery for many unrelated workflows. It can block task-assignment messages and SLA reminders that depend on this processor.

The workflow action can still succeed. The database can contain the correct state, task, and audit record. However, the user may not receive the email that tells them to act.

For example, a Checker task can exist while its assignment message stays in the outbox. The Checker does not receive that message.

This explains the High rating. The effect can extend beyond the messages with errors. The audit did not establish a Critical defect or prove that this condition exists in production.

Not tested: SQL selection, database claims, simultaneous workers, actual SMTP delivery, or the production polling interval. The results above prove the model behavior. They do not prove a production incident.

The previous fix lets processing continue after a message fails. That fix still applies to the selected batch. This finding concerns messages that never enter the batch.

6. What must change

The selection rule must give later messages an opportunity for an attempt, even when older messages continue to fail.

One possible design reserves some batch positions for messages with no previous attempt. Other positions permit retries. Another design rotates messages according to their last attempt.

These are design options. No option has been approved or implemented. The final rule must allow both new messages and retries to make progress.

Possible actionLimit
Increase the batch size.A larger group of failed messages can fill the larger batch.
Enable a retry delay.The problem remains if every poll occurs after the delay.
Poll more often.This can help during a positive retry delay. It does not solve the zero-delay case.
Always select new messages first.A continuous supply of new messages can prevent retries. Both groups need access to batch positions.

Test required before a correction is accepted

  1. Use an isolated SQL test database and the actual outbox processor.
  2. Create enough older failed messages to fill one batch. Add one later healthy message.
  3. Use a test sender. Make only the older messages fail.
  4. Run repeated polls with no retry delay.
  5. Repeat with the recommended delay. Move the test clock past all retry times before each poll.
  6. Check that the healthy message gets an attempt within an agreed maximum number of runs.
  7. Check that retries also continue. Confirm that message ownership and recipient data remain correct.

The correction must preserve public contracts and existing messages. A new deletion, archive, or dead-letter policy is outside this finding.
