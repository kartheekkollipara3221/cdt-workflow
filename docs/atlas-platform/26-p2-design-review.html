Module 26: review of the ClientInflows (P2) design

Status: 2026-11-20. Review of 25-client-inflows-p2-design.md, draft 2. No code, no SQL and no design text is changed by this review. The user decides which findings change the design.

1. Method

The review compares each statement of the design with:

  • the platform code of today (atlas-platform/src/, atlas-platform/WebUi/);
  • the workflow engine code (src/), read only;
  • the target copy of 2026-11-18 (Program_cs.txt, CPAtlasController_cs.txt, the interceptors, the settings key names; no key value or password was read out);
  • the earlier specs: module 1 (5.3, 5.9 to 5.13), module 8, module 9, module 10;
  • the requirements D1 to D34.

Paths: Service/ = atlas-platform/src/BBH.CP.Atlas.Service/, Data/ = atlas-platform/src/BBH.CP.Atlas.Data/, App/ = atlas-platform/src/BBH.CP.Atlas.App/, WebUi/ = atlas-platform/WebUi/src/app/platform/.

2. Result

The design is sound in its structure: the split into generic parts is correct, the engine does not need a change, and the save order follows module 10. But the design has 3 defects that make the app wrong or open as written, and 9 points that are not complete. All have a small correction. None needs an engine change or a new package.

3. High

DR-01 The account fields and RMCC change again at the second submit

  • Design: 5.2 (SetFromOption), 7.3, 10.6 ("E3 uses the RelationshipManager and RMCC of the first submit").
  • Code: the server runs the effects of each control at each save, with the stored value when the client sends none (Service/Application/ConfigSectionService.cs, ReadAndFilter and MapRecord; Service/Platform/Sections/AtlasServerEffects.cs, Values). The client also runs the effects when the form is built (WebUi/form/atlas-form.component.ts).
  • Effect: at the second submit, the server reads the AIN row again and writes AccountName, StarNumber, RelationshipManager, Custodian and RMCC again. If the RM changed in AIN after the first submit, E3 goes to the new RM, and History shows a change to part 1. This breaks answer Q8 and D16. Also, when a user opens the record, the read-only fields show the AIN values of today, not the saved values.
  • Correction: one generic rule, the same on the server and the client: an effect sets values (Set, Clear, SetFromOption) only when its source control is enabled for the user and the state. A source that a rule disables or hides sets nothing; the saved values stay.
  • TTDV2: no change for a user who can edit (the account control is enabled). A read-only user then sees the saved values. The TTDV2 tests must prove it.

DR-02 A save with no button name goes past the workflow

  • Design: 6.4 ("With no Button, the save is a plain save, as today").
  • Code: the save checks only the Create or Edit permission and the fields (ConfigSectionService.SavePage, LoadStored). It has no button check.
  • Effect: a Write user, or a client defect, can send a save with no Button. For a new record, this makes a record with no engine instance, no state and no email. In state Submitted, it writes part 2 ("Funds have been received", the files) with no second submit and no E3.
  • Correction: a generic rule. A save with no Button is the action of the Save button. If the form has no button with Action.Type = Save, the server refuses the save (NotAllowed). ClientInflows has no Save button, so each save must name SubmitPart1 or SubmitPart2. TTDV2 has a Save button, so it does not change.

4. Medium

DR-04 A Read user has no "Edit" item in the row menu (D24)

  • Code: with no Menus in the dashboard JSON, the menu shows "Edit" only for a user with the Edit permission (Service/Platform/Dashboard/AtlasDashboardService.cs, Menus).
  • Effect: a Read user can open a record only with the link on the ID. D24 wants the "Edit" item for all users.
  • Correction: JSON only. Each tab gets Menus with a rule: Edit and History for @Read, Delete for Write.

DR-05 The file download with a plain link can give 401 at the target

  • Design: 8.2 and 8.3 ("download URL", "download links").
  • Target: the API uses JWT bearer authentication (Program_cs.txt). The client adds the credentials in HTTP interceptors (winauthinterceptor.ts, apiinterceptor.ts). The API has a different address than the client (HostedURL, HostedClientURL). A browser link does not go through the interceptors.
  • Correction: the client gets the file with HttpClient as a blob, through the same interceptors as each other call, and then gives the blob to the browser. The load response needs only the file ID. Check at the target how the CDT download works today.

DR-06 The platform cannot read varbinary

  • Code: Data/Platform/AtlasSqlTypes.cs has no varbinary. The start-up already reads the columns of AttachmentTable into the table registry (App/Platform/AtlasPlatformStartup.cs).
  • Effect: the design does not say how the attachment service reads and writes FileContent.
  • Correction: add varbinary to the type map (generic). The list query of the attachments must not select FileContent; only the download reads it. If not, each form load reads all files of the record (up to 10 MB each).

DR-07 The account control and its columns are not consistent

  • Design 5.2: the control Account fills AccountNumber with SetFromOption. But AccountNumber has no control, and the Data list of the provider (7) does not have it.
  • Correction: the ngselect control writes the column AccountNumber (name AccountNumber, value = the account number). SetFromOption fills the 4 shown fields and RMCC. The column CFP.Inflow.Account is not used. This is an integration note for the target team.

DR-08 Some values are not in History, and Set cannot write a column with no control

  • Design 6.4: Action.Set sets CashSubmittedDate. This column has no control.
  • Code: the audit lists only the fields of the form (ConfigSectionService.Changes).
  • Effect: Set needs the same rule as 7.3 (a control or a column of the table). Status, CashSubmittedDate and RMCC do not show in History. A user who reads History does not see when the record became "Funds Received".
  • Correction: Set accepts a control name or a column name. The audit entry of a save with a workflow step gets one line for the status ("Status: Submitted to Funds Received"). Decide if the two other columns must show.

DR-09 The dashboard does not format the Amount (D23)

  • Gap report A10 says the column type currency exists. Code: the type only aligns the cell to the right (WebUi/dashboard/atlas-dashboard-columns.ts). CPTabColumn.Format is not read.
  • Effect: the Amount shows as a raw number with 4 decimals, not as USD.
  • Correction: a generic formatter for currency columns (2 decimals, thousands separator, $). Small client code. Check at the target that the Excel export gives the formatted or the numeric value, as the users want.

DR-10 An empty template value stops the engine action with a technical message

  • Engine: a template token with an empty value is a validation error; the action fails (src/WorkflowEngine.Application/Notifications/NotificationTemplateRenderer.cs).
  • Effect: AccountName comes from AIN and can be empty text. The user then gets "Template token 'accountName' requires ...".
  • Correction: before the first write, the adapter checks that each TemplateData value is not empty. An empty value is a page error that names the field.

DR-11 The CKEditor risk is tested too late

  • Design 13: the editor is build step 5. Not proved yet: @ckeditor/ckeditor5-angular with Angular 21; ng build with 0 warnings (bundle size limits); the editor style sheet with no change to angular.json (a target file that is not in the approved list).
  • Correction: a short test before step 1 (with step 0): add the two packages to the stand-in, show one editor, run ng build and ng test. If it fails, stop and ask (the earlier fallback was Jodit).

DR-12 The state check on load does not correct two failure cases

  • Design 10.3: "the state check on the next load corrects the record".
  • Case 1, first submit: the engine commits, then the Atlas commit fails. The record does not exist. The engine keeps an instance with no record, and E1 goes out later from the outbox with a link that opens nothing.
  • Case 2, second submit: the same failure. The check on load sets the record to "Funds Received", but the part 2 values and files are not saved. The record is then closed for good with an empty part 2, and E3 is sent.
  • The two cases need a lost database connection at the exact moment of the commit. They are rare.
  • Correction: text only. Add the two cases to "Accepted limits" (10.8) with the action for support: the error log Atlas.WorkflowStepFailed gives the instance ID; the target team corrects the data by script.
