Module 25: ClientInflows (P2) implementation design

Status: Draft 1, 2026-11-20. Design only. No code and no SQL script exists yet. The user must approve this design before the build starts (section 14).

1. Purpose

ClientInflows (app code CFPINFLOW) is release P2: the second platform app, and the first one with attachments, rich text and a workflow. This document tells how to build it. Most of the work is generic platform code that the next apps use again. The app itself is JSON and SQL.

Inputs:

  • Requirements: ONBOARDING_ANSWERS.md, decisions D1 to D34.
  • Gaps and answers: GAP_REPORT.md, items A1 to A17, B1 to B12, C1 to C8, answers Q1 to Q9.
  • Module designs: 08-attachments.md (section 10), 10-engine-adapter.md, 07-registry.md (section 5), 12-ttd-pilot-build.md (the model).

Rules that stay in force:

  • No CFPINFLOW, CFP, AIN or Inflow name in C# or TypeScript. Tests and JSON can have them.
  • The workflow engine code (src/) does not change (Q1, Q2).
  • TTDV2 and the current target apps do not change. Each new JSON key and each new request field is optional.
  • Database changes are SQL scripts only: additive, idempotent, with a CP_Atlas_ScriptLog row.
  • The time comes from TimeProvider. No DateTime.UtcNow.

6. Form behaviour (generic)

6.1 State in the rules (B4)

  • ConfigSectionService.RuleContext reads the value of the Workflow.StateField column of the record and gives it to the rule engine as the state list. Today the list is always empty.
  • A new record has the state Workflow.InitialState (Draft).
  • The state comes from the database row on load and on save. A state value from the client is never read.
  • A form with no Workflow binding has an empty state list, as today. TTDV2 does not change.

6.2 Validation and state

The field validator and the allow list use the effective form of the user and the state. A hidden or disabled field is not validated and its value is not accepted. Thus the part 2 fields cannot stop the first submit, and the part 1 fields cannot change at the second submit. Build step 3 has tests for the two cases.

6.3 MustBeTrue (B5)

New optional validator key. The value must be true. It runs on the server (AtlasFieldValidator) and on the client (atlas-validators.ts), with the shared cases file. Message: "Select <label> before you submit."

6.4 Button Execute and Action.Set (B6, B7)

  • New optional request field Button (the button name) on v1/ManagePage. With no Button, the save is a plain save, as today.
  • The server finds the button in the form JSON. It checks Permissions.Execute[<button>] and the button rules (roles and state) for the user. A refusal is HTTP 403 with the page error contract.
  • Action.Set gives field values for this save: field name to token. Tokens: {User.LanID} and {Now} (UTC, from TimeProvider), with the token code of AtlasDefaultTokens. A field in Set is server-set: a client value for it is not accepted.
  • The client sends the button name, never an engine action key. The binding selects the engine actions (10.2).
  • The client disables the buttons while a save runs.

7. Table option provider: the account lookup (B3)

A generic provider with the name Table, in Service/Platform/Options/. It reads the options from a table that the form JSON names.

"OptionsSource": {
  "Provider": "Table",
  "Parameters": {
    "Table": "AIN.AccountInventory",
    "Value": "AccountNumber",
    "Label": "{AccountNumber} - {AccountName}",
    "Data": "AccountName,StarAccountNumber,RelationshipManager,Custodian,RMCC",
    "OrderBy": "AccountNumber",
    "UserNameColumns": "RelationshipManager,RMCC"
  }
}

7.1 Rules

  • The table must be in LookupTables of the manifest. The platform reads its column metadata at start-up, with the same reader as the app tables. A lookup table is read-only: the platform never writes to it.
  • The start-up check refuses a table, a column or a label token that is not in the metadata. The names go into the SQL text only after this check, in brackets. All values are parameters.
  • If the table has an IsDeleted column, the provider reads only the rows that are not deleted (D29).
  • The response has only the Value, the label and the Data columns. No other column leaves the server.
  • The provider sends all rows with the form load, as the TTDV2 account list does today. The option list of a table is cached for a short time (60 seconds) in memory, so many form loads do not read the table each time.
  • KeepSavedValue: true on the control keeps a saved account in the list after the AIN row is deleted.

7.2 Use in other apps

Another app uses the same provider with its own Data columns. It adds AIN.AccountInventory to its LookupTables. No code is necessary.

7.3 Data-only effect target

SetFromOption can name a field that has a column and no control (here RMCC). The server effect sets the column from the option data. The client does not show it and does not send it. The start-up check accepts a target that is a control or a column of the app table, and refuses other names.

8.2 Server

  • IAtlasAttachmentService in Service/Platform/Attachments/: list, add, remove, open.
  • SavePage(input, files) reads the files. A file is accepted only when its control is a filepicker that is visible and enabled in the effective form (the same check as the allow list).
  • Limits: 10 MB for each file, 25 MB for the new files of one save, the default type list, the file signature check (module 8, 4.3). The file name is Path.GetFileName, 255 characters at most.
  • New optional request field RemovedAttachmentIds. The server removes (soft delete) only the IDs that belong to this record and to an enabled filepicker.
  • Required on a filepicker: after the save, the control has one file at least (files that stay + new files).
  • All of this is in the transaction of the record. Each added and each removed file gets one audit entry.
  • Load: the files of the record, grouped by control name. For each file: ID, name, size, created by, created date and the download URL.
  • New controller App/Platform/AtlasAttachmentController.cs: GET v1/Attachment/{appCode}/{id}. It checks View on the parent record, then streams the decompressed file with Content-Disposition: attachment and X-Content-Type-Options: nosniff. An unknown ID, a deleted file or a deleted record gives 404.

8.3 Client

  • New renderer filepicker in form/renderers/, registered in atlas-renderer-registry.ts. It uses the target file control of @pbdev/pbdev-core if the stand-in has it; the look follows the CDT step page.
  • The form sends the files as form parts <ControlName>#$#<FileName>, the format that the target uses today.
  • Remove: the question dialog, then the file shows as "removed when you save".
  • The client checks the size limits before it sends. The server checks again.
  • A disabled filepicker shows the list with download links only.

9. Rich text (B2, B9)

9.1 Client

  • New renderer richtext. It loads CKEditor 5 with a dynamic import(), so the editor code is only loaded for a form that has a richtext control.
  • Packages: ckeditor5 and @ckeditor/ckeditor5-angular, the latest versions at build time that support Angular 21, with fixed version numbers. licenseKey: 'GPL'.
  • Plugins: paragraph, headings, bold, italic, underline, strikethrough, lists, link, table, block quote, undo, paste from Office. No picture plugin and no upload adapter (D12, D31). A pasted picture is dropped.
  • A disabled control shows the editor in read-only mode with no toolbar.

9.2 Server

  • On save, each richtext value goes through HtmlSanitizer before validation and before the write. The check is by control type, so each app gets it.
  • Allowed tags: p, br, strong, b, em, i, u, s, h2, h3, h4, ul, ol, li, blockquote, a, figure, table, thead, tbody, tr, th, td. Allowed attributes: href on a; colspan and rowspan on cells; class on figure. Allowed link schemes: http, https, mailto. No style, no img, no event attributes.
  • The list is one constant in the platform. It is not in the app JSON, so an app cannot make it weaker.
  • A value that is empty after the clean-up is saved as NULL.
  • Largest size: 200,000 characters after the clean-up; more gives a field error.
  • The audit entry holds the old and the new value as plain text (tags removed, entities decoded). The History window shows plain text.
  • The dashboard shows a richtext column as plain text, with the same converter. (P2 has no such column.)
  • Rich text is not in the emails of P2.

10. Engine adapter (C1 to C8)

The design is module 10. This section gives the parts for a section form and the answers Q2, Q3 and Q8.

10.1 Parts

  • IAtlasWorkflowAdapter in Service/Platform/Workflow/: Start, Execute, ReadContext, DispatchNotifications. SLA synchronization and the history read are not in P2 (D20, D27).
  • The adapter uses the engine services from dependency injection, as the target services do (IStartWorkflowService, IWorkflowExecutionService, the dispatcher, the context reader, the registered normalizer and hasher).
  • BBH.CP.Atlas.Service.csproj gets a reference to the engine application project. The target Service project has this reference already. An app with no Workflow binding makes no engine call.

  • Steps: button name to a list of engine steps. The first step can change the state. Each later step must keep it.

  • The start-up check refuses: a Steps key that is not a button; a recipient key with no definition; a field name that is not a column; a Map value that is not an option of the field; a list key with no address in the settings.

10.3 Save order

For a save with a Button that has steps:

  1. Validate (rules, access, fields, files). No write.
  2. Begin the transaction. Write the record, the audit entries and the attachments. SaveChanges, no commit.
  3. Run the first step in the engine (Start with the initial action, or Execute).
  4. Engine Success is false: roll back. Return the engine code and message as a page error. Nothing changed.
  5. Engine Success is true: write WorkflowState (the engine state key) and Status (the label of StatusLabels). Commit.
  6. After the commit, run each later step in order. Then dispatch the notifications of all steps.

Failures after the commit do not undo the save:

  • A later step fails (E2): the record stays saved. The adapter writes an error log with the instance ID and the action key. The response says "Saved. One notification was not sent." No automatic second try in P2.
  • A dispatch fails: warning log; the engine outbox sends the email again (module 10, 4.5).
  • The commit of step 5 fails after the engine committed: error log, and the state check on the next load corrects the record (10.4).

Double submit: new optional request field RequestId (a GUID from the client for each user action). The idempotency key of step n is RequestId + : + n. With no RequestId, the server makes a GUID.

10.4 Load

When a record with a binding loads, the adapter reads the engine context. If the engine state is not the WorkflowState of the record, the platform writes the engine state and the status label to the record, writes one audit entry (WorkflowSync) and a warning log. The engine is the source of truth for the state. A record with no engine instance (new) is not checked.

10.5 Actor roles

ActorRoles: "User": the adapter sends the names of the active roles of the user in the app, from the active roles view. The engine role Write has the same name as the app role.

10.6 Recipients

SourceMeaning
ListByField + MapThe value of the field selects list keys. Each key has one or more addresses in AppSettings:Modules:<Code>:Workflow:Lists:<Key> (separated by ;).
FromNameFieldThe field holds display names, separated by ;. Each name is found in CP_Atlas_User.

Display name rules (D33, D34), in one service IAtlasUserDirectory:

  • The compare ignores case, and spaces at the start, at the end and doubled.
  • Exactly one active user (IsDeleted is not 1) with an email: use the email.
  • No user, a user with no email, or two or more users: leave the name out. Write the warning log event Atlas.RecipientSkipped with the app, the record ID, the recipient key and the name.
  • Optional: true: the step continues with no address for this key. Optional: false: an empty result is a field error and the save stops (before the first engine call).
  • The adapter removes duplicate addresses.

The recipients are found before step 3 of 10.3, from the values of the saved record. Thus E3 uses the RelationshipManager and RMCC of the first submit (Q8).

10.7 Template data

  • Field + optional Format: the value of the record as text. Format is a .NET format text, used with the en-US culture. A date field is formatted as stored (no time zone change for a date with no time).
  • RecordLink: AppSettings:Atlas:WebBaseUrl + /form/<Code>/<ID>. The start-up check gives an error when a binding uses RecordLink and the setting is empty.
  • The adapter sends the same template data with each step.

10.8 Accepted limits

  • A deleted record in state Submitted keeps its engine instance. No email goes out (no SLA). Accepted (gap N3).
  • E1 and E2 are two engine commits. A failure between them sends E1 and not E2. Accepted with Q2.

11. --atlas-check (B8)

  • New severity Info in AtlasStartupCheck. An Info line is printed and logged. It is not counted: the summary stays 0 error(s), 0 warning(s) and the exit code does not change. Info lines are never a reason to disable an app.
  • Generic data report: for each Table provider with UserNameColumns, the check reads the not-deleted rows and lists each row where a name (split by ;) does not match exactly one active user with an email. Format: Info: AIN.AccountInventory AccountNumber 12345: RelationshipManager "John Smith": no user.
  • The report prints 200 lines at most for each table, then the count of the rest.
  • The report runs only with the --atlas-check switch, not at each start-up of the host.
