Status: Draft 3, 2026-11-20. Draft 2 was approved by the user (14.1). Draft 3 has the corrections of the design review (26-p2-design-review.md, findings DR-01 to DR-21, answers in its section 8). Section 18 lists what changed. Design only. No code and no SQL script exists yet. The build starts with step 0 of section 13 when the user says so.

1. Purpose

ClientInflows (app code CFPINFLOW) is release P2: the second platform app, and the first one with attachments, rich text and a workflow. This document tells how to build it. Most of the work is generic platform code that the next apps use again. The app itself is JSON and SQL.

Inputs:

  • Requirements: ONBOARDING_ANSWERS.md, decisions D1 to D34.
  • Gaps and answers: GAP_REPORT.md, items A1 to A17, B1 to B12, C1 to C8, answers Q1 to Q9.
  • Review: 26-p2-design-review.md, findings DR-01 to DR-21 and the answers.
  • Module designs: 08-attachments.md (section 10), 10-engine-adapter.md, 07-registry.md (section 5), 12-ttd-pilot-build.md (the model).

Rules that stay in force:

  • No CFPINFLOW, CFP, AIN or Inflow name in C# or TypeScript. Tests and JSON can have them.
  • The workflow engine code (src/) does not change (Q1, Q2).
  • The current target apps do not change. Each new JSON key and each new request field is optional. Section 16 gives the two small changes for TTDV2 users who cannot edit.
  • Database changes are SQL scripts only: additive, idempotent, with a CP_Atlas_ScriptLog row.
  • The time comes from TimeProvider. No DateTime.UtcNow.

6. Form behaviour (generic)

6.1 State in the rules (B4)

  • ConfigSectionService.RuleContext reads the value of the Workflow.StateField column of the record and gives it to the rule engine as the state list. Today the list is always empty.
  • A new record has the state Workflow.InitialState (Draft).
  • The state comes from the database row on load and on save. A state value from the client is never read.
  • A form with no Workflow binding has an empty state list, as today. TTDV2 does not change.

6.2 Validation and state

The field validator and the allow list use the effective form of the user and the state. A hidden or disabled field is not validated and its value is not accepted. Thus the part 2 fields cannot stop the first submit, and the part 1 fields cannot change at the second submit. Build step 3 has tests for the two cases.

6.3 MustBeTrue (B5)

New optional validator key. The value must be true. It runs on the server (AtlasFieldValidator) and on the client (atlas-validators.ts), with the shared cases file. Message: "Select <label> before you submit."

6.4 One submit button (B6, B7, DR-02)

The rule: a section form with a workflow has one submit button. The server selects the workflow step from the state of the record.

  • A form is a "form with steps" when its Workflow binding has Steps (10.2). Steps has one entry for each state in which a submit is possible.
  • A form with steps has exactly one button with Action.Type = Save. This is the submit button. The start-up check gives an error for no such button or for two or more.
  • Each save of a form with steps is a submit. The server reads the state of the record from the database (a new record has InitialState) and takes the entry of Steps for this state. The request has no state, no engine action key and no button name.
  • When Steps has no entry for the state, the server refuses the save (code NotAllowed). On load, the server then hides the submit button. Thus the button rules need only the roles.
  • Optional Label in a step: the text of the submit button in this state. With no Label, the button keeps its text. ClientInflows does not use it (the text is "Submit" in the two states).
  • Optional Set in a step: field values for this save, name to token. A name is a control name or a column name of the app table (DR-08); the start-up check refuses other names. Tokens: {User.LanID} and {Now} (UTC, from TimeProvider), with the token code of AtlasDefaultTokens. A field in Set is server-set: a client value for it is not accepted.
  • Access: the save needs Create (new record) or Edit (existing record), as each save today. The engine checks the role of the action again.
  • A submit needs a RequestId (10.3).
  • The client disables the buttons while a save runs.
  • A form with no Steps saves as today. TTDV2 does not change.

Not built: the request field Button and Permissions.Execute of draft 2. With one submit button they are not necessary. Permissions.Execute, the button action type Execute and CPButtonAction.Set stay reserved, as in release P1.

6.5 Effects only from a control that the user can change (DR-01)

Today the server runs the effects of each control at each save, with the stored value when the client sends none. The client runs the effects each time the form opens. For a form with two submits, this reads the lookup table again at the second submit and changes the values of part 1.

The rule, the same on the server (AtlasServerEffects) and on the client (atlas-effects.ts):

  • An effect (Set, Clear, SetFromOption) sets values only when its source control is visible and enabled for the user and the state (the effective form).
  • When the source control is disabled or hidden, the effect sets nothing. The saved values stay in the record and show on the form.

Result for ClientInflows:

  • First submit: the account control is enabled. The server reads the AIN row and saves AccountName, StarNumber, RelationshipManager, Custodian and RMCC.
  • After the first submit: the account control is read-only. AIN is not read again. A later change in AIN does not change the record, the form or the recipients of E3 (Q8, D16).

TTDV2: no change for a user who can edit, because the source control is then enabled. A user who cannot edit sees the saved values. Build step 2 runs all TTDV2 tests. If a TTDV2 effect has a source control that is disabled for a user who can save, stop and ask.

7. Table option provider: the account lookup (B3)

A generic provider with the name Table, in Service/Platform/Options/. It reads the options from a table that the form JSON names.

"OptionsSource": {
  "Provider": "Table",
  "Parameters": {
    "Table": "AIN.AccountInventory",
    "Value": "AccountNumber",
    "Label": "{AccountNumber} - {AccountName}",
    "Data": "AccountName,StarAccountNumber,RelationshipManager,Custodian,RMCC",
    "OrderBy": "AccountNumber",
    "UserNameColumns": "RelationshipManager,RMCC"
  }
}

7.1 Rules

  • The table must be in LookupTables of the manifest. The platform reads its column metadata at start-up, with the same reader as the app tables. A lookup table is read-only: the platform never writes to it.
  • The start-up check refuses a table, a column or a label token that is not in the metadata. The names go into the SQL text only after this check, in brackets. All values are parameters.
  • If the table has an IsDeleted column, the provider reads only the rows that are not deleted (D29).
  • The response has only the Value, the label and the Data columns. No other column leaves the server.
  • When the user can change the control, the provider sends all rows with the form load, as the TTDV2 account list does today. The option list of a table is cached for a short time (60 seconds) in memory, so many form loads do not read the table each time.
  • When the user cannot change the control (disabled or read-only in the effective form), the server sends only the saved option: the value and its label, with no Data (DR-18). This is a rule for each dropdown with an options source, not only for the Table provider. A Read user and each user after the first submit thus do not get the RM, the custodian and the RMCC of all accounts.
  • KeepSavedValue: true on the control keeps a saved account in the list after the AIN row is deleted.

7.2 Use in other apps

Another app uses the same provider with its own Data columns. It adds AIN.AccountInventory to its LookupTables. No code is necessary.

7.3 Data-only effect target

SetFromOption can name a field that has a column and no control (here RMCC). The server effect sets the column from the option data. The client does not show it and does not send it. The start-up check accepts a target that is a control or a column of the app table, and refuses other names. The rule of 6.5 also applies to a data-only target.

8.2 Server

  • IAtlasAttachmentService in Service/Platform/Attachments/: list, add, remove, open.
  • AtlasSqlTypes gets the type varbinary, so the platform can read and write FileContent (DR-06). This is generic.
  • SavePage(input, files) reads the files. A file is accepted only when its control is a filepicker that is visible and enabled in the effective form. A filepicker control has no Field and no column, so the check reads the state of the control itself, not the field allow list (DR-20). The start-up check does not report "no column" for a filepicker.
  • Limits: 10 MB for each file, 25 MB for the new files of one save, the default type list, the file signature check (module 8, 4.3). The file name is Path.GetFileName, 255 characters at most.
  • New optional request field RemovedAttachmentIds. The server removes (soft delete) only the IDs that belong to this record and to an enabled filepicker.
  • Required on a filepicker: after the save, the control has one file at least (files that stay + new files).
  • All of this is in the transaction of the record. Each added file gets one audit entry with the event AttachmentAdd, and each removed file one with AttachmentRemove. These are the event names of module 9 (DR-15).
  • Load: the files of the record, grouped by control name. For each file: ID, name, size, created by and created date. No download URL (DR-05). The list query does not select FileContent; only the download reads it (DR-06).
  • New controller App/Platform/AtlasAttachmentController.cs: GET v1/Attachment/{appCode}/{id}. It checks View on the parent record, then streams the decompressed file with Content-Disposition: attachment and X-Content-Type-Options: nosniff. The server sets the content type from the file extension, not from the value that the client sent with the upload (DR-17). An unknown ID, a deleted file or a deleted record gives 404.

8.3 Client

  • New renderer filepicker in form/renderers/, registered in atlas-renderer-registry.ts. It uses the target file control of @pbdev/pbdev-core; the look follows the CDT step page. The stand-in has no file picker today: build step 4 makes the stand-in file picker from the real target source (DR-20).
  • The form sends the files as form parts <ControlName>#$#<FileName>, the format that the target uses today.
  • Remove: the question dialog, then the file shows as "removed when you save".
  • The client checks the size limits before it sends. The server checks again.
  • Download (DR-05): the client gets the file with HttpClient as a blob and then gives the blob to the browser. A plain browser link is not used: the target API uses JWT bearer authentication and has a different address than the client, and only an HttpClient call goes through the target interceptors. Build step 4 checks how the CDT download works at the target and follows it.
  • A disabled filepicker shows the list with the download action only.

9. Rich text (B2, B9)

9.1 Client

  • New renderer richtext. It loads CKEditor 5 with a dynamic import(), so the editor code is only loaded for a form that has a richtext control.
  • Packages: ckeditor5 and @ckeditor/ckeditor5-angular, the latest versions at build time that support Angular 21, with fixed version numbers. licenseKey: 'GPL'.
  • Plugins: paragraph, headings, bold, italic, underline, strikethrough, lists, link, table, block quote, undo, paste from Office. No picture plugin and no upload adapter (D12, D31). A pasted picture is dropped.
  • A disabled control shows the editor in read-only mode with no toolbar.
  • The risk is tested first (DR-11): build step 0 adds the two packages to the stand-in, shows one editor, and runs ng build (0 warnings, bundle size limits) and ng test. The editor style sheet must load with no change to angular.json, because this target file is not in the approved list. If the test fails, stop and ask (the fallback is Jodit).

9.2 Server

  • On save, each richtext value goes through HtmlSanitizer before validation and before the write. The check is by control type, so each app gets it.
  • Allowed tags: p, br, strong, b, em, i, u, s, h2, h3, h4, ul, ol, li, blockquote, a, figure, table, thead, tbody, tr, th, td.
  • Allowed attributes: href on a; colspan and rowspan on cells; class only on figure and only with the value table (DR-17). No style, no img, no event attributes.
  • Allowed link schemes: http, https, mailto. The server adds rel="noopener noreferrer" to each link.
  • The list is one constant in the platform. It is not in the app JSON, so an app cannot make it weaker.
  • A value that is empty after the clean-up is saved as NULL.
  • Largest size: 200,000 characters after the clean-up; more gives a field error.
  • The audit entry holds the old and the new value as plain text (tags removed, entities decoded). The History window shows plain text.
  • The dashboard shows a richtext column as plain text, with the same converter. (P2 has no such column.)
  • Rich text is not in the emails of P2.
  • Package version: a stable HtmlSanitizer version whose dependencies (AngleSharp, AngleSharp.Css) are also stable versions. Build step 5 verifies this (DR-17).

10. Engine adapter (C1 to C8)

The design is module 10. This section gives the parts for a section form and the answers Q2, Q3 and Q8.

10.1 Parts

  • IAtlasWorkflowAdapter in Service/Platform/Workflow/: Start, Execute, ReadContext, DispatchNotifications. SLA synchronization and the history read are not in P2 (D20, D27).

10.3 Save order

For a save of a form with steps (each such save is a submit, 6.4):

  1. The request has no RequestId: refuse the save (page error). The state has no step: refuse the save (NotAllowed).
  2. Validate (rules, access, fields, files). Find the recipients (10.6) and the template data (10.7). No write.
  3. Begin the transaction. Write the record with the Set values, the audit entries and the attachments. SaveChanges, no commit.
  4. Run the first engine action (Start with the initial action, or Execute).
  5. Engine Success is false: roll back. Return the engine code and message as a page error. Nothing changed.
  6. Engine Success is true: write WorkflowState (the engine state key) and Status (the label of StatusLabels). Add one status line to the audit entry of this save (12). Commit.
  7. After the commit, run each later engine action in order. After each one, compare the engine state with the WorkflowState of the record; a difference is an error log (DR-19). Then dispatch the notifications of all actions.

Failures after the commit do not undo the save:

  • A later action fails (E2): the record stays saved. The adapter writes the error log Atlas.WorkflowStepFailed with the instance ID and the action key. The response says "Saved. One notification was not sent." No automatic second try in P2. The target support team acts on this log event: it sends the email by hand (DR-19).
  • A dispatch fails: warning log; the engine outbox sends the email again (module 10, 4.5).
  • The commit of step 6 fails after the engine committed: error log. Section 10.8 gives the two cases and the action.

Double submit (DR-16):

  • Request field RequestId: a GUID that the client makes for each user action. It is optional in the v1/ManagePage contract, but a submit of a form with steps needs it (step 1). With no RequestId, the protection is lost, so the server does not make one itself.
  • The idempotency key of engine action n is RequestId + : + n.
  • The engine key is global and the engine compares the request hash. A second request with the same RequestId for a new record gets a second record ID, so the engine refuses it and the second record is rolled back. The adapter maps this engine result to the page error "This request was already processed."

10.4 Load

When a record with a binding loads, the adapter reads the engine context. If the engine state is not the WorkflowState of the record, the platform writes the engine state and the status label to the record, writes one audit entry (WorkflowSync) and a warning log. The engine is the source of truth for the state.

Each record with no engine instance is not checked (DR-21). This is a new record, and also a record that the target team moved from SharePoint; such a record loads with no error.
