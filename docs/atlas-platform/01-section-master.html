Section Master: reusable design

This report examines the Section Master form in CP Atlas. It shows the per-app code in the form. It gives a design that lets a new business app use the form with configuration only.

Language. This report uses ASD-STE100 Simplified Technical English at approximately 80% compliance. Code names, JSON keys and file names stay as they are in the source.

Ownership. The target team owns the CP Atlas code. This report gives requirements and a design to that team. This report does not change the workflow engine or the target code.

Source. target-implementation-read-only/. Line numbers refer to these .txt copies. Some copies have copy errors. An item marked Confirm depends on files that are not in the copy.

1. Purpose

Section Master shows a single-page form for one application record. SQMSO (Opportunity), SQMSB (Bid), TTD (Tax Time Database) and AIN (Account Inventory) use it. CDT uses Step Master (module 2).

All new business apps except one use Section Master. One more app uses Step Master (business owner, 2026-10-25). Thus Section Master is the platform for most new apps. If Section Master is generic, a new app needs only a JSON file and SQL scripts.

2. Current behaviour

2.1 Flow

  1. The dashboard opens sectionmaster/:code/:id. The value id = 0 means a new record.
    app.routes.ts.txt:30-31; cp-atlas-dashboard.ts.txt:109-125, 316-330
  2. The form component sends GET v1/SectionPage?Code=&ID=.
    cp-atlas-sectionmaster.ts.txt:69-86; cp-atlas-service.ts.txt:76-82
  3. The controller calls CPAtlasService.LoadSectionPage. This method selects a module service with an if chain on the app code.
    CPAtlasController.cs.txt:64-70; CPAtlasService.cs.txt:86-90, 164-176
  4. The module service reads its JSON file from the disk. If ID > 0, it puts the database row into the controls (BindData). Then it adds default data, options, status, header name and rules.
    CPTTDService.cs.txt:43-63, 146-171; CPSQMSOService.txt:68-111; CPSQMSBService.cs.txt:70-113; CPAINService.cs.txt:34-66
  5. The component makes an Angular reactive form from Controls and ChildControls. It adds validators from Validator.
    cp-atlas-sectionmaster.ts.txt:97-149
  6. The template shows each child control by Type: select, ngselect, textarea, text, currency, percent, datetimepicker, option.
    cp-atlas-sectionmaster.html.txt:15-126
  7. The buttons come from the JSON Buttons list. Submit saves through POST v1/ManagePage. Close goes back. Bid calls GET v1/Execute?action=MakeBid. On SQMSO and SQMSB, each other button sets Status to the button name and saves.
    cp-atlas-sectionmaster.ts.txt:298-380; cp-atlas-service.ts.txt:93-120

2.2 Parts that are already generic

  • The JSON supplies the controls, labels, types, validators, options, CSS classes and buttons.
  • The server has a rules engine (CPRule). A rule uses roles, states and owner to show, hide, enable or disable controls and buttons.
  • MapData and BindData copy form values to and from entity properties by name.

5. Reusable design

The design adds optional JSON properties and a server registry. If a new property is not in the JSON, the current behaviour does not change.

5.1Value-based client rules (Effects)

Add an optional Effects list to CPApplicationControl. The component runs the effects when it makes the form, and each time the source value changes. It does not use a timer or document.getElementById. This removes SM-01 and SM-09.

{
  "Name": "ClientRelationshipLeavingBBH",
  "Type": "option",
  "Effects": [
    { "When": { "Equals": "No" },
      "Show": ["RationaleForSecondarySale"],
      "Require": ["RationaleForSecondarySale"] },
    { "When": { "NotEquals": "No" },
      "Hide": ["RationaleForSecondarySale"],
      "Unrequire": ["RationaleForSecondarySale"] }
  ]
}
{
  "Name": "BidAskValue",
  "Effects": [
    { "When": { "Equals": "Yes, Fair Value" }, "Set": { "BidExpressedAsFairValue": "100 %" } },
    { "When": { "NotEquals": "Yes, Fair Value" }, "Clear": ["BidExpressedAsFairValue"] }
  ]
}
  • Conditions: Equals, NotEquals, In, HasValue. Do not add an expression language.
  • Actions: Show, Hide, Require, Unrequire, Enable, Disable, Set, Clear, SetFromOption, OptionsFromChild.
  • A hidden control has no validators. The client does not send it in the save.
  • The server must also examine the Require rules on save. A client rule is only for the user interface.

5.2Structured option data

Add an optional Data dictionary to CPKeyValue. SetFromOption reads from Data. If Data is not there, the client uses the current " - " split. This removes SM-04 and keeps the current options.

{ "Label": "12345 - Smith Trust - J. Doe",
  "Value": "12345 - Smith Trust - J. Doe",
  "Data": { "AccountNumber": "12345", "AccountName": "Smith Trust", "RelationshipManager": "J. Doe" } }

{ "Name": "Account", "Type": "ngselect",
  "Effects": [ { "When": { "HasValue": true },
    "SetFromOption": { "AccountNumber": "AccountNumber", "AccountName": "AccountName",
                       "RelationshipManager": "RelationshipManager" } } ] }

5.3Button actions from JSON

Add an optional Action object to CPButton. The Type values are Save, Close, Execute and Navigate. If a button has no Action, the component uses the current logic by button name. This removes part of SM-02.

{ "Name": "Accepted", "Label": "Accept", "Action": { "Type": "Save", "Set": { "Status": "Accepted" } } }
{ "Name": "Bid", "Label": "Make a bid", "Action": { "Type": "Execute", "Execute": "MakeBid", "OpenCode": "SQMSB" } }
{ "Name": "Close", "Label": "Close", "Action": { "Type": "Close" } }

5.4Redirect after save from JSON

Add an optional Redirects list to CPApplicationSection. The component uses the first entry that agrees with the roles of the user. This removes the remainder of SM-02.

"Redirects": [
  { "Roles": ["MFO"],  "Url": "/dashboard/{code}/MyBids" },
  { "Roles": ["IPFG"], "Url": "/dashboard/{code}/IPFGBids" },
  { "Url": "/dashboard/{code}" }
]

If there is no Redirects list, SQMSO, SQMSB, TTD and AIN use the current logic. A new app with no list goes to /dashboard/{code}.

5.5Control renderer registry

  • Replace the long *ngIf chain with one map from Type to a renderer component. Each current type keeps its current markup and its div_{Name} ID.
  • Add renderers for filepicker and grid, or confirm that the live template has them.
  • If Type is not known, show an "Unknown control type" message in non-production builds. In production, write a console error.
  • Remove the Vehicle1/2/3 special rows. Use OptionsFromChild and DivClass.

This removes SM-03 and SM-05.

5.6Server module registry

Replace the if chains with a registry. Use .NET keyed services. Keyed services are part of .NET 8 and later. No third-party package is necessary. This removes SM-06 and SM-10.

// Composition root: one line for each app.
services.AddAtlasModule<CPSQMSOService>("SQMSO", configFile: "SQMSO.json");
services.AddAtlasModule<CPTTDService>("TTD", configFile: "TTD.json");
// A new app with no special logic:
services.AddAtlasModule<ConfigSectionService>("PBSP", configFile: "PBSP.json");
  • AddAtlasModule registers the service by code for each interface that the service implements.
  • If a code has no service for an interface, return HTTP 404 or 400 with a clear message. Do not return null.
  • Load the JSON files from one folder setting (AppSettings:ConfigFolder). Keep them in a cache. Load them again when a file changes. Give a deep copy to each request, because the services change the section object.
  • Keep the old <Code>ConfigPath keys. If a key exists, it replaces the folder path for that code.
  • Keep CPApplicationCode for the current codes. The registry uses the string code, so a new app does not need an enum change.

5.7Generic section service

ConfigSectionService is the default service for a simple app. It does these steps from JSON:

  • Header. HeaderName, and an optional template such as "{Name} - {ID}".
  • Defaults. An optional Defaults map, for example { "Status": "DRAFT", "CreatedBy": "{User.DisplayName}" }.
  • Roles. It always reads only the roles for the current application. Then it applies CPRule to the controls and the buttons. This removes SM-08 and the missed calls in SM-09.
  • Options from data. An optional OptionsSource on a control, for example a stored procedure name. Module 5 (data mapping) gives the details.
  • Save and load. MapData and BindData with the entity or table from the module registration. Module 5 gives the details.

An app with special logic still has its own service class. The class inherits from ConfigSectionService. It overrides only the hooks that it needs: OnLoad, OnBeforeSave, OnAfterSave, OnExecute. This removes SM-07.

5.8Dashboard navigation

Add an optional FormType (SECTION or STEPPER) to each app in the dashboard JSON. onClick and editRow use it to open sectionmaster or stepmaster. If FormType is not there, the dashboard uses the current if chain.

5.9Server save pipeline

ConfigSectionService has one save pipeline. A module service changes it only through hooks (OnLoad, OnBeforeSave, OnAfterSave, OnExecute). This removes SM-13, SM-14 and SM-16.

  1. Load the configuration and the record.
  2. Read the user roles for this application only. Find the owner and the state.
  3. Apply CPRule and the server part of Effects. The result is the effective section for this user.
  4. Make an allow list: the controls that are visible and enabled in the effective section. Ignore all other Outputs. Write a warning log for each ignored name. This fixes H3 and the field part of H4.
  5. If the button or the save is not permitted for this user and state, stop with an error. This fixes the access part of H4.
  6. Examine the Validator rules and the Require effects on the server.
  7. Examine the version token (5.13).
  8. Map the allowed values to the entity.
  9. Set the system fields on the server: CreatedBy, CreatedDate, ModifiedBy, ModifiedDate and the Defaults values. Use TimeProvider, not DateTime.Now. The client cannot set these fields.
  10. Call the workflow engine (5.10). If the engine result is not a success, stop with an error.
  11. Write the audit entry on the server (5.12).
  12. Commit. If an error occurs, roll back, write a log and return the error (5.11).

Issue H6 (the engine and Atlas use separate transactions) also applies to step 10. The engine adapter spec (module 10) covers H6.

5.10Workflow binding from JSON

Add optional properties to the Workflow block. This removes SM-15.

"Workflow": {
  "Key": "SqmsOpportunity",
  "BusinessObjectPrefix": "SQMS-OPP-",
  "InitialAction": "SubmitOpportunity",
  "ActorRoles": "User",
  "Recipients": {
    "maker":        { "FromUserField": "CreatedBy" },
    "sellerRmTeam": { "FromUserField": "SellerRMTeam", "Multiple": true }
  },
  "Actions": { "...": "unchanged" }
}
  • BusinessObjectPrefix and InitialAction replace the values in code. Keep the current values, so that the engine instance IDs do not change.
  • ActorRoles: "User" sends the roles of the user for this application. If ActorRoles is a list, the service sends that list (current behaviour, for example ["MFO"]). Change SQMS to "User" only after a check that each submitter has the role that the engine needs.
  • Recipients maps a field to a recipient key. The service finds each user by display name in CP_Atlas_User.
  • The service must read Success and ResultCode from each engine result.
  • Actions does not change. GetWorkflowAction already uses it.

5.11Error contract

  • Add an optional Errors list to the ManagePage response: [{ "Field": "AccountName", "Code": "Required", "Message": "..." }]. Field is empty for a page error.
  • On error, the response has ID = 0 and Errors is not empty. The HTTP status stays 200 in phase 1, so the current client does not fail.
  • The updated client shows the errors and does not redirect. It shows "saved" only when Errors is empty.
  • Phase 2 (with approval): return HTTP 400 for validation errors and 409 for a version conflict.

This removes SM-16.

5.12Server audit

  • The save pipeline writes the audit entry in the same transaction. It uses the change list from MapData (lstDifference). The service already makes this list.
  • Keep the POST AuditLog endpoint for old clients. When the server audit is active for a module, the endpoint ignores calls for that module. This prevents two entries.
  • One shared audit table for all apps is part of module 9. Until then, use the current table of each app.

This removes SM-17.

5.13Version token

  • Add a rowversion column to each Section Master table. Use the script sql/01-section-master-rowversion.sql. The script is additive and safe to run again.
  • The load response has an optional Version (base64). The client sends it back in the save input.
  • If the save has Version and it is different from the database value, return a conflict error. If the save has no Version (an old client), do not examine it. This keeps the current clients working.

This removes SM-18.

Result. After this design, a new simple app needs these items only: a JSON file, one registration line, SQL scripts (table, procedures, entitlements) and one dashboard JSON entry.

6. Backward compatibility

  • Do not change the route sectionmaster/:code/:id.
  • Do not change the endpoints v1/SectionPage, v1/ManagePage and v1/Execute, or their request and response shapes. All new DTO properties are optional and nullable.
  • Do not change control names, the div_{Name} and btn_{Name} element IDs, or the #$# multi-value separator.
  • The current JSON for SQMSO, SQMSB, TTD and AIN must give the same result with no edits. Each new property has a fallback to the current code path.
  • Remove a legacy code path only when all these conditions are true:
    1. The JSON for that module has the equivalent Effects, Action or Redirects.
    2. The regression checks in section 8 pass for that module.
    3. The target team approves the removal.
  • Do not change the ManagePage response fields. Errors and Version are new optional fields. The HTTP status stays 200 in phase 1.
  • Do not change the engine instance IDs (BusinessObjectPrefix + ID) or the action keys.
  • Keep the POST AuditLog endpoint.
  • The only database change is an additive rowversion column (5.13). It does not change existing data.

8. Regression and acceptance checks

8.1 Current modules

Do these checks for SQMSO, SQMSB, TTD and AIN. Do them for a new record and for an existing record.

  • Make sure that the same controls show, with the same labels, values, options, disabled state and required markers.
  • Make sure that the same buttons show and do the same actions.
  • Make sure that the save sends the same Outputs names and values.
  • Make sure that the redirect after save goes to the same dashboard tab for MFO, IPFG and other users.
  • Make sure that the SQMS dependent fields give the same results: Account, OpportunityId, BidForFullCommitment, BidAskValue, FundConsideredSecondarySale, ClientRelationshipLeavingBBH, IsValuationForPrivateFundVehicle. The results must now apply immediately, not after 5 seconds.
  • Make sure that the SQMS status buttons start and execute the workflow engine actions as before, with the same engine instance IDs.
  • Make sure that a save with an extra output name (for example WorkflowState or IsDeleted) does not change that field.
  • Make sure that a save for a control that is hidden or disabled for the user does not change that field.
  • Make sure that a save that fails shows an error and does not redirect. The server must write no audit entry.
  • Make sure that an engine rejection shows an error. The record and the state must not change.
  • Two users save the same record. Make sure that the second user gets a conflict error.

8.2 New pilot app

  • Make sure that the app operates with these changes only: a JSON file, one registration line, SQL scripts and a dashboard JSON entry.
  • Make sure that a user with a role only in another app cannot see or change the pilot app records.
