Peak concurrent users on the whole portal

PF9 — Slow-request log event

recommended first
Recommendation: build it first. A new log event Atlas.SlowRequest (Warning) when a platform request takes longer than AppSettings:Atlas:SlowRequestMs. It records app, operation, LAN ID, duration and the number of SQL round trips. Reason: daily usage is unknown. This gives the numbers that decide PF1 and PF2, with no new package and no APM product.
Decision

PF3 (config part) — Bound the dashboard tabs

recommended now
Recommendation: JSON change only, no code. Every tab without a {LanId} filter gets MaxRows, or a narrowing filter. In TTDV2.Dashboard.json the tab Tax-Time All Report has no filter and reads the whole table. The code part of PF3 (parallel or streamed tab queries) is dropped: 3 sequential SELECTs cost about 50 ms.
Decision for the All Report tab (and the same pattern for the next apps)

PF8 — Index check in the start-up check

recommended in P2
Recommendation: build it with the next app. The start-up check reads sys.index_columns and gives a warning when a dashboard Filter or OrderBy column has no index. The new-app SQL template gets CREATE INDEX lines for the example filter columns (CreatedBy, TaxPreparerLanId, ModifiedDate). A table scan is invisible with 500 rows and painful with 500 000; the check finds the missing index at release time for every app.
Decision
Also add the indexes for TTDV2 now?

PF2 — Cache the user roles for a short time

recommended in P2, default off
Recommendation: build it, default off. New setting AppSettings:Atlas:RolesCacheSeconds (0 = off, as today). With a value, the roles of a LAN ID come from IMemoryCache and the query vw_CP_Atlas_ActiveUserRole runs once for each user in that time. Removes one round trip from every request. Trade-off: a grant or revoke applies after up to that many seconds.
Decision

PF1 — Async I/O end to end

recommended: defer
Recommendation: defer. At 2–5 requests a second, synchronous I/O does not starve the thread pool. The current apps run the same way today. The change needs additive ...Async(CancellationToken) overloads in the platform and async controller methods at the target (target code). Revisit when PF9 shows queueing.
Decision

PF5 (operational part) — Start-up after an app pool recycle

recommended: document
Recommendation: no code; document the IIS settings. The start-up (metadata of 40–60 tables, EF model, start-up check) runs once after each recycle. With IIS Start Mode = AlwaysRunning and Preload Enabled the first user does not wait for it. The code part (one metadata query instead of one for each table) is dropped: under a second in total.
Decision

PF4, PF6, PF7 — Items recommended to drop

recommended: drop
Recommendation: drop all three (keep them in the handoff as "not planned"). PF4: option lists are re-loaded on save, but PBAccounts is cached 24 h at the target and UsersInRoles is one small query. PF6: the form JSON parse is under a millisecond. PF7: the linear scans are not measurable with 10–50 controls.
Decision (select all that you want to KEEP in the backlog)
