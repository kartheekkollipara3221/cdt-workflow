How the new design works, end to end

This report gives a short overview of the generic Atlas platform. It tells you what the parts are and how a request goes through them. It does not give the full details. The full details are in modules 01 to 23.

Written in ASD-STE100 Simplified Technical English. Pilot app: TTDV2. Code: atlas-platform/. Target bundle: bcb4b2b.

1. The idea in one paragraph

Each old Atlas app has its own C# service, its own entity classes and its own form code. The new design replaces this with one generic service for all apps. Each app is only data: JSON files and a SQL table. The platform reads the table columns from the database. It reads the form, the rules and the dashboard from the JSON. Then it shows the form, checks the values and saves the record. A new app does not need new C# code or new Angular code.

TTDV2 is the first app on the platform. It has no C# code of its own. The old TTD app does not change. It continues to work as before.

3. How to add an app

  1. Write a SQL script that makes the app table, the audit table, the app row and the roles. For TTDV2, this is 040-ttdv2-app.sql.
  2. Write the three JSON files: the manifest, the form and the dashboard.
  3. Register the app with one line: AddAtlasModule<ConfigSectionService>("TTDV2").
  4. Run --atlas-check. Correct all errors.
  5. Set the app to Enabled and restart the app pool.

An app that needs special behavior can add a small subclass with hooks: OnLoad, OnBeforeSave and OnAfterSave. Most apps do not need it.

5. The user flow

5.1 Open the dashboard

  1. The user selects the app on the home page. The home page shows only the apps for which the user has a role.
  2. The browser asks the API for the dashboard.
  3. For each tab, the server makes one SQL query from the dashboard JSON. Column names come only from the table metadata. User values are SQL parameters. The query always shows only the records that are not deleted.
  4. The browser shows the tabs and the grid. The user clicks a row or "New" to open the form.

5.2 Open the form

  1. The browser asks the API for the form of the record. If the user opens a different record before the answer comes, the browser cancels the old request.
  2. The server checks the access. It reads the record from the table.
  3. The server puts the values into the form controls. It applies the rules: some fields become hidden or read-only. It removes the values of the hidden fields.
  4. The server sends the form, the values and the version of the record.
  5. The browser draws each section and each field with the correct control.

5.3 Change values

When the user changes a value, the browser runs the effects and the computed values from the JSON. For example, it calculates the weekly total. It shows field errors immediately. The server does the same checks again at save. The server does not trust the browser.

5.4 Save

  1. The browser sends the field values and the version.
  2. The server checks the access and applies the rules again. It accepts only the fields that the user can change. Other fields give an error.
  3. The server converts each value to the column type and checks it. It runs the effects and the computed values again. It adds the system values: created by, modified by, dates.
  4. The server writes the record and the history row in one transaction. If another user changed the record after the load, the version is different. Then the server saves nothing and shows a conflict message.
  5. The server sends back the record ID and the new version.

5.5 Delete

The platform never removes a row. It sets IsDeleted to 1 and writes a history row. The record then disappears from the dashboard and the form. It stays in the table and in the history.

5.6 History

The user clicks "History". The server reads the history rows of the record, oldest first. If the rules hide a field from the user, its old and new values show as ***.

6. Safety

  • Access: each operation checks the role of the user. Roles come from the existing dbo.CP_Atlas_* tables, through a read-only view.
  • No SQL injection: table and column names come only from the database metadata. All values are SQL parameters.
  • The server decides: the server applies the rules, effects and checks again. A change in the browser cannot bypass them.
  • No lost updates: the record version stops two users from overwriting each other.
  • All or nothing: the data and its history row commit together. If one fails, nothing is saved.
  • Hidden data stays hidden: hidden values are not sent on load and show as *** in the history.

7. How it fits into the target

  • The platform code goes into new Platform/ folders in the four target projects. The existing code does not change, except for a small number of hand edits. INTEGRATION.md gives each edit.
  • The existing apps (TTD, CDT, SQMS, AIN) continue to use their own services. TTDV2 uses the generic service.
  • The platform uses the existing users, roles and app tables. It reads them and does not change them.
  • The workflow engine does not change.

8. Known limits

  • A change to the config or to a table needs an app-pool restart.
  • The dashboard cannot run a tab from a stored procedure yet (RV-N1). Correct this before app #2.
  • Start-up does not try again after a short SQL failure (RV-07). Restart the app pool.
  • Rollback 090 gives back only the TTD roles that 050 removed in the hour before the copy.
  • Performance work comes after the integration and the review with the target team.
