1. The idea

Each current Atlas app (TTD, CDT and the others) has its own C# service, its own entity classes and its own screen code. The platform replaces this with one generic service and one generic form. A platform app is only data: 3 JSON files and a SQL table.

The platform reads the table columns from SQL Server at start-up. It reads the form, the rules and the dashboard from the JSON files. Then it shows the form, checks the values, saves the record and writes the audit.

The current apps do not change. Each new line in the shared target files runs first. For a current app, it does nothing, and the current code runs as before.

11. Request flows

11.1 Home menu: GET v1/Application

  1. CPAtlasService.GetApplication calls dbo.Get_Application (current).
  2. AtlasApplicationMenu.Enrich adds FormType and HasDashboard to the platform rows and removes disabled platform apps.
  3. The menu shows an app when HasDashboard !== false.

11.2 Dashboard: GET v1/Dashboard?code=TTDV2

  1. The PLATFORM line in LoadDashboard finds TTDV2 and calls ConfigSectionService.LoadDashboard.
  2. AtlasDashboardService reads TTDV2.Dashboard.json, checks View access for each tab, and runs the tab queries from AtlasTabQueryBuilder.
  3. In cp-atlas-dashboard.ts, GenerateColumns calls columnDefs for a tab with Columns. sumsRow gives the totals row.
  4. Add and Edit call AtlasDashboardNavigation.open. It opens form/TTDV2/:id.

11.3 Open the form: GET v1/SectionPage?AppCode=TTDV2&ID=n

  1. AtlasFormComponent calls AtlasApiService.
  2. ConfigSectionService.LoadPage checks access, reads the record (or the defaults for ID 0), runs the rules (AtlasRuleEngine) and the effects, and loads the options.
  3. The form draws each control with the renderer registry.

11.4 Save: POST v1/ManagePage

ConfigSectionService.SavePage does these steps in this order. An error in a step stops the save and returns the errors (HTTP 200 with Errors, ID 0).

11.5 Delete and history

  • POST v1/RemovePage?code=TTDV2&id=n: ConfigSectionService.RemovePage checks Delete access, sets the SoftDelete field of the form (IsDeleted for TTDV2) and writes a Delete audit row.
  • GET v1/GetAuditLog?appCode=TTDV2&refID=n: ConfigSectionService.GetAuditLog reads TTDV2.AuditLog in the target History Log format. POST v1/AuditLog does nothing for TTDV2 (AuditMode: Server).

11.6 A current app (for example TTD)

The PLATFORM line finds no platform app. The current if chain runs, with the enum from AtlasAppCode.ToLegacy. The result is the same as before.

12. Start-up and registration

// program.cs
builder.Services.AddAtlasPlatform(configuration);
builder.Services.AddAtlasModule<ConfigSectionService>("TTDV2");   // one line for each app
var app = builder.Build();
if (check) return await app.Services.RunAtlasCheckAsync(Console.Out);   // optional --atlas-check
await app.Services.StartAtlasPlatformAsync();
  1. AtlasConfigStore reads the manifests and JSON files.
  2. AtlasColumnMetadataReader reads the table columns of the registered apps.
  3. AtlasStartupCheck compares the JSON with the tables.
  4. An app with errors is disabled (DisableModule): 404, not in the menu, log event Atlas.AppDisabled. The current apps continue to operate.

12.1 How the platform keeps the table definitions

The platform keeps the table definitions only in memory. It does not write them to a file or to a database table. SQL Server is the source of truth. The platform reads it again at each start.

ManifestsTable, AuditTable, AttachmentTable of each registered app
→
AtlasColumnMetadataReaderone query on sys.tables, sys.schemas, sys.columns
→
AtlasTableRegistrysingleton dictionary, key "Schema.Name"
→
AtlasPlatformContextEF Core shared-type entities
  1. Which tables. The start-up collects the table names from the manifest of each registered app. It includes disabled apps, so an app that is switched on later has its tables ready. For TTDV2: TTDV2.General and TTDV2.AuditLog.
  2. How they are read. AtlasColumnMetadataReader gets the name, SQL type, length, precision, scale, nullable, identity, computed and default constraint of each column.
  3. Where they are kept. AtlasTableRegistry is a singleton with one Dictionary<string, AtlasTable>.
    • AtlasTable: schema, name and the list of columns. It finds the key (ID) and the soft-delete column (IsDeleted).
    • AtlasColumn: also gives the .NET type, the EF Core store type (for example decimal(19,2)), and flags for row version and database-generated values.
  4. How EF Core uses them. AtlasPlatformContext.OnModelCreating maps each table as a shared-type entity Dictionary<string, object?> with the name "Schema.Name". Code reads and writes rows with Records("TTDV2.General"). The registry makes a ModelKey from all table and column definitions. AtlasModelCacheKeyFactory gives this key to EF Core, so EF Core builds the model one time and keeps it in its cache.
  • A change to an app table (for example a new column or a new type) needs an app pool restart. This is the same as for a change to a config file.
  • The JSON files do not define columns. They only use column names. --atlas-check compares these names with the columns in the registry.
  • If a table does not exist, or the API login cannot see it, the reader does not find it. The start-up check then disables only that app.

15. How to add a new app

A new platform app needs no new C# and no new TypeScript. TTDV2 is the example.

  1. Write a SQL script from 040: schema, main table, audit table, app row, roles.
  2. Write <CODE>.app.json, <CODE>.json and <CODE>.Dashboard.json in Config/.
  3. Add one line to program.cs: AddAtlasModule<ConfigSectionService>("<CODE>").
  4. Add AppSettings:Modules:<CODE> to appsettings.json.
  5. Add new Tailwind classes from the JSON to the safelist.
  6. Run --atlas-check. The result must be 0 errors.
  7. Give roles to the testers.

An app that needs custom logic gets a subclass of ConfigSectionService with OnLoad, OnBeforeSave or OnAfterSave, and its name in the manifest Service.

16. Rules for the team

  • Do not edit the platform files at the target. Report the bug. The fix comes in a new package.
  • Do not remove the current if chains. They serve the current apps.
  • Do not rename app codes, role names, table names or JSON keys. They are stable identifiers.
  • Database changes go in SQL scripts only. Do not use EF migrations for platform tables.
  • If you scaffold CPSharepointContext from the database again, leave out the new tables.
  • Give TTDV2 roles only to testers until the business approves.
  • After a change to a config file, restart the app pool and run --atlas-check.
  • After each change, test one current app (dashboard, add, edit, history) and TTDV2.

17.2 Open the form (load)

Client (atlas-form.component.ts, ngOnInit)

  1. The route gives code and id. id = 0 means a new record.
  2. The form calls GET v1/SectionPage?AppCode=TTDV2&ID=n. If you go to a different record before the answer comes, switchMap cancels the old call.

Server (ConfigSectionService.LoadPage)

  1. It reads the record (ID > 0) and checks View access, or it checks Create access for a new record. If the record does not exist, it gives 404. If the user has no access, it gives 403 in Enforce mode.
  2. It puts the saved values into the controls, or the Defaults for a new record (BindValues).
  3. It loads the drop-down options (LoadOptions).
  4. It runs the OnLoad hook. TTDV2 has no hook.
  5. It runs the rules (AtlasRuleEngine) and sets each field to hidden, read-only or editable.
  6. It removes the values of fields that a rule hides. The hidden data then does not go to the browser.
  7. It adds the header text, Version (the row version, for conflict checks), UserPermissions and Computed.

Client (build)

  1. It makes an Angular FormGroup from the controls (buildFormGroup).
  2. For each control Type, the renderer registry gives the component. A type with no renderer is disabled and is not sent.
  3. It connects the effects. They run one time at load, and again each time the source value changes.
  4. It connects the computed values. The client shows WeeklyTotal while the user types.
  5. If UserPermissions does not permit the save, the form is read-only and has no Save button.

17.3 While the user types

  • Validators (atlas-validators.ts) show field errors.
  • Effects (atlas-effects.ts) show, hide, require, set or clear other fields.
  • Computed fields update.

All of this is only for the user. The server does each check again at save, so a changed browser cannot get past the rules.

17.4 Save

Client (save)

  1. It marks the shown fields as touched. If a shown field is not valid, it opens the "mandatory fields" modal and stops.
  2. It sends POST v1/ManagePage with AppCode, ID, Version and Outputs. Outputs has only the shown fields.

Server (ConfigSectionService.SavePage)

#StepWhat it does
1LoadStoredReads the current record and checks Edit or Create access.
2ApplyRulesRuns the rules again on the server.
3ReadAndFilterUses the allow list. It refuses an unknown or disabled field (Atlas.FieldRefused). It ignores a server-set or unchanged field (Atlas.FieldIgnored).
4ValidateFieldsRuns the same validators as the client.
5CheckVersionCompares Version with the row version. If another user saved first, it gives a conflict.
6MapRecordConverts each text value to the column type (AtlasValueConverter).
7ComputeAndSystemFieldsCalculates WeeklyTotal again, and sets Created/Modified By and Date.
8RunBeforeSaveThe OnBeforeSave hook.
9PersistSaves the record and the audit row in one transaction. If nothing changed, it writes no audit row.
10CompleteRuns OnAfterSave and returns the result.

If steps 1 to 8 find errors, the server returns HTTP 200 with an Errors list and ID = 0. Nothing is saved.

Client after the answer

  • Errors: a field error goes under its field. Other errors go at the top of the form.
  • Success: the message "Record saved successfully" shows, and the form goes back to the dashboard.

17.5 Delete and History

  • Delete: the form asks for confirmation, then calls v1/RemovePage. The server checks Delete access, sets IsDeleted, and writes a Delete audit row.
  • History: the button shows only when UserPermissions.CanViewHistory is true. It opens atlas-history-dialog.ts, which uses v1/GetAuditLog.

17.6 The main rule

The client is for the user. The server is the authority. Rules, validators, effects and computed values run on both sides. The client gives the user fast feedback. The server makes the decision. The shared case files (atlas-validator-cases.ts, atlas-effect-cases.ts) are tested on both sides, so the two sides stay the same.

18. How the dashboard works

The dashboard has no new Angular component at the target. The current dashboard (cp-atlas-dashboard.ts) shows TTDV2. The platform adds 2 things:

  • Server: AtlasDashboardService builds the tabs, rows, menus and buttons from TTDV2.Dashboard.json.
  • Client: 3 small edits from step 6 (columns, totals row, navigation).

18.2 Load the dashboard: server

GET v1/Dashboard?code=TTDV2 → the PLATFORM line in CPAtlasService.LoadDashboard → ConfigSectionService.LoadDashboard → AtlasDashboardService.Load.

  1. App check: the app must be registered and Enabled. If not, the result is 404.
  2. Access check: the user must have View access. If not, the result is 403 in Enforce mode.
  3. For each tab:
    1. It runs the tab Rules. A hidden tab gets no rows, and no query runs for it.
    2. If the tab shows rows of a different app, that app must be enabled and the user must have View access to it.
    3. Rows: AtlasTabQueryBuilder makes one SQL query. Table and column names come only from the table registry, and each name is quoted. Each filter value is a SQL parameter. The platform always adds IsDeleted = 0.
    4. User columns (Type: "user"): one query gets the display names of all LAN IDs in the rows.
    5. Dates: dates and booleans are changed to the same text format as the form.
    6. Menus: Edit, History and Delete are visible only if Permissions permits them for the user.
  4. Buttons: "Add New" shows only if the user has Create access.
  5. The response has AppCode = "TTDV2".

18.4 Navigation

AtlasDashboardNavigation.open(code, id, target):

  1. It reads the v1/Application rows one time and keeps them.
  2. It finds the FormType of the app. TTDV2 has FORM.
  3. If there is a FormType, it opens form/<code>/<id> and returns true.
  4. If there is no FormType (all current apps), it returns false. The current if chain then runs.

"Add New" uses the button Target (Id: 0). Edit uses the row ID.

18.5 The main rule

The server decides what the user can see. The client only draws it. Hidden tabs get no rows. Menus and buttons come from Permissions. Each Edit and Delete is checked again on the server for each record.

19. How the rules engine works

The rules engine is one class: AtlasRuleEngine (Service/Platform/Rules/AtlasRuleEngine.cs). It runs only on the server. It uses who the user is to decide which parts of the form or dashboard are visible, hidden, editable or read-only. The record owner and the record state are also inputs.

19.1 Rules, Effects and Permissions

MechanismInputOutputRuns on
PermissionsRoles, ownerAllow or deny an operation (View, Create, Edit, Delete, History). Deny gives 403.Server (AtlasAccessService)
RulesRoles, owner, statesVisible, hidden, read-only or editable parts (controls, buttons, tabs, menus)Server (AtlasRuleEngine)
EffectsField valuesShow, hide, require, set or clear other fields while the user typesClient and server

Rules do not look at field values. Effects do that.

19.3 One rule

{ "Roles": ["Prepare"], "IsOwner": true, "Disabled": false }

A rule matches when all of its conditions are true. A condition that the rule does not give counts as true.

  • Roles: the user has one or more of these tokens.
  • States: the record is in one or more of these states.
  • IsOwner: the owner value is the same.

When a rule matches, it gives Visible (default true) and Disabled (default false) for the target, and optional lists of child controls: ShowControls, HideControls, EnableControls, DisableControls.

19.4 The two modes (manifest RuleMode)

ModeHow the matched rules are combined
FirstMatchOnly the first matched rule counts. This is the behavior of the current apps.
MostPermissive (TTDV2)All matched rules count. Visible if any rule makes it visible. Disabled only if all rules disable it. Show wins over Hide. Enable wins over Disable.

19.5 When no rule matches (manifest RuleDefault)

DefaultResult
KeepNo change. The JSON values stay.
ReadOnly (TTDV2)Visible, but disabled
HiddenHidden and disabled

If a target has no rules, nothing changes.

19.6 Where the rules apply

Form (ApplyToSection, in LoadPage and again in SavePage)

  1. Each top-level control (a section container) uses its own Rules. If it has none, it uses the app-level Rules of the form.
  2. The result goes to the container, and then to each child control:
    • A hidden container hides its children.
    • HideControls and ShowControls change single children.
    • A child that the JSON disables stays disabled, unless a rule names it in EnableControls.
    • A disabled grid control also disables its cell editors.
  3. Buttons use their own Rules.
  4. The engine returns the fields that the rules hid and disabled (AtlasRuleOutcome). The service then:
    • at load, removes the values of hidden fields, so the hidden data does not go to the browser;
    • at save, refuses a value for a hidden or disabled field (Atlas.FieldRefused).

Dashboard (AtlasDashboardService)

  • Tab Rules: the default is Hidden. A hidden tab gets no rows.
  • Button Rules and menu Rule: these show, hide or disable the item.

19.7 TTDV2 worked example

"Rules": [
  { "Roles": ["@Read"],   "Disabled": true },
  { "Roles": ["Prepare"], "IsOwner": true, "Disabled": false },
  { "Roles": ["@Admin"],  "Disabled": false }
]

Mode MostPermissive, default ReadOnly:

UserMatched rulesResult
Read1Read-only
Prepare, own record1 + 2Editable (rule 2 does not disable)
Prepare, other user's record1Read-only
Prepare, new record1 + 2 (a new record is owned)Editable
Owner1 + 3Editable

With FirstMatch, a Prepare user gets only rule 1, so the form is always read-only. That is the reason why TTDV2 uses MostPermissive.

19.8 Notes for the team

  • Rules only make parts read-only or hidden. Permissions decide if the operation is permitted at all. Both must agree. For example, Edit.Own: [Prepare] and rule 2 above agree.
  • The client does not run the rules again. It shows the states that the server sent. The server runs the rules again at save, so a changed browser cannot edit a disabled field.
