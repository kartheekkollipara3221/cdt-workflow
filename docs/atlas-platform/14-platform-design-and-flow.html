Atlas Platform Design and Flow

This document shows how the atlas-platform code works, from start-up to the saved record. It shows the flow of each request with a diagram. It also shows why this design is more reusable than the current target implementation.

1. Summary: what changes

Today, each business app in CP Atlas is a C# class. The class loads the JSON, binds the data, applies the rules, saves the record and runs the dashboard. Five app classes share one base class, but the app code also lives in the controller, in the Angular dashboard and in the Angular form. A new app needs new C# code, new EF models, new stored procedures and new TypeScript.

The platform turns this around. One generic service (ConfigSectionService) and one generic Angular form (AtlasFormComponent) run every app. The app is described in three JSON files and one SQL table. The code reads the table columns from SQL Server at start-up. A C# class is optional; TTDV2 has one class with one hook and two option providers (69 lines in total).

Backward compatibility. The current apps (TTD, AIN, SQMSO, SQMSB, CDT) do not change. The platform sits next to them. The controller asks the resolver first; if the code is not a platform app, the current if chains run as before.

2. How the target works today

The current flow for TTD is the reference. The numbers come from the read-only copy of the target.

  1. Routing by enumCPAtlasController gets code as the enum CPApplicationCode. CPAtlasService.LoadApplicationService(code) has an if chain that makes new CPTTDService(...), new CPAINService(...), and so on. A new code needs a new enum value and a new branch.
  2. App classCPTTDService (274 lines) reads TTD.json from a path in appsettings, loads TTDGeneral with EF, copies the seven day columns into the grid by hand, fills the account list from Oracle, and saves with MapData<TTDGeneral> (reflection on property names).
  3. No server checksThe UI validates. The server does not validate again, does not check that a value is in the options, and does not check the roles on save or delete. The audit entry is sent by the browser after the save (POST v1/AuditLog).
  4. Dashboard by procedureEach tab names a stored procedure. The procedure gives the rows and the column widths. A new tab is a new procedure.
  5. Angular branchescp-atlas-dashboard.ts has 14 references to app codes, and cp-atlas-sectionmaster.ts has 7. Field-change logic (for example Account → Account Number) is TypeScript for that app.

Spec 01, section 2, estimates the cost of app #17 with this design: a C# class, EF models, stored procedures, enum values, and TypeScript changes in the dashboard and the form.

4. Flow: start-up

The target program.cs gets two lines before Build(). The platform does the rest in a hosted service, before the server takes the first request.

builder.Services.AddAtlasPlatform(configuration);
builder.Services.AddAtlasModule<CPTTDV2Service>("TTDV2");   // one line for each app

The start-up check finds these errors before a user does: a manifest code without a registration line (and the reverse), a table or column that does not exist, a form field that names no column, an unknown option provider, a column type that the platform does not support, a SoftDelete field that is not IsDeleted, a rule or default that names an unknown control, a pattern that does not compile, and a typo in a JSON property name. The same checks run with BBH.CP.Atlas.App.exe --atlas-check --environment QC and return exit code 0 or 1.

5. Flow: one request

The controller endpoints do not change. CPAtlasService gets two optional constructor parameters, and each public method gets a few lines marked PLATFORM at its start.

The resolver gives 404 with a problem body when the app is not registered, when Enabled is false, when the start-up check disabled it, or when its table was not loaded at start-up. The AtlasProblemExceptionFilter turns each AtlasProblemException into an RFC 7807 response with title, status, detail, type and traceId.

The endpoints a platform app uses are the current ones: GET v1/Application (menu), GET v1/Dashboard, GET v1/SectionPage, POST v1/ManagePage, POST v1/RemovePage, GET v1/GetAuditLog. POST v1/AuditLog does nothing for a platform app, because the server writes the audit.

6. Flow: open a form

ConfigSectionService.LoadPage(page) builds the CPApplicationSection that the browser renders. The response has the same shape as today, with optional new properties (Version, UserPermissions, Computed, Effects).

  1. Manifest and formGet the enabled manifest of the app and a fresh copy of the form JSON from the config store.
  2. Record and accessFor ID > 0: load the row from the main table as a dictionary (no tracking), then Access.Demand(View). For a new record: Access.Demand(Create).
  3. Bind valuesAtlasFormFields.From(section) lists each control with a Field. Each value is converted to wire text by the column type. A grid with BindMode: SingleRowFields gets one row with one value for each column.
  4. OptionsA control with OptionsSource asks the named provider (PBAccounts, UsersInRoles, or an app provider such as TaxYears). With KeepSavedValue, an old saved value that is no longer in the list is added at the top. A user control gets the display name of the LAN ID.
  5. DefaultsAn empty control with a Defaults token gets its value: {User.LanID}, {User.DisplayName}, {Today}, {Options[n]}, or plain text.
  6. HookOnLoad(context). TTDV2 writes the dates of the selected week into the grid column headers.
  7. RulesRules.ApplyToSection sets Visible and Disabled on controls and buttons from the roles, the record state and the owner, with RuleMode and RuleDefault from the manifest.
  8. ResponseHeader name, AppCode, Version (the rowversion as Base64), UserPermissions (CanCreate, CanEdit, CanDelete, CanViewHistory) and Computed.

7. Flow: save a form

The save is the part of the platform with the most rules. The browser sends {AppCode, ID, Version, Outputs:[{Name, Value}]}. The server trusts no value: it checks each one against the form, the rules, the options and the column type.

The allow list in detail

Submitted valueResult
A name that is not a control of this formNotAllowed
A hidden or disabled field with a changed value (typed compare)NotAllowed; the same value is ignored
A value of a control with options that is not in the server list for this userNotInOptions; an unchanged saved value stays valid
A system column, a Computed target, or a SetFromOption / Set / Clear targetIgnored; the server sets it (Atlas.FieldIgnored)
Grid JSON that does not parseInvalidGrid
A field that a rule hid, then a client Show effectStill hidden: an effect can only narrow what the rules allow

A delete (RemovePage) sets IsDeleted = 1, ModifiedBy and ModifiedDate, and writes an audit row with event Delete. The Delete permission is enforced in both access modes.

8. Flow: dashboard

A platform dashboard tab has Source: Table, a Filter, an OrderBy and Columns. The platform builds the query. The current tabs with a Procedure still work the same way as today.

9. Flow: the browser

The Angular platform adds one route, form/:code/:id, next to the current sectionmaster/:code/:id. The current dashboard component gets one new line at the start of onClick and editRow: formRoute(formTypeOf(apps, code), code, id). An app with FormType: FORM in the menu rows opens the platform form; the other apps open the current pages.

10. Security and rules

Today

  • Roles set only the Visible and Disabled flags in the response.
  • Save, delete and download do not check the roles again.
  • The server does not validate the values.
  • Audit entries come from the browser after the save.
  • No version check: the last write wins.

Platform

  • Permissions in the form JSON: View, Create, Edit (Own / All), Delete, History. OwnerFields names the LAN ID columns that make a user the owner.
  • Access.Demand runs before each operation on the server. AccessMode: LogOnly logs Atlas.AccessDenied and continues (P1); Enforce returns 403. A Delete is always enforced.
  • The allow list, the option check and the validators run on the server (section 7).
  • The audit row is written in the same transaction as the record. The browser cannot add or change an entry.
  • The rowversion column gives a Conflict error when another user saved first.

Role tokens

A role name in a rule or in Permissions is a role of the app in the CP_Atlas_* tables. Two tokens are platform-wide: @Read (any role of the app) and @Admin (a role named Admin). The option provider UsersInRoles lists the users with the named roles, so a form can give a list of people with no SQL.

Rules

A rule has criteria (Roles, States, IsOwner) and effects (Visible, Disabled, ShowControls, HideControls, EnableControls, DisableControls). The manifest sets RuleMode (FirstMatch as today, or MostPermissive for a user with more than one role) and RuleDefault (what happens when no rule matches: ReadOnly or Hidden). The form JSON can give app-level Rules as the default for all section controls.

11. Why the design is reusable

The question for each module was the same: what must change when app #17 arrives? The platform moves each answer from code to data, or to one registration point.

Extension points, from smallest to largest

  1. JSON only. Fields, options, rules, effects, defaults, computed fields, permissions, dashboard tabs. No build, no deployment of code.
  2. Option provider. One class with Name, GetOptions and DescribeValue. The JSON names it.
  3. Hooks. OnLoad, OnBeforeSave (can add errors and change the record), OnAfterSave (must not throw). The module reads through the contexts and writes only through the record in OnBeforeSave.
  4. Renderer. One Angular component that extends AtlasRendererBase, registered by type name.
  5. Platform service. Added to AtlasModuleServices, so no module constructor changes.

What is not in P1. Step Master (multi-step forms, CDT), attachments, and the workflow engine adapter are designed (specs 02, 08, 10) but not built. P1 covers the Section Master apps. The same layers take the next modules.

12. What a new app needs

This is the onboarding list for an app with a single-page form (the TTDV2 pattern, spec 12, section 8).

  1. SQL scriptFrom docs/atlas-platform/sql/05-new-app-template.sql: schema, main table (ID int IDENTITY, CreatedBy, CreatedDate, ModifiedBy, ModifiedDate, IsDeleted bit NOT NULL DEFAULT 0, RowVersion), audit table, filtered indexes, grants, the app row and its roles.
  2. CODE.app.jsonThe manifest (figure: TTDV2.app.json, 19 lines).
  3. CODE.jsonThe form: sections, controls, validators, options, effects, rules, permissions, defaults, computed fields.
  4. CODE.Dashboard.jsonThe tabs and the add button.
  5. Role grantsUsers to roles in the CP_Atlas_* tables (template 06-grant-revoke-role-template.sql).
  6. One registration linebuilder.Services.AddAtlasModule<ConfigSectionService>("CODE"); when the app needs no hook, or a small class that inherits ConfigSectionService.
  7. Check--atlas-check returns 0. Then set Enabled for the environment.

No TypeScript change, no enum value, no stored procedure, no EF entity.
