1. Executive Summary

Fact The current application is a console-style .NET 10 proof of concept for a reusable SQL-backed workflow engine. Its primary purpose is to replace SharePoint Designer workflow behavior with metadata-driven workflow execution, task ownership, SLA tracking, notification outbox records, audit history, idempotency, optimistic concurrency, seed verification, and form-open workflow context output.

Fact Portfolio Trade is the first sample workflow definition. The code keeps Portfolio Trade behavior in seed metadata, sample JSON files, tests, and demo scripts rather than in a hardcoded Portfolio Trade engine service. The reusable engine works with workflow definitions, versions, states, actions, roles, transitions, tasks, SLA policies, notification routes, audit rows, idempotency records, and opaque section data.

Recommendation The current code is already separated enough to move into or reference from an ASP.NET Core API. The most practical integration strategy is to reuse the existing WorkflowEngine.Application, WorkflowEngine.Infrastructure, and WorkflowEngine.Domain projects, then replace the console command layer with API controllers or Minimal API endpoints. Do not move Program.cs or command handlers as-is into controllers; controllers should call the same underlying services directly.

Major integration risks: there is no API project in this repository; actor identity and roles are currently simulated through JSON/CLI input; MockSectionData is a POC substitute for real form persistence; start-workflow --reset and --admin-override are console/demo conveniences that should not become normal production endpoints; the workflow execution service is synchronous while web APIs usually prefer async paths for database I/O.

4. Current Runtime Flow

Startup Flow

  1. src\WorkflowEngine.Console\Program.cs builds configuration using base path AppContext.BaseDirectory.
  2. Configuration sources are loaded in this order: appsettings.json, appsettings.Development.json, environment variables, then command-line args.
  3. A ServiceCollection is created. The console registers IConfiguration, TimeProvider.System, validators, normalizers, hashers, result builders, command handlers, demo runner, and CommandRegistry.
  4. AddWorkflowInfrastructure(configuration) validates the SQL connection string and notification sender settings, then registers EF Core and infrastructure services.
  5. The console creates one DI scope, resolves CommandRegistry, and calls Dispatch(args).
  6. The returned CommandResult is written to Console.Out for exit code 0 or Console.Error for non-zero exit code.
  7. The process returns CommandResult.ExitCode.

Error and Exit Behavior

Console command errors return a non-zero CommandResult.ExitCode and a message written to stderr by Program.cs. Business errors inside workflow execution are normally represented as WorkflowActionResultEnvelope values with Success=false and result codes such as ValidationFailed, Forbidden, InvalidTransition, ConcurrencyConflict, WorkflowDefinitionVersionMismatch, IdempotencyConflict, AmbiguousRoleMatch, AlreadyExists, or WorkflowInstanceNotFound.

Major Module Explanations

Application Contracts

The contract classes solve the boundary problem between UI/API callers and the workflow engine. WorkflowActionEnvelope is the button-click command; WorkflowContextResponse is the form-open context; AvailableWorkflowAction tells the UI what actions are available; WorkflowActionResultEnvelope is the post-action response. These classes are business/application contracts, not console presentation logic. They should move directly into or be referenced by the API project and should become the public JSON contracts unless the API adds thin wrappers.

Validation, Normalization, Hashing, and Result Building

WorkflowActionEnvelopeValidator, WorkflowActionEnvelopeNormalizer, CanonicalRequestHasher, WorkflowActionResultBuilder, and CanonicalWorkflowResultSerializer form the reusable application layer around execution. The validator protects required envelope shape; the normalizer exists mainly for sample override reuse; the hasher enables idempotency; the builder centralizes response shapes; the serializer makes replay deterministic. These should be registered as DI services in the API. The API should call them in the same order as ExecuteJsonCommandHandler, but without file I/O.

Workflow Execution

WorkflowExecutionService is the core business operation. It resolves the persisted workflow instance, verifies request identity against that instance, verifies definition version, rejects completed workflows, resolves action and transition metadata, enforces actor role authorization, emits option conflict warnings, enforces concurrency guards, appends mock section data, closes and creates tasks, queues notification outbox rows, writes audit, and stores idempotency replay data inside one transaction. It is infrastructure/application orchestration logic and should be used as a scoped API service. A controller should not manually reproduce its behavior.

Persistence and Seed Metadata

WorkflowDbContext, entity classes, migrations, WorkflowSeedService, and SeedVerificationService solve the SQL persistence and metadata setup problem. They belong in the API infrastructure layer. The API should coordinate migration and seeding through deployment scripts or admin operations, not through public endpoints. Portfolio Trade seed metadata should remain seed data; do not convert it into code branches.

Workflow Context

WorkflowContextReader participates in both form-open behavior and refreshed post-action results. It reads the current instance, active version, current state label, pending task, SLA, and transitions available to the caller's roles. It should become a controller dependency for context endpoints or a dependency of domain form-open services. It should receive roles from authenticated claims in a real API.

SLA and Notification Outbox

RunSlaService is a background/operations service, not a user-click service. It scans active workflows with pending overdue tasks and queues one SlaTaskOverdue notification per task. ProcessNotificationOutboxService claims pending or expired-processing rows, sends through the configured INotificationSender, and marks them sent or releases the claim on failure. In an API project, these should usually run in hosted background services, scheduled jobs, or admin-only operations.

Console Command Layer

The command registry, argument parser, command handlers, and demo runner are presentation/orchestration for the console POC. They are useful documentation for behavior but should not be the primary API layer. In particular, ExecuteJsonCommandHandler reads from disk; an API endpoint should accept the envelope from the request body. Show* handlers format text; API endpoints should return typed JSON. DemoCommandHandler and start-workflow --reset are demo/test conveniences.

5. Create an execute action endpoint

The controller should accept a WorkflowActionEnvelope body, stamp actor identity, normalize, validate, hash, execute, and map result code to HTTP status.

[ApiController]
[Route("api/workflows/{workflowInstanceId}/actions")]
public sealed class WorkflowActionsController : ControllerBase
{
    [HttpPost]
    public ActionResult<WorkflowActionResultEnvelope> Execute(
        string workflowInstanceId,
        [FromBody] WorkflowActionEnvelope envelope,
        [FromServices] IWorkflowActorResolver actorResolver,
        [FromServices] WorkflowActionEnvelopeNormalizer normalizer,
        [FromServices] WorkflowActionEnvelopeValidator validator,
        [FromServices] CanonicalRequestHasher hasher,
        [FromServices] IWorkflowExecutionService executionService)
    {
        var actor = actorResolver.Resolve(User);
        envelope.Actor = new WorkflowActor
        {
            UserId = actor.UserId,
            DisplayName = actor.DisplayName,
            Roles = actor.Roles.ToList()
        };

        envelope.Workflow ??= new WorkflowActionBlock();
        envelope.Workflow.WorkflowInstanceId = workflowInstanceId;

        var normalized = normalizer.Normalize(envelope, businessObjectOverride: null, workflowInstanceOverride: null);
        var errors = validator.Validate(normalized.Envelope);
        if (errors.Count > 0)
        {
            // Prefer using WorkflowActionResultBuilder here to keep contract shape identical.
            return BadRequest(errors);
        }

        var result = executionService.Execute(new WorkflowExecutionRequest(
            normalized,
            hasher.ComputeHash(normalized.Envelope),
            AdminOverride: false));

        return StatusCode(MapWorkflowStatus(result.Result.ResultCode), result);
    }
}

Caution: The snippet is intentionally incomplete around error mapping. In your implementation, use WorkflowActionResultBuilder.BuildValidationFailed for validation failures so response shape matches the console contract.

public sealed class NotificationOutboxHostedService(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();
            var processor = scope.ServiceProvider.GetRequiredService<IProcessNotificationOutboxService>();
            await processor.ProcessAsync(stoppingToken);
            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
