1. Scope and ownership

Decision: the target API uses generic Start, Context, and Action services for user-driven SQMS workflow operations. It does not need WorkflowEngine.Sqms for these controller paths.

Target API owns

  • Authentication and trusted actor roles
  • Opportunity/Bid validation and persistence
  • HTTP DTOs and status mapping
  • Recipient and template-data enrichment
  • Saving returned Status/WorkflowState
  • The outer transaction

Generic engine owns

  • Workflow instance runtime
  • Metadata action/role validation
  • Authoritative next-state selection
  • Available actions and refreshed context
  • Audit, idempotency, and notification outbox
  • No knowledge of SQMS form fields
Not covered as HTTP requests: automatic Opportunity close, Bid classification, opening announcements, and reminders. Section 8 explains how the current scheduled implementation can be retained or transferred later.

3. How to read responses

Casing matters: the wrapper properties are lower camel case, while nested application-contract properties are PascalCase in the current API configuration.
JSON pathMeaning and target use
result.actionResult.SuccessWhether the Start/Action succeeded. Do not persist target workflow state when false.
result.actionResult.ResultCodeStable workflow result classification for target error mapping and logs.
result.actionResult.WorkflowInstanceIdEngine identity. It should match the deterministic ID convention.
result.actionResult.OldState / NewStateWhat the current operation changed.
result.actionResult.Notification.QueuedWhether this operation created an outbox record.
result.actionResult.Diagnostics.ReplayTrue means the engine returned the stored result. Do not repeat target writes or side effects.
result.workflowContext.Workflow.CurrentStateAuthoritative current state after success; persist this value to target Status and WorkflowState.
result.workflowContext.Workflow.WorkflowInstanceVersionCurrent engine version for concurrency display/coordination.
result.workflowContext.ActorAccess.CanActWhether the resolved actor can perform at least one current action.
result.workflowContext.AvailableActionsAuthoritative role-filtered buttons/actions for the UI. Do not hardcode actions from target status.

  • Resolve these values on the server from trusted Opportunity/Bid data and directory/application sources.
  • Do not let the browser select route keys, To/Cc placement, or arbitrary recipient input keys.
  • Metadata determines whether an action sends email and how inputs become To/Cc.
  • Static configured Cc recipients remain in NotificationRecipientRule; the request does not repeat them.

7. Persistence, transaction, replay, and failure

Begin target-owned SQL transaction → save prerequisite Opportunity/Bid business changes → invoke generic workflow service in-process on the same connection/transaction → verify actionResult.Success → verify Diagnostics.Replay is false → persist workflowContext.Workflow.CurrentState to target Status and WorkflowState → set target ModifiedBy and ModifiedDate → commit once
ResultTarget behavior
Success, not replayPersist authoritative returned state and commit target plus workflow changes together.
ReplayDo not repeat target updates, emails, or other business side effects. Reload and verify the already committed target state.
Workflow failureRoll back target changes. Map ResultCode/Message; do not infer a new state.
Exception or target persistence failureRoll back the shared transaction so runtime, audit, idempotency, outbox, and target state do not diverge.
HTTP boundary warning: calling a separate Workflow API process over HTTP cannot share the target EF transaction. The strongest consistency model is in-process use of the generic application/infrastructure services behind a thin target-owned application service.

8. Future scheduled ownership in the current code

The target team may choose not to use WorkflowEngine.Sqms for user-driven Start/Context/Action while still retaining its tested scheduled implementation.

Current technical contractMeaning
ISqmsScheduledService.RunAsync(CancellationToken)Supported entry point. Controllers should not call internal scheduled transition or notification-queue services directly.
AddSqmsWorkflowIntegration(configuration)Registers the current SQMS data store, workflow helpers, scheduled service, link builder, and options.
dotnet WorkflowEngine.Console.dll run-sqms-scheduledExisting operator/console trigger suitable for an external scheduler host.
process-notification-outboxSeparate operation that sends queued messages. The SQMS scheduled run queues; it does not replace the sender job.

Current run ordering

  1. Read open Opportunities and close those whose bidding period is due.
  2. Read closed Opportunities with submitted Bids and classify each valid Bid.
  3. Re-read still-open Opportunities so a just-closed Opportunity cannot receive a stale opening/reminder.
  4. Queue due opening/reminder occurrences with database replay protection.

Scheduled transitions alone directly project Status, WorkflowState, ModifiedBy, and ModifiedDate. Other Opportunity/Bid columns remain target-owned.

Option 1 — retain current scheduled project

Reference WorkflowEngine.Sqms only from the scheduled host. Lowest implementation and regression risk.

Option 2 — move scheduling into target worker

Transfer the scheduler, data-store queries, parsing, occurrence keys, and projection behavior into a target-owned worker while preserving acceptance behavior.

Option 3 — reimplement later

Use the current scheduled scenarios and live evidence as the acceptance contract. This carries the most reimplementation risk.

No public scheduled route exists. The target team owns the operator host, service identity, trigger schedule, non-overlap control, deployment, monitoring, and alerting.

9. Target implementation checklist

  • Register the generic workflow Application/Infrastructure services in the target host.
  • Keep controllers thin; use a target-owned workflow coordination service.
  • Build trusted actor ID/display name/roles from authenticated identity.
  • Use the exact SQMS workflow and ID keys shown here.
  • Save the Opportunity/Bid before Start.
  • Read AvailableActions instead of hardcoding UI actions from Status.
  • Supply server-resolved notification inputs only on configured notification actions.
  • Persist the authoritative context state only after non-replay success.
  • Use one in-process transaction across target and workflow persistence.
  • Keep scheduled processing disabled until its ownership and deployment are approved.
