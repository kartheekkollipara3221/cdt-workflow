1. The idea

A state machine is a thing with a life cycle. It has four parts:

PartMeaningExample from the engine
StateA condition that the thing can have.A task is Pending or Completed.
Move (transition)A permitted change from one state to another state.Pending to Completed.
TriggerThe event that starts a move.An action that closes the task.
GuardA check that must pass before the move.The version in the request is the same as the version in the database.

An explicit state machine has one place in the code that declares the states and the moves. All writers use that place. A test can walk the full table. An implicit state machine has no such place. Its states are text values, flags or empty dates. Its moves are if statements and UPDATE statements in many files.

Implicit (the engine today)

// ProcessNotificationOutboxService.cs
row.Status == "Pending"
.SetProperty(item => item.Status, "Sent")

// WorkflowActionNotificationDispatcher.cs
.SetProperty(item => item.Status, "Processing")

// WorkflowSlaSynchronizationService.cs
row.Status = "Cancelled";

Six files write the e-mail status. Each file has its own text values and its own checks. Only the SQL CHECK constraint knows the full list of values.

Explicit (the shape that the project rules permit)

// Example only. Not approved code.
public static class OutboxStatus
{
    public const string Pending = "Pending";
    public const string Processing = "Processing";
    public const string Sent = "Sent";
    public const string Cancelled = "Cancelled";
}
// + one small class with the permitted moves
// + one test that walks the table

One place has the values and the permitted moves. The stored text stays the same. No library is necessary.

Why this is important

  1. Two copies of one rule can become different. The e-mail delivery (E05) is written two times. Three differences exist today.
  2. A state with no name is difficult to monitor. A reminder that cannot be queued (E04, "Blocked") is only a warning text. The warning comes back at each scan.
  3. A typing error in a text value compiles. If code compares with "Canceled" in place of "Cancelled", the query finds no rows and gives no error. If code writes that value, the SQL CHECK constraint refuses it at run time. The engine has 96 such values in 13 files (inventory, appendix A).
  4. A rule between two machines can break, and nobody sees it. Example: a completed workflow can keep an open task (rule I1, section 4).
This is not a defect list. Most of the 24 machines work correctly today. The inventory is a map. The main workflow state machine (states, actions and transitions in the metadata) is already explicit, and it is the design of the engine. The inventory lists only the life cycles around it.

5. Engine machines (E01 to E13)

Short names: WES = WorkflowExecutionService.cs, SWS = StartWorkflowService.cs, SLASYNC = WorkflowSlaSynchronizationService.cs, RUNSLA = RunSlaService.cs, OUTBOX = ProcessNotificationOutboxService.cs, DISPATCH = WorkflowActionNotificationDispatcher.cs, APIACT = WorkflowActionService.cs (API), CTX = WorkflowContextReader.cs, DBC = WorkflowDbContext.cs. The red numbers in each figure are the numbers of the findings below the figure.

E01 Workflow instance life cycle Known HighAct

One row in WorkflowInstance stands for one business object, for example one trade. Status tells if the workflow runs (Active) or is finished (Completed). CurrentStateKey tells the business step, for example Draft or PendingChecker. Version counts the moves. Each move adds 1.

1 SaveDraft does not use the version check Known: SaveDraft race, High, open

All other actions change the instance with one guarded UPDATE: "write the new state WHERE Version = the version that I read". If another request changed the instance first, zero rows change, and the action stops with ConcurrencyConflict. SaveDraft does not run this UPDATE (WES:675-676).

  1. The trade is in Draft, Version 3. User A and user B open it.
  2. User B sends SubmitForChecker. At the same time, user A sends SaveDraft.
  3. Both requests read Draft, Version 3. All checks pass for both.
  4. The guarded UPDATE of B writes PendingChecker, Version 4. B commits.
  5. The SaveDraft of A has no guarded UPDATE. Nothing reads the version again. A commits its audit row ("SaveDraft, Draft to Draft") and its idempotency record.

Effect. The engine tells user A that the draft save succeeded. But the trade is already with the checker. The audit shows a draft save in a state that the trade had left. In the console path, the section data of A is also saved.

Decision. Q41 and W4. The fix must decide the answer for a SaveDraft that comes after another move. ConcurrencyConflict agrees with the behaviour of all other actions.

2 Start does not check that the first state exists Code fact

Start always writes the literal Draft as the first state (SWS:400). It does not check that the active version has a state with the key Draft. The literal itself is accepted (D08). The gap is only the missing check.

Example. A new workflow calls its first state New. Start makes the instance in Draft. No transition starts at Draft. Each action gets InvalidTransition: "No transition exists for state 'Draft'". The instance cannot move. W7 adds this check.

3 A move to a terminal state does not check the open task Code fact

PROJECT.md section 15 says that no Pending task can stay when the workflow completes. The code closes a task only when the transition row names it in TaskToCloseKey (WES:702-724). Nothing checks the result.

  1. A new workflow has the transition Approve: PendingChecker to Approved. Approved is terminal.
  2. The metadata author forgets TaskToCloseKey on this row.
  3. The checker approves. The instance becomes Completed.
  4. The checker task stays Pending. Its SLA schedule stays Active.
  5. The SLA scan reads only instances that are Active. It never selects this schedule again.

Effect. No wrong e-mail goes out. But the data shows an open task and an active SLA for a finished workflow, for all time. Each report that counts open tasks counts it. The current PortfolioTrade and SQMS metadata do not have this error. The risk is in new metadata. W7 can find the error before a version becomes active.

4 Two sources say "finished" Code fact

Source 1 is Status = 'Completed'. Source 2 is IsTerminal = 1 on the state definition of CurrentStateKey. All guards read source 1. If a person changes IsTerminal in place on a version that has instances (see D09), the old instances get two different answers. A report that reads IsTerminal then disagrees with the engine.

5 The switch for the whole workflow is not read at Start Code fact

WorkflowDefinition.IsActive is the switch for the whole workflow. Start reads only the switch of the version (SWS:441-452). If an operator sets the workflow inactive and the version stays active, new instances still start. Only the notifications without an instance read the workflow switch (QueueWorkflowNotificationService.cs:36).

What you decide. Q40 (start engine work), Q41 (SaveDraft first), and if you want W7 (metadata check command).

E02 Task life cycle Stable

A task is work for one role, for example the checker review. It is Pending (open) or Completed (closed). The database permits at most one Pending task for each instance (filtered unique index, DBC:310-312). There is no Cancelled state; the specification does not have one. A workflow with no tasks is valid (SQMS).

1 A metadata error looks like a concurrency error Code fact

Before a move, the engine checks that the task in TaskToCloseKey is the open task (WES:1061-1072). If the names are different, the result is ConcurrencyConflict with the field expectedCurrentTaskKey.

Example. The transition says "close CheckerReview". The open task is MakerRework. The user gets "the workflow changed; load it again". The user loads it again and tries again. The same error comes back each time, because the cause is in the metadata, not in another user. Support can look in the wrong place.

2 Three ways to read "the open task" Code fact

WES uses OrderBy(Id).FirstOrDefault (it takes the oldest). CTX uses SingleOrDefault (it fails if there are two). SLASYNC uses Single (it fails if there are none or two). Today the index permits at most one, so the three agree. If a script or a schema change ever permits two open tasks, the three places act differently. W1 can pin this.

What you decide. Nothing now. Both items are part of W1 and W7.

E03 SLA schedule life cycle Known F09Act

A task with an SLA policy gets a schedule. The schedule says when the task becomes overdue and when the reminders go out. Active: in use. Superseded: replaced, because the target date changed. Completed: the task closed. Each task has at most one Active schedule (filtered unique index). WorkflowTask.DueAtUtc is a copy of OverdueAtUtc of the Active schedule.

1 An SLA change and a task completion at the same time Known: F09, open

  1. The target application sends a new target date for task T (an SLA-only request).
  2. At the same time, a user completes task T.
  3. The SLA request reads task T as Pending. It does not lock the row (SLASYNC:171-178).
  4. The completion commits: task T is Completed, schedule v1 is Completed.
  5. The SLA request can then write schedule v2 as Active for task T.

Effect. A closed task has an Active schedule, so rule I2 breaks. The scan does not select it, because the task is not Pending. No wrong e-mail goes out, but the data is not correct. Work item W8.

2 An SLA-only request with no open task gives HTTP 500 Inference - verify (code path agrees)

  1. The caller sends an action request with workflowInstanceId and slaTargetDate, and no actionKey.
  2. The instance has no Pending task. Examples: it is in Draft, it is Completed, or the ID does not exist.
  3. The SLA service looks for the one open task with .Single(). There is none, so .NET throws InvalidOperationException.
  4. The API catches only WorkflowSlaValidationException (APIACT:92-98).
  5. The global exception handler gives HTTP 500 for all other exceptions: "An unexpected error occurred."

Effect. Compare: an action request with an unknown ID gets the structured result WorkflowInstanceNotFound. The SLA-only request with the same ID gets a general 500. The caller cannot tell "wrong ID" from "server error". The log records an error for a mistake of the caller. Work item W6 (contract change: stop-and-ask, see question 5).

3 Only a task completion ends an Active schedule Code fact

No other code ends an Active schedule. If a task stays Pending on a completed instance (E01, item 3), its schedule stays Active for all time.

What you decide. W8 (F09) and W6 (the answer for the SLA-only case).

E04 SLA reminder cursor Act

In an Active schedule, the column NextReminderAtUtc is a cursor. It tells when the next reminder is due. The SLA scan runs on a timer. It finds the schedules with a cursor that is due, queues one e-mail row for each reminder, and moves the cursor to the next time. The kind of reminder (DueToday or Overdue) is not a column. The scan calculates it again each time.

1 "Blocked" is not stored and does not end Code fact

If the scan cannot queue a reminder, it rolls back, adds a warning to the run result, and does not move the cursor. The next scan selects the same schedule and fails again. This continues until the task closes or a person corrects the data. There are six causes (RUNSLA:178-240, 280-287):

  • The recipient list (snapshot) is missing or not valid.
  • The route key of the reminder is missing.
  • The task context JSON is not valid.
  • The first e-mail of the task (the "primary" row) is missing, or there are two.
  • The subject is longer than 300 characters.
  • The calendar data has an error.

Effect. This is the specified behaviour ("warned and skipped"). The gap: nobody can count blocked schedules in the database, and the same warning comes back at each scan. The task owner gets no reminder.

2 A rule between machines that no code checks early Code fact

A reminder copies its subject and body from the first e-mail of the task. That is the outbox row with the same task and no reminder kind (RUNSLA:219-231). This row exists only if the transition that created the task has a notification route.

Effect. A task with an SLA policy must come from a transition with a route. If that transition has no route, the schedule is Blocked at each scan. Nothing checks this before the first scan. W7 can check it when the metadata is made.

3 The kind of reminder is calculated in three places Code fact

(1) The calculator, when the schedule is made. It does not store the value. (2) The scan, with its own expression (RUNSLA:366). (3) The workflow context shows OnTrack or Overdue. It compares DueAtUtc with the clock (CTX:165-201), as PROJECT.md section 13 specifies. Places 1 and 2 must agree. If somebody changes only one of them, they disagree. W1 can pin them.

What you decide. If you want W7 (check the route rule early). A stored "blocked" state is not in the inventory list; it would be a new item.

E05 E-mail outbox delivery ActKnown D04

Each e-mail is first a row in NotificationOutbox. A sender claims the row: it writes Processing, a token and a start time. Then it sends the e-mail and marks the row Sent. If the send fails, the row goes back to Pending with a later retry time. There are two senders: the outbox worker (a job on a timer) and the API dispatcher (it sends the e-mails of one action during the HTTP request).

Claim, send, "mark Sent" and release are in the worker (OUTBOX) and again in the API dispatcher (DISPATCH). In total, six files write the status: three insert rows (WES, RUNSLA, QueueWorkflowNotificationService.cs) and three change rows (OUTBOX, DISPATCH, SLASYNC). The two copies are not the same:

2 No maximum number of attempts Known: D04, owner decision open

A row that always fails goes back to Pending each time, and RetryCount grows. With the default settings (zero delay), the worker tries it again at each run. With a delay, the delay doubles after each failure, up to the maximum (default 3600 seconds). There is no dead-letter state.

3 "At least once" Known: by design

After a send, "mark Sent" can change zero rows. A stopped process can also leave a stale claim, and the worker claims it again. Then the same e-mail can go out two times. This is accepted.

4 Cancel during send Inference - verify (code path agrees)

  1. 09:00:00 The worker claims an SLA reminder row: Processing, token T.
  2. The worker checks the schedule: it is Active. The worker calls the SMTP server.
  3. 09:00:01 A checker closes the task. The same transaction completes the schedule, sets the reminder row to Cancelled and clears the token (SLASYNC:219-231).
  4. 09:00:02 The SMTP server accepts the e-mail. The reminder goes out.
  5. The worker runs "mark Sent WHERE Status = Processing AND token = T" (OUTBOX:141-155). Zero rows match.
  6. The run result has only the warning "row N was claimed but could not be marked Sent".

Effect. The e-mail went out, but the row says Cancelled (reason WorkflowTaskCompleted). A person who reads the outbox thinks that no reminder went out. The business effect is small: one reminder at the moment of completion. But the record is not true. Work item W5: write the test first.

Example of a design, not approved: the cancel does not change a row in Processing with a fresh lease. The worker then marks that row Sent or Cancelled.

5 The requirement text is older than the code Code fact (not in the figure)

PROJECT.md section 14 says that the command stops at the first failure. The code continues with the next rows (OUTBOX:168-187). docs/OUTBOX_RETRY_ROLLOUT.md describes the code. This is a gap in the text, not a code defect. Only you can approve a change to PROJECT.md.

What you decide. W3 and each of its three differences (question 4), W5, and D04 (maximum attempts).

E06 Idempotency record Known L1, L4, F07

An idempotency key names one request. If the same request comes again (for example a retry), the engine gives back the first result and does not do the action a second time.

State of the keyRequestWhat the engine does
UnknownAnyIt runs the action. On success, it stores the record in the same transaction (WES:885-891).
StoredSame request hashIt returns the stored result with Replay = true. This check comes first, before all other checks (WES:61-65).
StoredDifferent request hashIt returns IdempotencyConflict (WES:962-969).
Unknown, two requests at the same timeSame keyThe second insert breaks the unique index. The engine reads the record and returns the replay (WES:892-903).

The source of the key is different for each caller. The API makes a new GUID for each HTTP request. SQMS makes a fixed key from the entity, the version and the action. Start uses the key of the request, or a new GUID.

Only a success is stored Code fact

A failed request with the same key runs again. This is usually correct, because a retry after a failure can succeed. Do not expect a replay of a failure.

Known items Known: L1, L4, F07, retention

  • L1. An HTTP caller cannot send its own key. So a retry after a timeout is a new action. If the first call committed, the retry usually gets InvalidTransition, because the state moved.
  • L4. The duplicate check reads the SQL message text (error 2601 or 2627 and the text "IdempotencyRecord", WES:944-950). A new index name or a message in another language breaks it.
  • F07. The assignment role is not in the request hash. The same key with another role gives the old result, not IdempotencyConflict.
  • Retention (deferred). No rule removes old records. The table grows.
What you decide. Nothing new. W1 pins the four rows of the table.

E08 Version activation and metadata IsActive ActKnown D09

A workflow has versions, for example PortfolioTrade v1 and v2. One version is active, and new instances use it. A running instance keeps its own version. Each metadata row also has IsActive. Rows become inactive. They are never deleted.

The database does not keep "one active version" Code fact

No filtered unique index exists. The SQL scripts check the rule (error 52502), and the seed service keeps it. SeedVerificationService checks it only for PortfolioTrade. If a script leaves zero or two active versions, Start throws an exception for that workflow key (SWS:441-452). No new workflow of that kind can start.

The IsActive filter is not the same in all readers Code fact

Example. An administrator sets a task definition inactive, but a transition still names it.

  1. The action creates the task. WES:728-732 reads the definition with no IsActive filter.
  2. If the task has an SLA policy, the SLA service reads the same definition with the filter (SLASYNC:32-35, .Single). It throws, and the action fails with an error.
  3. If the task has no SLA policy, the action succeeds. It makes a task from an inactive definition.

SQMS sends version 1 as a literal Code fact

SqmsScheduledService.cs:246 asks for the route of version 1. The queue needs that version to be active (QueueWorkflowNotificationService.cs:37-38). If SQMS gets an active version 2, the open and reminder e-mails fail with NotFound.

The seed changes version 1 in place Known: D09, Major, open

There is no publication procedure for a new version.

What you decide. If you want W7. It checks "one active version" for all workflows, not only PortfolioTrade.

The two-phase result Known: D02 / F06, open

P01 Record life cycle Act

Each app has a main table (pilot: TTDV2.General). A record is New (ID = 0, not saved yet), Active, or Deleted. Delete is a soft delete: IsDeleted becomes 1, the row stays, and the platform treats the row as "not found". RowVersion is the version token: a save must send the version that the user loaded.

1 No restore Code fact

Only the delete sets IsDeleted to 1 (CSS:739). Only a new record sets it to 0 (CSS:473). A deleted record can come back only with SQL. If users need an "undo", that is a new feature.

2 Delete sends no version token Code fact

  1. 10:00 User A opens record 42.
  2. 10:05 User B opens record 42, changes the hours, and saves. The RowVersion changes.
  3. 10:10 User A clicks Delete on the old screen and confirms.
  4. The server deletes record 42. It does not compare versions, because RemovePage(int id) has no version (CSS:725; client WEB/atlas-api.service.ts:44-47).

Effect. User A deletes a record with changes that A did not see. A save in the same situation gets Conflict. No data is lost: it is a soft delete, and the audit has the Delete entry. The inventory has no work item for this. A fix needs a version in the delete request. That is a v1 contract change, and RemovePage(int id) is a method that the target code calls. Both are stop-and-ask.

3 A save with no change still changes the RowVersion Inference - verify (code path agrees)

  1. User A and user B open record 42.
  2. User A clicks Save with no change. The server writes ModifiedBy and ModifiedDate (CSS:476-477), so the RowVersion changes. The audit writes no entry, because no field changed.

P02 Save steps and result protocol Stable

The save runs 12 steps in a fixed order with one state object (SaveState, CSS:263-326): load, rules, read and filter, validate, check the version, map, stop on errors, computed and system fields, OnBeforeSave, stop on errors, save, complete. This part is already clear.

Two parts are implicit:

  • Two channels for a failure. A business failure returns HTTP 200 with ID = 0 and a list of Errors (CSS:843-850). An access failure or "not found" returns an HTTP problem: 403, 404, 400 or 500 (APP/AtlasProblemExceptionFilter.cs). A client must check both channels. The platform client does.
  • Error codes are text values: NotAllowed, NotInOptions, InvalidGrid, VersionRequired, Conflict, SaveFailed, and the codes of the validator and the value converter. The client adds Http and Invalid.

Decision SV-06: a failure in OnAfterSave is logged, and the save still returns success.

Why const, and not static readonly or an enum (W2)

EF Core writes a const value into the SQL as a fixed text: WHERE [Status] = N'Pending'. That is the same SQL as today. A static readonly field or a variable becomes a SQL parameter: WHERE [Status] = @p0. Then the SQL text changes, and SQL Server can stop using a filtered index for that query, because a filtered index matches fixed values. An enum changes the type of the property and needs a value converter. So const is the smallest change that keeps the database behaviour the same.
