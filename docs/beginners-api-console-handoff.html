3. Mental Model

What this project owns

Workflow state, metadata-driven transitions, tasks, SLA due dates, notification outbox rows, SMTP sender abstraction, idempotency, audit history, and workflow context/action result contracts.

What this project does not own

Form field validation, real user lookup, role lookup tables, business object lifecycle, UI rendering, JWT policy decisions, or Portfolio Trade field-level business rules.

Core flow

1
Form/business API creates or loads the business object. The workflow engine does not create the business record and does not validate form fields.
2
Workflow starts or moves by action key. The caller sends workflowKey, business object identity, or a workflow instance ID plus an actionKey. The caller never sends toState.
3
SQL metadata decides the transition. The engine matches current state, action key, and allowed role. It closes and creates tasks, writes audit rows, queues notification rows, and updates the workflow instance in one workflow transaction.
4
The API returns workflow result and context. The UI uses refreshed workflow context for current state, current task, SLA, and available workflow actions.

Portfolio Trade sample only

Portfolio Trade proves the reusable engine. Its states, roles, actions, notification text, and sample JSON are seed/demo metadata. Do not hardcode Portfolio Trade behavior inside the reusable engine.

4. Local Setup

Prerequisites

  • .NET 10 SDK.
  • SQL Server reachable from the developer machine.
  • Optional fake SMTP server such as smtp4dev for SMTP smoke tests.

Local connection string

The current local verification database used by this repo is:

Server=DOLLY;Database=cdt_workflow_api_20260527;Integrated Security=true;TrustServerCertificate=True;Encrypt=False

It is configured under ConnectionStrings:DefaultConnection. Environment override form:

$env:ConnectionStrings__DefaultConnection='Server=DOLLY;Database=cdt_workflow_api_20260527;Integrated Security=true;TrustServerCertificate=True;Encrypt=False'

Target API naming mismatch

The target API sample uses an existing app context connection named DBConnection. Workflow infrastructure expects DefaultConnection. Either add ConnectionStrings:DefaultConnection to the target API configuration or intentionally map the same database connection under both names.

6. API Endpoints

The active reference API is workflow-api/src/WorkflowEngine.WorkflowApi. It is controller-based ASP.NET Core and keeps controllers thin.

Workflow-only request shape

The API request body intentionally omits console-only dataSave, UI echo fields, expected state guards, idempotency keys, and business object payload. The target form/business API owns form data persistence and should call workflow after its own business save succeeds.

7. Target API Integration

Treat this repo as the workflow reference source. The destination API may have its own project names, DbContext, authentication, controller style, and response wrapper. Keep the integration narrow.

Target API goal

On one user action, the target API should save its own form/business data, execute exactly one workflow action, dispatch notification rows created by that action, and return a response to the UI. 

Target API request
  -> authenticate user in target API
  -> save target business/form data in target tables
  -> call workflow execution/start service
  -> dispatch action-created notification rows for WorkflowInstanceId + CorrelationId
  -> return actionResult + workflowContext

Step-by-step integration plan

1
Add workflow project references. Reference WorkflowEngine.Application, WorkflowEngine.Domain, and WorkflowEngine.Infrastructure from the target API project or copy them into the target solution with the same project boundaries.
2
Register workflow infrastructure in the target API composition root. Keep the target API's existing app DbContext registration. Add workflow infrastructure separately. Do not replace the target API's existing database context. 
builder.Services.AddWorkflowInfrastructure(builder.Configuration);
3
Configure workflow database connection. Add ConnectionStrings:DefaultConnection. It may point to the same SQL Server database as the target API if that is the deployment decision, but the key name must exist for workflow services.
4
Map target identity to workflow actor. Use the target API's authenticated LAN ID, display name, and application roles/claims. Do not create a workflow SQL user table.
5
For new business records, start workflow. Call the application start workflow service, or expose a thin endpoint equivalent to POST /v1/WorkflowStart. Use initialActionKey when the first user click should submit immediately instead of just creating Draft.
6
For existing records, execute workflow action. Build an internal workflow action envelope from target API data, or use the reference WorkflowActionService pattern. Set PersistSectionData = false for API integration because the target API owns form data.
7
Dispatch action-created notifications immediately. Copy or adapt IWorkflowActionNotificationDispatcher and WorkflowActionNotificationDispatcher. After a successful workflow action, dispatch pending rows by WorkflowInstanceId plus CorrelationId. Convert dispatch failure to NotificationDeliveryFailed so the UI does not see a false success.
8
Return workflow result and context. Preserve the target API's existing wrapper style if needed, but include the workflow action result and refreshed context so the UI can update buttons/state without guessing.

Minimal target service pattern

public TargetActionResponse SubmitOrMoveWorkflow(TargetActionRequest request)
{
    var actor = ResolveActorFromTargetAuth();

    // Target API owns business/form data.
    SaveTargetBusinessData(request);

    var workflowResult = ExecuteWorkflowAction(actor, request);

    if (workflowResult.Success && workflowResult.Notification?.Queued == true)
    {
        DispatchCreatedNotifications(
            workflowResult.WorkflowInstanceId,
            workflowResult.CorrelationId);
    }

    if (!workflowResult.Success)
    {
        return BuildFailureResponse(workflowResult);
    }

    var context = ReadWorkflowContext(
        workflowResult.WorkflowInstanceId,
        actor.UserId,
        actor.Roles);

    return BuildSuccessResponse(workflowResult, context);
}

8. Notifications and SMTP

Notification model

  • Workflow transitions queue rows in NotificationOutbox.
  • Rows are rendered from SQL metadata templates and caller-provided notificationContext.
  • Rows store both plain text and HTML bodies; HTML values from notificationContext are escaped by the engine.
  • Recipients are separate typed notificationRecipients To/Cc arrays supplied and validated by the caller.
  • The exact recipient snapshot is stored on the task and initial outbox row; SLA reminders reuse the task snapshot unchanged.
  • Action-created rows are dispatched by the API immediately after the workflow transaction commits.
  • One outbox row is one complete email and one message-level retry lifecycle; there is no partial recipient status.
  • Pending rows remain available for retry through process-notification-outbox.
  • SLA overdue rows are created by run-sla, not by form buttons.

Sender options

Value Behavior Use
Notifications:Sender = Console Writes notification output to console. Console demo default.
Notifications:Sender = NoOp Does not send real email. Reference API default.
Notifications:Sender = Smtp Sends one multipart text and HTML email with MailKit using SMTP host/from config and the row's exact typed To/Cc snapshot. Target SMTP integration and live smoke testing.

SMTP configuration shape

{
  "Notifications": {
    "Sender": "Smtp"
  },
  "Smtp": {
    "Host": "smtp.your-firm.example",
    "Port": 25,
    "From": "workflow@example.test",
    "RecipientOverride": "operator@example.test"
  }
}

Smoke-test safety

Keep Smtp:RecipientOverride set during live SMTP smoke testing. Remove it only when ready to send to the caller-supplied recipients.

Caller-supplied typed recipients

"notificationRecipients": {
  "toEmailAddresses": ["primary@example.test", "secondary@example.test"],
  "ccEmailAddresses": ["manager@example.test", "operations@example.test"]
}

The target API builds and validates both ordered arrays from business data it already owns. The workflow API replaces only actor identity from trusted headers and passes recipient strings unchanged. The engine does not trim, normalize, validate, deduplicate, resolve roles/directories, or parse singular/delimited recipient fields.

The created task and initial outbox row store the same exact recipient snapshot. SLA overdue rows copy the task snapshot unchanged. Smtp:RecipientOverride sends only to the override mailbox, suppresses intended To/Cc envelope recipients, and writes both ordered intended lists into the controlled diagnostic body.

Send notification values as plain data, not HTML. Seeded templates bold important values in the HTML email body and render tradeLink as a clickable link.

Common notification context tokens

Scenario Useful tokens
Task assignment referenceNumber, submitterDisplayName, recipientDisplayName, deskName, securityType, accountShortName, accountDisplayName, submittedDate, tradeLink
Return to Maker referenceNumber, returnedByDisplayName, recipientDisplayName, accountShortName, accountDisplayName, submittedDate, tradeLink
Trading execution to BDRM traderDisplayName, deskName, securityType, accountShortName, accountDisplayName, tradeLink
Workflow completion confirmerDisplayName, accountShortName, accountDisplayName, tradeLink

If required template tokens are missing, workflow execution returns validation failure and rolls back workflow side effects. The target API should build notificationContext from data it already owns.

9. Task Scheduler

Use a separate scheduled processor on the target machine for SLA overdue detection and notification retry. The processor can be the published console app.

Recommended wrapper script

$ErrorActionPreference = 'Stop'
Set-Location $PSScriptRoot

& dotnet .\WorkflowEngine.Console.dll run-sla
if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }

& dotnet .\WorkflowEngine.Console.dll process-notification-outbox
exit $LASTEXITCODE

What each scheduled run does

Step Effect
run-sla Scans pending tasks with overdue DueAtUtc and queues one overdue notification per task.
process-notification-outbox Sends pending notification rows, including failed action-created rows and SLA overdue rows.

Why the scheduler still matters

The target API sends normal action-created notifications immediately, but if SMTP fails the row is released back to Pending. The scheduled outbox processor is the retry/backlog path.

10. Database and Migrations

Schema ownership

Workflow EF Core is pinned to the dbo schema through WorkflowDbContext.DefaultSchema, HasDefaultSchema("dbo"), and migration history table configuration for [dbo].[__EFMigrationsHistory].

Deployment decision needed

Decide how the target machine applies workflow migrations. Options include a deployment pipeline step, a controlled admin migration run, or a one-time DBA-reviewed script. Do not use the console demo --reset behavior as a production data management tool.

Fresh local setup

dotnet run --project src\WorkflowEngine.Console -- init-db
dotnet run --project src\WorkflowEngine.Console -- verify-seed

If tables were created under the wrong schema

Existing databases that already contain workflow tables under a user default schema need a controlled cleanup or schema transfer. The current code fixes fresh migrations; it does not automatically move old incorrectly owned tables.

12. Pitfalls

Pitfall Correct behavior
Adding toState to request JSON. Do not. SQL transition metadata decides next state.
Hardcoding Portfolio Trade transitions in services. Do not. Portfolio Trade is seed/sample metadata only.
Using the target API as the SLA/outbox scheduler. Do not. Use Task Scheduler or a separate worker process.
Creating a workflow user or role mapping table. Do not. User identity and roles come from target auth/claims or trusted integration boundary.
Letting workflow.options override metadata. Do not. Options are advisory; metadata wins.
Calling DateTime.UtcNow inside workflow services. Use injected TimeProvider.
Using System.Net.Mail.SmtpClient. Use MailKit. It is the only pre-approved third-party package for SMTP.
Adding SMTP credentials in appsettings. Do not. v1 assumes IP-restricted relay. Credential support needs a secret-management decision.
Declaring the target service itself as IWorkflowActionNotificationDispatcher. Keep the dispatcher as a separate class and register it separately.
Reusing a completed business object ID in production. Do not. v1 has one workflow lifetime per business object identifier.

Quick handoff summary

Use src/ for the reusable engine and console processor. Use workflow-api/ as the active API reference. In the target API, save business data first, execute workflow second, dispatch action-created notifications by workflow instance plus correlation id, and schedule console run-sla plus process-notification-outbox outside IIS.
