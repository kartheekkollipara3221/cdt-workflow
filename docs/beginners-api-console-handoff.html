Beginner Handoff: How the Workflow API Works

The short version

Your application saves its own form data, resolves the few users that come from UI fields, and calls the workflow endpoint. The workflow engine decides the valid transition from metadata. It owns workflow state, tasks, SLA, recipient placement, notification snapshots, audit, and retry state.

A real Maker-submit scenario

  1. The Maker completes the business form. The business API saves it.
  2. The UI already knows the logged-in Maker and resolves that person's stored address.
  3. The UI calls Workflow Start with originalMaker. It may include UI-selected copied users under selectedCcUsers.
  4. The engine loads the active workflow definition and derives businessObjectType.
  5. The engine captures originalMaker once in WorkflowParticipant.
  6. The selected transition loads ordered recipient rules. For submit, metadata supplies the Checker To address and optionally consumes selected copied users for Cc.
  7. The engine resolves one final To/Cc snapshot, creates the task and outbox row transactionally, and stores the same snapshot on both.
  8. Future return-to-Maker routes read the captured participant. The UI cannot replace the Maker.
  9. SLA reminders copy the task snapshot unchanged, even if metadata or participant rows later change.
Address strings can be stored without validation. The workflow capture/resolution path does not check email syntax, a directory, a mailbox, or SMTP. Delivery may still fail later when the configured sender tries to construct or send the message; that failure applies to the one outbox message and uses its one retry lifecycle.

What the UI does not send

  • No destination state. It sends actionKey; metadata determines the destination.
  • No business-object type on Start. The workflow definition owns it.
  • No current state, current task, or version echoes. The engine reads persistence.
  • No body correlation or idempotency IDs. The trusted API generates them.
  • No final To/Cc arrays. Recipient rules own placement.
  • No SLA duration, reminder time, timezone, recurrence, route, or UTC deadline. Metadata owns those.
  • No form/section data. The business API owns it.

Start versus Action

When no workflow instance exists, call POST /v1/WorkflowStart and persist the returned workflowInstanceId with the business record. Every later button click calls POST /v1/WorkflowAction. An Action request may omit actionKey only when it carries slaTargetDate for same-endpoint SLA synchronization.

Console versus HTTP

The console is an engine test harness. execute-json reads the larger internal WorkflowActionEnvelope under samples/workflow-actions. Those files intentionally exercise console-only request metadata, guards, test form data, and direct final recipient arrays. Do not use them as UI bodies. 

dotnet run --project src/WorkflowEngine.Console -- init-db
dotnet run --project src/WorkflowEngine.Console -- verify-seed
dotnet run --project src/WorkflowEngine.Console -- demo
